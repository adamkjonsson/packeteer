# Plan — issues #71, #72, #73

*Written 2026-08-11. Status: not started. Both open questions settled
2026-08-11 — see [#71](#71--parsedpacketpayload_offset) and
[#73](#73--ergonomics-making-reassembly-the-default).*

Three issues added to the v0.8.0 milestone after the first six (#61–#66) were
merged to `main`. All three come from
[zpfwire](https://github.com/adamkjonsson/python-zipline-wire), the downstream
project reviewing the `0.8.0.dev0` build, and all three are follow-ons from
work that has already landed.

| Issue | Summary |
|-------|---------|
| [#71](https://github.com/adamkjonsson/packeteer/issues/71) | `ParsedPacket` carries no payload offset, so a record's byte offset cannot become the payload's |
| [#72](https://github.com/adamkjonsson/packeteer/issues/72) | `Defragmenter` reports nothing about which fragments composed a reassembled datagram |
| [#73](https://github.com/adamkjonsson/packeteer/issues/73) | Ergonomics of the defragmentation API — reassembly should be the default |

## The constraint that shapes all three

**0.8.0 has not shipped.** `Defragmenter`, `open_pcap`, `PcapRecord` and the
new `ParsedPacket` fields exist only in `0.8.0.dev0`, so their APIs can still
change outright — no deprecation shims, no compatibility layers, no
`Breaking:` markers needed for anything introduced in this same unreleased
cycle.

This is what makes #72 and #73 cheap to do properly. **The window closes when
0.8.0 is tagged.** Doing these three before the release costs a fraction of
what doing them after would.

Suggested order: **#71 → #72 → #73**. The ergonomic layer in #73 is only worth
building once it has provenance (#72) and offsets (#71) to hand out.

## #71 — `ParsedPacket.payload_offset`

Smallest and lowest-risk; no design fork.

### Verified

The naive arithmetic really does break, silently, on exactly the case #66
introduced. A 60-byte padded frame carrying a 4-byte payload:

```
frame=60  payload=4
naive offset  = 56    # len(frame) - len(payload)
true offset   = 42    # 14 (eth) + 20 (ip) + 8 (udp)
```

The naive value is 14 bytes past the truth and lands on padding zeros
(`00000000` instead of `deadbeef`), returning wrong bytes with no error.
`frame.find(payload)` happens to give 42 here, but it is guesswork.

### Implementation

The same threading exercise as `decode_app` in #61, through the same call
sites, so the shape is known:

- Add `payload_offset: int | None = None` to `ParsedPacket`
  (`src/packeteer/parse/core.py`, near the existing `payload` field).
- Thread an integer `base` through `_parse_pppoe_and_mpls`,
  `_parse_ip_protocol`, and `_try_parse_vxlan` / `_try_parse_geneve` /
  `_try_parse_gtpu`.
- Inside `_parse_ip_protocol` no end-trimming happens, so relative offsets by
  subtraction are safe *there*. The #66 padding trim sits **outside** it —
  which is exactly why the offset must be tracked rather than derived from
  lengths at the end.
- Forward `base` into all seven recursive `parse_packet` calls (pseudowire,
  VXLAN, GENEVE, GTP-U, IP-in-IP, GRE, EtherIP) so a nested `payload_offset`
  is relative to the **outer** frame, per the issue's preferred reading. One
  addition then works at any tunnel depth.
- `payload_offset` stays `None` when `payload` is empty — including when
  `decode_app=True` consumed it into `dns` / `dhcp` / `http`.

### Tests

Padded frame (the case the arithmetic breaks on), unpadded frame, tunnelled
packet at two depths, snaplen-truncated capture, `decode_app=False` (offset
present) vs `True` (payload empty → `None`), and a property check across
`testcases/*.pcap` that `frame[off:off + len(payload)] == payload` for every
payload-bearing packet.

### Scope — decided

The issue floats per-layer offsets (`ip_offset`, `transport_offset`) as a
fuller version. Since `base` gets threaded anyway they would cost little *now*
— but they are API surface to support forever, and `payload_offset` alone
closes the stated gap.

**Decided (Adam, 2026-08-11): ship `payload_offset` only.** The fuller version
is filed as
[#74](https://github.com/adamkjonsson/packeteer/issues/74) (unmilestoned) for
a later release. The threading work here is the expensive part and it is
reusable, so adding the rest later is cheap in implementation; the cost is API
surface, better spent when a real use case asks for it.

## #72 — Provenance for reassembled datagrams

### Verified

The issue's figures reproduce exactly on `testcases/fragmentation.pcap`:
287 records in → 148 passthrough + 59 reassembled, 0 incomplete, from 139
input fragments.

### Implementation

Adopt the issue's token design, and take the breaking change outright rather
than adding `feed_tracked()` alongside — `Defragmenter` is unreleased, so
there is nothing to stay compatible with:

```python
@dataclass
class AssembledFrame:
    frame: bytes
    tokens: list[Any]      # contributing fragments' tokens, in arrival order
    fragment_count: int    # 1 for a passthrough

def feed(self, frame: bytes, ts: float = 0.0, token: Any = None) -> list[AssembledFrame]
```

- `defragment()` / `defragment_ipv4` / `defragment_ipv6` keep returning bare
  frames — that wrapper exists precisely for callers who said they only want
  bytes. They unwrap `.frame` internally.
- `fragment_count == 1` becomes the documented way to spot a passthrough,
  replacing the `result[0] is frame` identity check that the issue rightly
  calls out as unpromised behaviour.
- `IncompleteDatagram` should carry `tokens` too, for symmetry — a caller
  reporting what was lost wants to name those packets just as much.

### Naming

`AssembledFrame` rather than the issue's `ReassembledFrame`: most instances
are passthroughs that were never fragmented. Minor, but it is the name callers
will type.

### Tests

Tokens preserved in arrival order; out-of-order fragments yield tokens in
**arrival** rather than offset order (worth pinning explicitly — it is a real
choice); `fragment_count` of 1 vs N; tokens on incomplete datagrams; and a run
over `testcases/fragmentation.pcap` asserting all 139 input fragments are
accounted for across the 59 reassembled outputs.

## #73 — Ergonomics: making reassembly the default

The open-ended one. The issue says reassembly "ideally should be hidden from
users", with an option to turn it off.

### The conflict to settle first

**Automatic defragmentation and byte-exact round-tripping are mutually
exclusive.**

`parse` → `build` currently reproduces fragmented captures byte-for-byte,
including later fragments — that was the last thing fixed in #65. If
`packeteer parse` reassembles by default, a fragmented capture parses to
*whole datagrams*, and rebuilding emits unfragmented packets. The capture no
longer round-trips.

### Recommended split, by what each entry point is *for*

| Entry point | Reassembly | Why |
|---|---|---|
| **New `iter_packets(path=…)`** | **on** by default | Analysis front door — the ergonomic answer to "I want packets, not pieces" |
| `parse_pcap_file` / `packeteer parse` | **off**, opt-in `--defragment` | The spec path is the round-trip path; default-on silently breaks it |
| `open_pcap` / `read_pcap` | off, no option | These report the file's records; reassembly breaks the 1:1 with records and byte offsets |
| `pcap_info` / `file-info` | off | It is a diagnostic — hiding fragmentation is the opposite of useful. Better: *report* fragment counts |
| `parse_packet` / `parse_pcap_packet` | n/a | Single packet, stateless — reassembly impossible by construction |

### The new front door

Where "hidden from users" actually gets delivered:

```python
from packeteer.parse import iter_packets

for pkt in iter_packets(path="capture.pcap"):     # reassembled, decoded, parsed
    pkt.payload            # whole datagram payload
    pkt.payload_offset     # from #71
    pkt.source_records     # from #72 — which file records it came from
```

It composes `open_pcap` → `Defragmenter` → `parse_packet` internally, which is
exactly the three-step incantation every consumer currently writes by hand.
It is also where #71 and #72 pay off: the caller gets whole packets **and**
keeps provenance, which is otherwise the thing lost by hiding the fragments.

### Decided

**Decided (Adam, 2026-08-11): defragmentation in `packeteer parse` is
opt-in**, via a `--defragment` flag, and `parse_pcap_file(defragment=False)`
by default. The byte-exact round trip is preserved, and no `Breaking:` note is
needed for the parse path.

Reassembly is on by default only in the new `iter_packets` front door, where
the caller has asked for packets rather than records.
