Two strands that share no code.

**Two-way TCP**: #198, with #218 and #219. A generated TCP stream sends all its
data from the client, so DNS over TCP replayed from a capture would send its
responses from the wrong side. 0.18.0 refuses that input rather than send it
wrong, naming #198:

```console
$ packeteer stream --protocol tcp --payload dns --protocol-messages dns.json \
    --server-port 53 --client-ip 10.0.0.2 --server-ip 10.0.0.1 --packets 6 --seed 5 --json d.json
error: message 1 travels server to client, and a payload_fn sends every message
from the client.  Over UDP, protocol_conversation and UDPStreamConfig.messages send
it the right way (stream --protocol udp does); over TCP that is not supported yet:
https://github.com/adamkjonsson/packeteer/issues/198
```

0.19.0's plan sized #198 as "several days", because loss, retransmission,
corruption and the re-acknowledgement all have to be right both ways.
**Most of that is already done.** `--payload http` (#169) sends server data
through the same impairment passes, and they were written for both
directions: `_reacknowledge`, `apply_loss_recovery`, `_restamped`,
`_ack_positions` and duplication all work by `pkt.direction`. The emit
loop's in-order acknowledgement rule (`seq_before == dst.ack`) is symmetric.
What is left is the data loop itself, plus the two passes that are **not**
direction-aware. Both already give wrong output on `--payload http`:

<a name="bug-a"></a>
- **#218: a server RST carries a stale sequence number.** `_apply_server_rst`
  takes the RST's `seq` from the server's ACK of the split segment. Any
  server data sent after that ACK and before the RST is not counted.
  Reproduced on 0.19.0 with `generate_http_stream(…, seed=0, requests=3)`
  and `server_rst_probability=1.0`:

  ```
  s2c ACK[0]   seq=3427104802 len=0
  s2c 200 OK   seq=3427104802 len=224
  s2c RST      seq=3427104802          # should be 3427105026
  ```

  All 200 seeds tried give a stale RST. A receiver that follows RFC 5961 §3
  ignores an RST whose sequence number is not exactly `RCV.NXT`, so the
  capture shows a reset the client would never act on. Plain TCP streams
  are not affected today, because their server sends no data. #198 changes
  that.

<a name="bug-b"></a>
- **#219: a stray segment can be forged from the wrong side.** `_apply_stray`
  copies a random data segment's `seq`/`ack`, but always builds the forgery
  client → server. When the segment it copies is server data, the forgery
  carries the server's sequence numbers from the client's address: 93 of
  200 seeded HTTP streams with one stray. That isn't a hijack attempt that
  could happen on a real network, which is what `--stray-packets` is
  supposed to model.

# Part 1 — #213, the checksums in C

## The fix

- **`ones_complement_checksum`** sums with `array("H", data)` (byteswapped
  on a little-endian host) and `sum()`, then folds the carry, as the issue
  proposes. 0.19.0 measured it at 52.8 → 5.3 µs for 1,500 B, and the whole
  TCP rebuild at 55.0 → 5.9 µs. The `int.from_bytes(...) % 0xFFFF` form is
  faster still (3.6 µs to verify), but needs a special case to *compute* a
  checksum: a non-zero multiple of 0xFFFF must give 0x0000, not 0xFFFF. It
  is used only if it still measures clearly faster once that case is in.
- **Keep the rebuild.** `_derived_checksum` still rebuilds the header, as
  #68 designed. Verifying in place measured 5.5 µs against the rebuild's
  5.9 µs once the sum is fast, which is not worth changing the design for.
  [The comment on #213](https://github.com/adamkjonsson/packeteer/issues/213#issuecomment-6385565979)
  has the numbers.
- **`crc32c`** only affects SCTP, and is [Q4](#q4).

## Tests

`test_checksum.py` gains an equivalence test against the old loop, copied
into the test as the reference. It covers random inputs of every length from
0 to 70 bytes and a few large ones, odd and even; all-zero; all-0xFF; inputs
whose sum is an exact multiple of 0xFFFF; and RFC 1071's worked example.
Also, a one-off check recorded here rather than kept as a test: `parse` of
every fixture gives byte-identical JSON before and after.

## Changelog

`Changed`: checksum computation is about 10× faster for full-size frames,
which makes `parse` about 40% faster on a capture of full-size TCP segments.
Results are unchanged.

### What #213 corrected

**`int.from_bytes`, not `array`.** With the special case in, it still
measured 1.5× faster than the issue's `array` version at every size:

| | 20 B | 60 B | 1,500 B | 9,000 B |
|---|---|---|---|---|
| 0.19.0 | 0.84 µs | 2.10 µs | 52.3 µs | 317 µs |
| `array` + `sum` | 0.37 µs | 0.50 µs | 5.3 µs | 30.4 µs |
| `int.from_bytes` % 0xFFFF | 0.18 µs | 0.27 µs | 3.4 µs | 19.8 µs |

The buffer as one big-endian integer is congruent to its word sum modulo
0xFFFF, because 2¹⁶ ≡ 1. Two cases need care, and both are in the
function's comments and the tests. An all-zero buffer has a sum of 0 and
a checksum of 0xFFFF. A non-zero multiple of 0xFFFF folds to 0xFFFF
(one's-complement −0), not to 0, so its checksum is 0x0000. It also
removed `checksum.py`'s only use of `struct`.

**The one-off check passed.** `parse` of all 34 fixtures under
`testcases/` and the repository root gives byte-identical JSON on
`d7538d8` and after the change. Each run was checked to import its own
tree. The full suite passes unchanged. End to end:

| | `stream1.pcap` | 34 fixtures |
|---|---|---|
| 0.19.0 | 68.9 ms | 147.4 ms |
| #213 | 39.8 ms | 93.4 ms |

**[Q4](#q4) is settled by its own rule:** slicing-by-8 measured 1.1–1.2×
faster than the byte loop (113 µs against 129 µs for 1,500 B), well short
of 3×, so `crc32c` is unchanged. In pure Python, its eight table lookups
per eight bytes cost about the same as eight lookups one byte at a time.
The changelog says so, and nothing is added.

**Tests:** `test_checksum.py` keeps its four tests and adds:

- RFC 1071's worked sum (0xDDF2);
- the word-by-word reference over 20 random buffers of each length from 0
  to 70;
- frame-sized and 64 KiB buffers;
- nine edge buffers, including both special cases;
- a range check;
- CRC-32c's standard check value (`123456789` → 0xE3069283), which it
  lacked.

The equivalence tests pass on the old code too, as they must: they pin that
nothing changed.

# Part 2 — #214, the printable-payload test in C

`_is_printable_ascii` becomes
`bool(data) and not data.translate(None, _PRINTABLE_ASCII)`. It measured
28.7 → 1.0 µs on 1,400 printable bytes.

**Tests:** equivalence against the generator version, for every single byte
value, the empty input, and random buffers, both printable and with one
non-printable byte at the start, middle and end.

**Changelog:** `Changed`, folded into #213's entry as a second sentence:

### What #214 corrected

the function, and the comment there names #214. Measured on printable
payloads: 1.03 → 0.14 µs at 40 B, 28.8 → 1.03 µs at 1,400 B, and 183 →
5.9 µs at 9,000 B.

**A bullet of its own, not a sentence.** The plan folded this into #213's
entry as a second sentence. It is a second bullet under the same
`Changed` instead, since it is a different function with a different
issue number.

**The one-off check passed, in both modes.** `parse` of all 34 fixtures
gives byte-identical JSON on `030830d` and after, both by default and with
`decode_app=False`, where HTTP and DNS payloads reach this function instead
of their decoders. The fixtures hold few all-text payloads (`stream1.pcap`
has one with `decode_app=False`), so the unit tests carry the weight.

**Tests** are two more in `test_parser_to_config.py`'s

- every byte value on its own is text exactly when it is 0x20–0x7E;

The empty payload was already pinned. Both tests pass on the old code too,

# Part 6 — #218, the RST at the server's real sequence number

## The fix

The RST's `seq` is the server's `SND.NXT` at the moment it is sent. Its
`ack` is the server's `RCV.NXT`. That is: the last server segment sent
before `rst_send_usec` that has survived the cut, plus its sequence length;
and the acknowledgement that segment, or a later server ACK before the RST,
carried. This means walking the server's packets up to `rst_send_usec`,
not taking the reply to the split segment. Use the SYN-ACK when nothing
else is left, as today.

The "data still in flight" rule is unchanged: client data the client sends
before it learns of the RST is kept, and server data after the RST is
dropped.

## Tests

An invariant test over `--payload http --server-rst 1.0` and plain TCP, with
many seeds: the RST's `seq` equals the server's next sequence number, and
its `ack` equals the last in-order client byte the server received. The 0.19.0
example above, with seed 0 and three requests, is pinned by value.

## Changelog

`Fixed`: a server RST after the server has sent data carries the server's
current sequence number, so a receiver would accept it. For the same seed,
the output of `--payload http --server-rst` changes in the RST only.

### What #218 corrected

**The RST takes the server's state from the packets, as planned.**
`SND.NXT` is a new helper, `_snd_nxt`: the furthest end of any server
segment, in serial arithmetic. Every server segment left was sent by the
RST's moment, so no time bound is needed. `RCV.NXT` is the existing
`_rcv_nxt_at`, the same walk a retransmission uses, taken up to just
*before* the reset. The client segment the RST is timed at is still in
flight, and the server has not received it. The SYN-ACK fallback is now
only for `RCV.NXT` when no client SYN is present, which never happens.

**One limit, documented in the code rather than worked around:** a server
segment lost on the wire with nothing from the server after it is not in
the capture, so `SND.NXT` cannot count it. The RST then numbers from the end
of what the client can have received, which an RFC 5961 receiver accepts.

**Plain TCP was affected too, after a loss, which the plan did not expect.**
It said plain streams were untouched, because their server sends no data.
They were untouched only without loss. The old code took the RST's numbers
from the split segment's ACK. That ACK was found by sequence number, and
after a loss it went wrong in two ways:

- **No ACK found** (the split segment's ACK lost, or a duplicate ACK naming
  an earlier byte): the RST fell back to the SYN-ACK *as is*. Its `seq` was
  the server's ISN, one short of anything the server could send, and its
  `ack` was the client's ISN + 1, as if nothing had arrived.
- **The wrong ACK found**: a later duplicate ACK naming the same byte was
  taken for the split segment's ACK. Its time became the cut, so ACKs after
  the reset survived: server ACKs after its own RST, and teardown ACKs
  whose FIN had been removed. 40 of 1,800 old streams had teardown ACKs and
  no FIN. Both emit paths send a segment's ACK before any further data, so
  an ACK with data emitted in between is now refused as the split segment's
  ACK, and the cut falls at the split segment.

Together, the old RST was wrong in 31 of 60 seeded plain streams with
loss, and 33 of 60 with recovery.

**A wider filter was tried first and reverted.** Dropping every ACK each
side sends after the reset also removed, under `gap_jitter`, server ACKs
*sent* before the RST and only *captured* after it. Those are real. The
fault was the pairing, not the filter.

**What changed, against `9bab73e`,** over 300 seeds each:

| | Changed | Outside the RST |
|---|---|---|
| plain | 0 | 0 |
| plain, `rst_propagation_delay` + `gap_jitter` | 0 | 0 |
| plain, loss | 190 | 7 |
| plain, loss + `retransmit_lost` | 193 | 31 |
| `--payload http` | 300 | 0 |
| `--payload http`, loss + `retransmit_lost` | 281 | 19 |

Every packet removed outside the RST is a bare ACK. In all 57 streams with
removals, every removed ACK comes after every ACK kept, so the cut is clean
in time. Nothing was added.

**Tests** are `test_server_rst_sequence.py`. Over 60 seeds of plain TCP
(clean, loss, loss + recovery, delay + jitter) and of HTTP (clean, loss +
recovery), it checks:

- the RST's `(seq, ack)` against the server's state, worked out from the
  packets as a reader of the capture would;
- the RST's bytes on the wire say the same;
- the server sends nothing after its RST, without jitter;
- the issue's example, pinned by value (`seq` 3427105026, after the 224-byte
  response);
- plain seed 0's lost-ACK case, which numbered from the ISN.

On the old code, 190 subtests fail across every lossy and HTTP case, and
clean plain TCP passes, as it should.

# Part 8 — #198, a TCP stream sends each message from its own side

## The design

It mirrors #195:

- **`TCPStreamConfig.messages: Sequence[AppMessage] | None = None`**, the
  name and type `UDPStreamConfig.messages` has. When it is set, data
  message `i` is `messages[i % len(messages)]`. It cycles, as every payload
  does (0.17.0's Q1). Each message is sent from its own side and
  acknowledged by the other:

  ```python
  sender, receiver = (client, server) if msg.direction == "c2s" else (server, client)
  if emit(sender, receiver, flags, chunk, msg.direction, f"DATA[{i}]"):
      emit(receiver, sender, TCP_ACK, b"", other(msg.direction), f"ACK[{i}]")
  ```

  Setting it alongside `payload_fn` is a `ValueError`, and `payload_sizes`
  is ignored, both as on UDP.
- **In `generate_tcp_stream`, not through `render_tcp_session`**
  ([Q1](#q1)). That is where `psh_probability`, `window`, `gap_jitter`,
  `packet_hooks`, per-side SYN options and stray injection live.
  `TCPSession` has none of these, so going through it would lose them or
  mean porting them.
- **Segmenting** ([Q2](#q2)). Recommended: a message longer than the
  peer's MSS (less 12 bytes when timestamps were negotiated) is split, as a
  real stack and `TCPSession` both split it. PSH goes on its last segment,
  and the labels are `DATA[i] [k/n]`. `num_data_packets` still counts
  messages. DNS over TCP crosses the MSS as soon as DNSSEC is involved, so
  this is not an edge case.
- **PSH**: with `messages` set, `psh_probability` is ignored, and PSH marks
  the end of each message. The docstring says so.
- **No `messages`, no change.** The data loop, every RNG draw and every
  label stay the same, so a seeded plain TCP stream is byte-identical to
  0.19.0's. Pinned by hash, checked against a worktree at `7fb19b5`.

## The CLI and `app`

- `stream --protocol tcp --protocol-messages` uses
  `app.protocol_conversation` and passes `messages`, as UDP has since #195.
  The refusal of an `s2c` element on TCP goes, along with
  `_TCP_DIRECTIONS_ISSUE` in `app/__init__.py` and the sentence in
  `__main__.py`'s help.
- **`protocol_payload_fn` keeps refusing a reply.** A `payload_fn` still
  sends from the client only, over any transport. Its message names
  `TCPStreamConfig.messages` and `UDPStreamConfig.messages` instead of
  #198.
- `--sessions N` needs nothing, because `generate_session_mix` uses
  `dataclasses.replace` and `messages` rides along. A test confirms it, as
  #194's did.

## The impairment audit

These are the passes, and each one's state once #218 and #219 are fixed. Each row
gets a test over a two-way stream:

| Pass | Two-way already? | Test |
|---|---|---|
| Loss (in `emit`) | yes: the in-order rule is symmetric | a lost server segment draws duplicate ACKs from the client |
| `apply_loss_recovery` | yes (`ack_dir`) | a lost server segment is retransmitted by the server and acknowledged by the client |
| `_apply_retransmission` | yes (`_restamped` by direction) | a spurious server retransmission has server addresses and a fresh TSval |
| `_apply_corruption` + `_reacknowledge` | yes | a corrupted server segment is not acknowledged; the client's later ACKs repeat |
| `_apply_server_rst` | after #218 | the RST is at the server's `SND.NXT` mid-response |
| `_apply_stray` | after #219 | a stray copying server data comes from the server |
| `_apply_duplication` | yes | unchanged |

**The invariant checker.** One test helper walks a finished stream and
checks, for each direction, that:

- every in-order segment starts at the previous one's end;
- every ACK acknowledges no more than the peer has delivered, and exactly
  the last in-order byte;
- TSecr echoes the latest in-order TSval.

It runs over every impairment above, alone and combined, over many seeds.
It is #115's method: impaired streams, with messages that can be told
apart, checked by machine rather than by eye.

## Docs

## Changelog

`Added`: `TCPStreamConfig.messages`. `Changed`: `stream --protocol tcp

### What #198 corrected

**The design held: `messages` in `generate_tcp_stream`'s data loop**

2026-10-24 as recommended. Each message goes from its own side, and the

# Part 9 — #221, a bare section's `direction` is refused ([Q9](#q9))

## The bug

`_directed_sections_in` sends a bare section `c2s` and hands it to the
protocol as it is. The protocol's `from_spec` reads only its own keys, and
`check_section` only refuses a section in which *nothing* is recognised. So
`{"raw": …, "direction": "s2c"}` builds a message, and the `direction` is
read by nothing. This is #137's failure mode, a key accepted in silence,
on the one key that decides which way a message goes.

## The fix

**Refuse it**, as the issue proposes ([Q9](#q9)). A bare section with a
`"direction"` key is refused, naming its index and the shape to write:

```
message 1 has "direction" but is a bare section; write {"dns": {...}, "direction": "s2c"}
```

- **The wrapped form is the escape for a protocol with its own `direction`
  field.** Inside `{"proto": {"direction": …}}` the inner key is the
  protocol's field and the outer one the message's, so nothing becomes
  unwritable. No shipped or vendored protocol has such a field: DNS, DHCP
  and HTTP's section keys don't include it, and in `src/tests/kober/` the
  word appears only in doc strings.
- **The same refusal with `directed=False`** (`protocol_messages`, which
  `--payload http` uses). A direction there is taken from the message, and
  a `direction` key would still be read by nothing.
- **A whole packet with a top-level `direction` is refused too.** Found
  checking this part's own claim, which first said it was refused already.
  It is not: `{"network": …, "transport": …, "dns": …, "direction": "s2c"}`
  is accepted, and the message goes the way its ports say, `c2s` here. A
  packet's direction is `packet_metadata.direction`, and the refusal says
  so. This is the same fault in the third input shape, so it is fixed
  here rather than filed.

## Tests

The issue's input on TCP and UDP, through the CLI and through
`protocol_conversation`: refused, naming message 1 and the wrapped shape.
Also:

- the same with `protocol_messages`;
- a wrapped section with `direction` is still accepted;
- a bare section without one is still `c2s`;
- a wrapped section of a protocol with a `direction` field keeps that field
  inside it. This uses a test protocol registered for the purpose;
- a whole packet with a top-level `direction` is refused, naming
  `packet_metadata.direction`, and one with `packet_metadata.direction`

## Changelog

Wrap it: `{"dns": {...}, "direction": "s2c"}`. A whole packet with a

# Part 10 — #220, a message `parse` could not decode is refused, not skipped ([Q8](#q8))

## The bug

`parse` decodes an application message per packet. A DNS-over-TCP message
split over segments is not decodable from any one of them, so each segment
is written with a `payload` section and no `dns` one. `_directed_sections_in`
skips any packet without the protocol's section, which is right for an
ACK or the handshake, and wrong here: the skipped packets *are* a message.
The list then cycles to fill `--packets`, so the loss isn't even visible
as a shorter stream.

Kober's point about why it matters is the plan's too. TCP is used for DNS
at all because a message is too big for one datagram (truncation fallback,
zone transfers, DNSSEC answers), so these are the messages that vanish.

## The fix

**Refuse, naming the packets** ([Q8](#q8)), which is the issue's first
option:

- **What is refused:** a packet with a `payload` section and no section
  for `--payload`, on the protocol's flow, meaning one of its ends is on
  one of the protocol's `ports`. The message names the packet's index, its
  direction and its byte count, and says why: `parse` decodes a message
  only when one packet holds all of it.
- **What is still skipped:** a packet with no payload (ACK, handshake,
  teardown), and a payload on another flow. A capture holding other
  traffic, such as port 443 beside port 53, replays its DNS as before.
- **Not reassembly, in this release.** The issue's second option, decoding
  a DNS-over-TCP message in `parse` by its 2-byte length prefix, changes
  what `parse` writes for every such capture. It also meets the question
  #114 settled for TCP streams: a spec is per packet, so that it rebuilds
  byte for byte. That is its own design, and a follow-up issue if
  zipline-kober wants it ([Q8](#q8)).

The same rule holds on UDP: a payload-only packet on port 53 is a datagram
`parse` could not decode as DNS, and dropping it in silence is the same
fault.

## Tests

- **The issue's reproduction:** generate with a 3,234-byte response,
  `parse`, replay. Refused, naming the three packets and 3,234 bytes, with
  exit status 1.
- A parsed capture whose messages all fit replays as before.
- A capture with a payload on an unrelated port still replays its DNS, and
  the unrelated payload is skipped.
- An undecodable single-segment payload on port 53, over UDP and over TCP,
  is refused.
- ACKs and the handshake are still skipped.
- `protocol_conversation`, `protocol_payload_fn` and `protocol_messages`
  all refuse, since they share the reader.

## Changelog

`Changed`: **Breaking:** a packet in a `--protocol-messages` packet spec
that carries a payload but no section for the protocol is refused, when
it is on the protocol's flow, where it used to be skipped and the list
cycled. `parse` writes such packets for a message split over TCP segments,
which it cannot decode on its own. Instead, write the message as a wrapped
section,
for DNS `{"dns": {"raw": …}, "direction": "s2c"}`, with the message's
bytes put back together from the packets.

### What #220 corrected

**One error names every packet.** The plan said the refusal names "the
packet". `_directed_sections_in` collects them all and refuses after the
walk, so a response split over three segments is one error. It gives each
packet's index, direction and bytes, and the total. The total for the
issue's response is 3,236 bytes: the 3,234-byte message plus DNS over
TCP's 2-byte length prefix, which is what was on the wire. A packet's flow
is decided by `_undecoded_bytes`: either end on one of the protocol's
`ports`. The bytes come from the payload section's hex, or its UTF-8 text.

**A known limit, measured rather than guessed.** A corrupted copy that
`parse` cannot decode, from a capture made with `--payload-corruption`,
would be refused, even though its clean retransmission carries the whole
message. Flipping a DNS message's last byte rarely makes it undecodable.
Over 15 seeds at `--payload-corruption 0.5`, on TCP and on UDP, and 15 at
`--packet-loss 0.3 --retransmit-lost` on TCP, `parse` wrote no
payload-only packet on port 53, and every replay ran. Recorded, not fixed:
telling a corrupted copy from an undecodable message needs the same
per-flow reasoning as reassembly ([Q8](#q8)).

**Tests:**

- In `test_tcp_directions.py`, `TestAMessageParseCouldNotDecodeIsRefused`:
  - the issue's reproduction at the CLI: generated, parsed and replayed.
    It exits 1, names three packets and 3,236 bytes, and writes no output
    file;
  - all three readers refuse;
  - an undecodable datagram on port 53 over UDP is refused;
  - an ACK and a TLS payload on port 443 are still skipped.
- The existing parse-then-replay tests for UDP (#195) and TCP (#198) still
  pass, so a capture whose messages fit replays as before.

On the old code the four refusal tests fail and the "skipped" test passes.

**Docs:** `stream.md`, after the parsed-capture example; the reader's
docstring.

### What zipline-kober's review of `.dev3` found

**#220 and #221 confirmed**, on 2026-10-25, with all three things it was
asked to check:

- the #220 reproduction exits 1 and names the three segments, and the

- `bare.json` is refused on both transports;
- the whole-packet `direction` is refused.

**Two minor bugs, both in #220's error message**, filed as #222 and #223.

# Part 11 — #223, the error says why for the transport it is on

## The bug

`_refuse_undecoded` gives one cause on every transport: "a message split
over TCP segments". On UDP that cause cannot happen. A payload with no
section there is a datagram `parse` could not decode.

## The fix

The cause is worded by transport, which means `_directed_sections_in`
needs it. Its three callers, `protocol_conversation`, `protocol_payload_fn`
and `protocol_messages`, all have `transport` already, so it gains a
keyword argument and passes it on:

- **UDP:** `parse` writes a payload without a section when it could not
  decode it as a message: malformed, truncated, or not `<protocol>`.
- **TCP:** both causes. It was split over segments, which `parse` does not
  join, or it does not decode.

The fix is the same either way, a wrapped section, so that sentence stays.

## Tests

- Kober's UDP reproduction: a truncated 10-byte response is refused, the
  error names neither TCP nor segments, and it says the datagram did not
  decode.
- The TCP message names both causes.
- The `test_undecodable_on_udp_too` test, which asserted only the index,
  also asserts the UDP wording.

## Changelog

Folded into #220's `Changed` entry, since both are unreleased: the error
gives the cause for the transport.

### What #223 corrected

**Nothing in the design.** `_directed_sections_in` takes `transport` as a
required keyword, since it is private and both its call sites have it.
`protocol_payload_fn` reaches it through `protocol_conversation`. A new
`_undecoded_causes` gives the cause.

- **UDP:** *could not decode it as a dns message: malformed, truncated, or
  not dns at all*.
- **TCP:** *… on its own: split over TCP segments, which parse does not
  join, or malformed, truncated, or not dns at all*.

Any other transport gets UDP's wording, since only TCP splits a message.

**Kober's UDP reproduction, recreated** with a query, a response and the
response's first 10 bytes, exits 1 naming index 2 (`s2c`, 10 bytes). The
error mentions neither TCP nor segments.

**Tests**, in `TestAMessageParseCouldNotDecodeIsRefused`:

- `test_kobers_udp_reproduction` at the CLI;
- `test_undecodable_on_udp_too` now asserts the UDP wording, and that
  neither "TCP" nor "segment" appears;
- the #220 reproduction asserts the TCP wording.

All three fail on the old code.

**Docs:** `stream.md`'s paragraph on refused payloads gives both causes.

# Part 12 — #222, the error gives the message's size, not the payload's ([Q10](#q10))

## The bug

The error reports the payload's bytes as captured. On TCP, for a protocol
that frames its messages, that count includes the frame: DNS's 2-byte
length field. The error then suggests a wrapped section, and `raw` is the
message *without* the frame, since the builder adds it. So the count it
gives is the one that does not work. `format.md` says the builder adds the
field, but nothing in the error points there.

## The fix

**Say what the bytes add up to** ([Q10](#q10)), the issue's first option:

- **When the named packets in one direction decode together as one
  message,** `proto.decode` of their joined payloads over the transport,
  the error says so and gives both sizes. For example: *3 packets, 3,236
  bytes of payload: together one 3,234-byte dns message after its framing*.
  The message's own size is its encoding without transport framing: for
  a protocol carried over UDP as well, `len(proto.encode(message, "udp"))`,
  and the joined payload's size for one that runs over TCP only, which has
  no separate form. No DNS-specific code: checked on kober's response,
  `dns.decode(joined, "tcp")` gives the message, and encoding it for UDP
  gives 3,234 bytes against TCP's 3,236.
- **The suggestion says what `raw` holds**: the message without any length
  field the transport adds, since the builder adds it. Or write the
  message's fields.
- **When they do not decode together,** the sizes stay as now, and #223's
  wording applies.

**Not done:**

- **Printing the section** (the issue's option 2). For this response the
  decoded section is 20,719 characters of JSON, too much for an error
  message.
- **Refusing a `raw` whose first two bytes equal its length less two**
  (the issue's heuristic). A real DNS message whose ID happens to match its
  length would be refused, and the error above already prevents the
  mistake.

## Tests

- Kober's reproduction: the error gives 3,236 bytes of payload and one
  3,234-byte message, and says `raw` takes the message without the length
  field.
- Following the error as written, `raw` from the joined payloads less the
  2 bytes it names, replays byte-identical to the original response.
- Segments that do not decode together, such as a truncated response's
  first segment alone, keep the payload sizes and name no message size.
- UDP: one undecodable datagram has no frame, and the error says nothing
  of one.

## Changelog

Folded into #220's entry: on TCP the error gives the message's size beside
the payload's, and says `raw` excludes the length field the builder adds.

### What #222 corrected

**"One whole message" needed a stricter test than decoding.** DNS's
`decode` reads the length field and ignores whatever follows, so a run
holding two messages, or one with bytes after it, also decodes. A run is
sized only when re-encoding the decoded message for TCP gives exactly the
joined length. A partial run fails to decode: *DNS/TCP length prefix says
3234 bytes but only 2894 available*.

**The sizes come from the protocol, not from DNS knowledge.**
`_whole_messages` groups the refused packets into runs going one way and
joins each. A run that decodes as exactly one message is named with its
size: `proto.encode(message, "udp")` for a protocol carried over UDP too,
less than its TCP encoding by the length field. The note reads:

```
The packets at index 9, 11, 13 (s2c) are together one 3234-byte dns message, after the 2-byte
length field TCP adds; in a wrapped section, 'raw' is the message without that field, which the
builder adds back
```

A protocol that runs over TCP only is sized without a framing remark,
since it has no unframed form to compare against. Nothing is said on UDP,
or of a run that is not one message.

**`_undecoded_bytes` became `_undecoded_payload`**, returning the bytes
rather than their count, since the runs are joined from them. Hex that does
not parse stands as that many zero bytes, so it is still counted and
refused, and never decodes.

**Following the error now works.** Kober's reproduction, with `raw` set to
the joined payloads less the 2 bytes the error names, replays exit 0. The
server's byte stream is identical to the original capture's: 3,351 bytes
each.

**Tests**, in `TestAMessageParseCouldNotDecodeIsRefused`:

- the #220 reproduction asserts the note, then follows it to a byte-identical
  server stream (`_server_stream`);
- no size for part of a message, for two messages in one run, or on UDP.

On the old code the two tests expecting the note fail. The three
"no note" tests pass there too, as they must, since the old error never
gave one.

**Docs:** `stream.md` says what `raw` holds over TCP, and why the error
gives two sizes.

### What zipline-kober's review of `.dev4` found

**#222 and #223 confirmed**, on 2026-10-25, with what it was asked to check:

- the size note is given on #220's reproduction;
- following it replays the original server stream exactly;
- the UDP wording mentions neither TCP nor segments.

**One new bug**, filed as #224, in both of them: the transport they word the
error by is the **replay's** `--protocol`, not the capture's. Reproduced
here on `9473ae7`:

- `A.parsed.json`, from the TCP capture, replayed with `--protocol udp`:
  the error gives the UDP cause ("malformed, truncated, or not dns") and no
  size note, though the response is one well-formed message split over
  three TCP segments. Joining the payloads into `raw` as counted then
  sends a 3,236-byte datagram that does not decode as DNS. That is #222's
  mistake, over UDP this time.
- `U.parsed.json`, from a UDP capture, replayed with `--protocol tcp`: the

Every packet `parse` writes says how it was captured, in
`network.protocol` (`tcp` here, with `seq` and `ack` in `transport`).

# Part 13 — #224, the error goes by how each packet was captured

## The bug

`_refuse_undecoded` words the cause, and `_whole_messages` decides whether
to look for one, by the `transport` the replay will use. Whether a payload
can be part of a split message, and whether it starts with a length field,
depends on how it was **captured**. Replaying a capture over the other
transport is a natural use of a parse document, such as a UDP variant of a
DNS-over-TCP exchange, and it is exactly the case where the length field
has to come off.

## The fix

As the issue suggests:

- **Each undecoded packet records its own capture transport:**
  `network.protocol` when it is `tcp` or `udp`. For a packet that does not
  say, such as a hand-written spec, it falls back to the replay's.
- **The cause** is TCP's (split, or does not decode) when any named packet
  was captured over TCP. It is UDP's (does not decode) when all were
  captured over UDP.
- **Runs** are grouped by direction and capture transport. The search for a
  whole message runs on a TCP-captured run, whatever the replay transport,
  with `proto.decode(joined, "tcp")` as now.
- **The note's last clause** goes by the replay's transport, since that is
  what the builder does with `raw`:
  - over TCP, the builder adds the field back, as now;
  - over UDP, the note says no length field is sent. `raw` is the message
    without that field either way.

## Tests

- **Kober's case:** `A.parsed.json` replayed over UDP gives the TCP cause and
  the size note, with the UDP clause. Following it, `raw` without the
  2 bytes, the response decodes in the replay, and with the 2 bytes it
  does not, as the issue's table shows.
- **The reverse:** `U.parsed.json` replayed over TCP gives the UDP cause
  only.
- **Same transport:** both replays still give what `.dev4` gave, so the
  existing #220, #222 and #223 tests pass unchanged.
- **No `network.protocol`:** a packet without it takes the replay's
  transport.

## Changelog

Folded into #220's entry: the cause and the size note go by how each packet
was captured, not by the replay's transport.
