# Part 1 — #227, a corrupted segment stays corrupt

## The bug

`_apply_corruption` flips the last byte of the datagram, then hands the
list to `_reacknowledge` with the corrupted indices as `not_arrived`.
`_reacknowledge` rewrites the ACKs of every packet that travels *against* a
direction that lost something. When both directions lost a segment, a
corrupted segment of one direction is among the packets whose ACK gets
rewritten. `_reacked` then rebuilds that segment through `_build_packet`
from its already-flipped payload, which gives it a fresh, **valid**
checksum.

Reproduced on `main` (`5d0f46b`) with the issue's script: `c2s CORRUPT[0]
BAD`, `s2c CORRUPT[1] ok`, `s2c CORRUPT[3] ok`. Over 200 seeds of the
issue's two-way conversation, **296 of 617** `CORRUPT` segments carry a
valid checksum.

## The fix

**Flip the byte after the re-acknowledgement, not before.** The loop in
`_apply_corruption` gives the copy only its `CORRUPT[…]` label. After
`_reacknowledge` returns, each index in `corrupted` gets `_corrupted(…)`
applied to whatever frame is now at that position, rebuilt or not.
`_reacknowledge` keeps list order, so the indices still hold.

This is the issue's second suggestion. The first was to re-apply the
corruption inside `_reacked` for a packet in `not_arrived`. That would make
the receiver model know about the damage, which is not its job. Done this
way, nothing outside `_apply_corruption` changes. The ACK rewrite on the
damaged segment is still right: the sender stamped that ACK before the
segment was damaged in flight.

The docstrings of `_apply_corruption`, and the comment above
`_reacknowledge` that says a corrupted copy "fails its checksum on arrival",
are correct once this is fixed. One sentence in `_apply_corruption` says
why the flip comes last.

**Prototyped and measured** against `5d0f46b`, over 200 seeds each, with
`payload_corruption_probability=0.2`:

| | Streams changed | Valid-checksum `CORRUPT` after |
|---|---|---|
| one-way (generated payload) | 0 | 0 / 488 |
| one-way, loss + `retransmit_lost` | 0 | 0 / 483 |
| two-way (`messages`) | 109 | 0 / 617 |
| two-way, loss + `retransmit_lost` | 99 | 0 / 599 |

In every changed stream, only `CORRUPT` frames' bytes differ. Labels,
timestamps, `seq` and `ack` are identical, and so are the RNG draws, so
nothing after the pass moves.

## Tests

In `test_receiver_acknowledgements.py`, beside
`TestACorruptedSegmentIsLostToTheReceiver`:

- Over 60 seeds of two-way `messages`, with and without loss + recovery,
  and on `--payload http`: every `CORRUPT[…]` packet fails its transport
  checksum. Check it with `parse_packet`'s derived checksum status, so
  the test reads the capture the way a consumer does, not with a
  hand-rolled sum.
- The issue's seed-3 example, pinned: all three `CORRUPT` segments are
  bad.
- A seeded one-way stream with corruption, pinned by SHA-256 computed on
  `5d0f46b` before the change.

On the old code the first two fail and the pin passes.

## Changelog

`Fixed`: with data in both directions (`TCPStreamConfig.messages`,
`--protocol-messages`, `--payload http`), a corrupted segment whose
acknowledgement was rewritten after a corruption in the other direction got
a valid checksum again. Every `CORRUPT[…]` segment now fails its checksum.
For the same seed, output changes in those segments' bytes only, and
one-way streams are unchanged.

### What #227 corrected

**Nothing in the design.** `_apply_corruption` labels the copy in its loop
and flips the byte after `_reacknowledge`, as planned. Its docstring says
why the flip comes last.

**Both directions were affected, not only s2c.** On the old code, the new
test's failures include c2s `CORRUPT` segments, for example seed 58's
`CORRUPT[2]`. Whichever direction's acknowledgements get rewritten, a
corrupted segment travelling that way gets rebuilt.

**Tests** are `TestACorruptedSegmentFailsItsChecksum` in
`test_receiver_acknowledgements.py`. A checksum fails when the parser
records `transport.checksum`, the same reading
`test_real_corpus.TestACorruptedSegmentAndItsResend` uses.

- Over 60 seeds of two-way `messages`, with and without loss + recovery,
  every `CORRUPT[…]` fails its checksum, and some streams corrupt both
  directions.
- The HTTP generator: the shared `_http` stream (seed 3) has 6 valid
  `CORRUPT` segments on the old code.
- The issue's seed-3 example, pinned by label and direction.
- A one-way stream with corruption and loss + recovery, pinned by SHA-256
  computed on `5d0f46b`.

On the old code, 180 subtests fail and the pin passes.

# Part 2 — #228, a stray can carry a Timestamps option ([Q1](#q1), [Q2](#q2))

## The design

A new field, **`stray_timestamps: bool = False`**, on `ImpairmentConfig` and
`TCPStreamConfig`. The CLI flag is `--stray-timestamps` and the INI key is
`stray_timestamps`, the same names as the field, as for
`--stray-timing-window`. When it is set, and the connection negotiated
timestamps, each stray gets a Timestamps option built with `_options_for`.
That is the helper `apply_loss_recovery` already uses for a segment a pass
builds itself:

- **TSval** is the impersonated side's clock at the stray's own capture
  time: `clocks[ref.direction].at(stray_usec)`. That is what the real
  sender would have stamped at that moment, so it is never older than
  `TS.Recent` for anything that arrived before it. RFC 7323 §5's PAWS
  accepts it, as well as §3.2. Only content-based defences are left, which
  is the issue's aim.
- **TSecr** is `_tsecr_at(packets, ref.direction, stray_usec)`, the
  impersonated side's echo at that time.
- `timestamps=` is set on the stray's `TCPStreamPacket`, the same as for
  every other packet that carries the option.

`_apply_stray` gains `clocks`, as `_apply_retransmission` and
`_apply_corruption` have. `apply_impairments` already computes them.

**A connection that did not negotiate timestamps** (`--no-tcp-options`, or
a spec without them) gets no option, and the flag does nothing there. A
stray carrying an option the connection never agreed to would itself be
a giveaway, and RFC 7323 §3.2 has a receiver ignore it. The docstring
says so. Refusing the combination would make one config fail on some
flows and pass on others.

**No new randomness.** Adding the option draws nothing. With the flag off,
output is byte-identical to 0.20.0, and the test pins that. With it on,
the same seed gives the same strays at the same times and sizes, now with
the option. The one exception is [Q2](#q2)'s cap, which changes the payload
length drawn, not the number of draws.

**What changes downstream of the pass:** nothing reads stray timestamps.
Duplication copies verbatim, and every other pass runs before the strays.

## Plumbing

- `ImpairmentConfig`: the field and its `Attributes` entry. `any_post_pass`
  is unchanged, because the flag means nothing without
  `stray_packet_count`.
- `TCPStreamConfig`: the field, its docstring, and the forwarding at
  `tcp_stream.py:765`.
- `__main__.py`: the INI key in the spec table (near `stray_timing_window`,
  as `bool`), the argument (`store_true`, `default=None`, like the
  others), and both config builders (`_build_stream_config` and
  `_impairments_from_args`, which `--payload http` uses). Keep it lean:
  forwarding only.
- Protocol handling is the same as for `--stray-timing-window`. It modifies
  `--stray-packets` and impairs nothing by itself, so it is not added to
  `_TCP_ONLY_ANOMALY_FLAGS`. `--stray-packets`, which it needs, is already
  refused on UDP and SCTP. The docs table shows `—` in the UDP column, as
  it does for the timing window.

## Tests

`test_stray_direction.py` is the natural home. It could be renamed
`test_strays.py`, but that is test-only, so do it only if the file reads
better for it.

- Over 60 seeds of plain TCP, two-way `messages`, and `--payload http`, with
  `stray_timestamps=True`: every stray parsed from its bytes has a
  Timestamps option. Its TSval is at least the TSval of every segment from
  that direction captured before it, and at most the TSval of every one
  after it. Its TSecr is a TSval the peer actually sent.
- Under `--no-tcp-options`: strays carry no option, and the stream is
  byte-identical to the same seed without the flag.
- Flag off: a seeded stream with strays, pinned by SHA-256 on `5d0f46b`.
- [Q2](#q2): no stray's frame is larger with the option than the largest
  data segment the configuration allows.
- CLI: `--stray-timestamps` and the INI key reach the config, in
  `test_cli.py`, the same way as `--stray-timing-window`.

## Docs

- `docs/cli/stream.md`: a row in the impairments table.
- `docs/internals/stream-generators.md`: one more sentence in the
  `stray_packet_count` row.
- `docs/guide/generating.md`: one sentence where strays are described. A
  consumer that applies RFC 7323 §3.2 drops a stray without the option,
  and this flag is how to test past that rule.

## Changelog

`Added`: `ImpairmentConfig.stray_timestamps` and
`TCPStreamConfig.stray_timestamps`, `--stray-timestamps`, and the INI key
`stray_timestamps`. On a connection that negotiated timestamps, a stray
then carries a Timestamps option with the impersonated side's clock at the
time it is sent, so a receiver applying RFC 7323 §3.2 or PAWS does not
drop it on that basis. Off by default, and output is unchanged when it is
off.

### What #228 corrected

**[Q2](#q2)'s mechanism was wrong, and its goal is kept.** Lowering
`randint`'s upper bound does not shift the value down by 12. A different
range gives a different value, and because `randint` rejects out-of-range
values, it can take a different number of underlying draws. For the
default range that's about 12 in 2,048 per stray (`getrandbits(11)` either
way). Every later stray, and its time, would then move. So the plan's
claim that the draw count is unchanged was false. Instead, the size is
drawn as before and the option's 12 bytes come off the drawn size, with a
floor of 1. That is stronger than planned: **every stamped stray's frame is
exactly as long as without the flag**, not merely no longer, and no draw
changes on any path.

**The plain path already capped the range.** `generate_tcp_stream` caps
`max_payload` at MSS − 12 when timestamps are negotiated (without
`payload_sizes` or `payload_fn`), and passes that capped range to the
strays. There a stray was never oversized, and with the flag its payload
is at most 1436, not 1448. That's smaller than a full data segment, which
gives nothing away. It is the cost of the uniform rule. Q2's oversize was
real on `--payload http` (the range is taken as given, default 40–1460)
and with `messages` or `payload_fn`. The test pins it there: a 1460-byte
stray on HTTP becomes 1448 with the option, inside a 1500-byte MTU.

**The config template was stale.** `stream.ini.template` still said strays
are sent client → server, which has been wrong since #219. It now has the
new key and the right direction, with a `Documentation` changelog entry.
`test_stream_template` caught the missing key.

**Tests** are a new file, `test_stray_timestamps.py`:

- Over 60 seeds each of plain, two-way `messages` and HTTP: every stray
  parses with a Timestamps option equal to its `timestamps`. Its TSval is
  no older than its side's TSvals before it and no newer than those after
  it, and its TSecr is a TSval the peer sent before it.
- The same frame length, and a payload exactly 12 bytes shorter, as
  without the flag (20 seeds × 3 generators).
- The full-size HTTP case above.
- No new randomness: labels, times, directions, `seq` and `ack` match
  without the flag, and every non-stray frame is byte-identical.
- A bare handshake: the flag changes nothing, and strays carry no
  timestamps.
- Flag off: an HTTP stream with strays, pinned by SHA-256 computed on
  `5d0f46b`. Plain TCP stays pinned by `test_stray_direction`.
- CLI: `--stray-timestamps` reaches plain and `--payload http` streams
  through `_cmd_stream`, and the config key is read.

# Questions

<a name="q1"></a>
## Q1 — a flag, or a mode with a stale variant? **Settled 2026-10-26: a `bool`, as recommended**

The issue offers two TSvals: *near the victim segment's*, or *deliberately
stale*. They test different things. A current TSval gets past §3.2 and
PAWS, so only content-based defences remain. A stale one, older than
`TS.Recent`, is exactly what PAWS drops, so it tests whether the consumer
implements PAWS.

**Recommended: a `bool`, current TSval only.** That is what zpfwire#57
needs, and zpfwire implements no PAWS check, so a stale mode would test
nothing there. If a stale mode is ever wanted, it gets its own field, so
this one never has to change type.

The alternative is `stray_timestamps: str | None` (`None`, `"current"`,
`"stale"`), which costs a CLI choice list and a definition of "stale"
(how stale, and drawn how) that nobody has asked for yet.

<a name="q2"></a>
## Q2 — does the option come out of the stray's payload? **Settled 2026-10-26: yes, the upper bound drops by 12, as recommended**

The option adds 12 bytes (`TCP_TIMESTAMPS_OVERHEAD`). Real data segments
on a timestamped connection are already capped at MSS − 12. With the
default `stray_payload_range` of `(40, 1460)`, a stray could carry 1,460
bytes plus the option, a frame bigger than any real segment on the
connection and over a 1,500-byte MTU. That size alone gives the forgery
away.

**Recommended: when the option is added, lower the range's upper bound by
12** (and keep `min ≤ max`), so the frame is never larger than it would
have been without the option. This only applies when the flag is set, so
nothing existing moves. The `randint` draw count is unchanged. Only the
bound changes, so a seed gives a stray up to 12 bytes shorter.

The alternative: leave the range as given, document it, and accept the
oversized frame. That is simpler, but it leaves a size-based tell in a
feature whose purpose is to remove the cheap tells.
