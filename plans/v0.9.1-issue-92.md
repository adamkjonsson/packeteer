One issue on the v0.9.1 milestone, a patch release. It is a follow-on from
#68, which added `transport.length` and `transport.checksum` to the packet
spec and the clearing pass that keeps them out of it whenever a rebuild could
derive them.

| Issue | Summary |
|-------|---------|
| [#92](https://github.com/adamkjonsson/packeteer/issues/92) | Truncated captures keep `transport.checksum`, so a snaplen reads as corruption |

## The constraint that shapes this release

**The two keys mean something, and the meaning is what broke.** After #68 the
documented reading of a surviving `transport.checksum` is *"this checksum was
wrong on the wire"* — `docs/packet-spec/format.md` says the keys "appear only
where a rebuild could not work the value out for itself", and lists the two
cases. That reading is the whole value of the feature: it is the only way to
tell a corrupt segment from its clean retransmission, and `zpfwire` uses it to
drop segments a receiver would have dropped.

A snaplen-limited capture breaks it on **every packet**, silently. So this is
not "a redundant key appears"; it is a documented invariant that is false in a
common kind of capture.

## #92 — Truncation clears the derivable fields

### Verified

The issue's reproducer is exact, and all four transport/IP-version
combinations are affected. Same 200-byte packet, captured whole and then with
100 bytes cut from the record:

| | intact | truncated |
|---|---|---|
| TCP/IPv4 | `checksum=None` | `checksum=4557` |
| UDP/IPv4 | `checksum=None length=None` | `checksum=24854 length=208` |
| TCP/IPv6 | `checksum=None` | `checksum=10443` |
| UDP/IPv6 | `checksum=None length=None` | `checksum=30740 length=208` |

The cause is as the issue diagnoses:
`_clear_derivable_transport_fields` guards `pkt.ip is None` and never the
truncation half that its own docstring promises.

### The suggested fix does not work

The issue proposes *"skipping the clearing pass when the declared length
exceeds the bytes in hand"*. That leaves the behaviour exactly as it is:

```
current behaviour      -> 4557
with the pass skipped  -> 4557
expected per the issue -> None
```

The parser captures `checksum` and `length` **unconditionally**, and this pass
is the only thing that ever sets them back to `None`. Skipping it is
indistinguishable from the bug.

What the issue's *Why it matters* section actually asks for is the opposite:
on truncation the fields must be **cleared unconditionally**. The docstring is
what points the wrong way — "does nothing when … the payload is truncated"
describes the intent (do not derive from bytes the sender did not use) while
its literal implementation is the buggy output. Rewriting it is part of the
fix, not a tidy-up.

### The consequence to accept, and to write down

**Corruption is undetectable in a truncated capture.** A packet that was both
snaplen-cut *and* genuinely corrupt comes out with `checksum` cleared, exactly
like a clean one. That is not a regression to fix later — the bytes the sender
checksummed are not in the file, so no answer is available. Clearing is the
honest one: it says "unknown" instead of saying "corrupt" about every packet.
It gets a test of its own so the behaviour is pinned rather than incidental.

### Should UDP `length` be cleared too?

It is tempting to keep it as the last record of the original datagram's size.
It is not worth it: `_apply_ip` never writes IP `total_length` into the
`network` section at all — it is always derived on rebuild — so a truncated
packet's spec cannot reproduce the original packet whatever we do here.
Keeping `length` preserves nothing and breaks the same documented reading.

**Decided: clear both**, as the issue expects.

### Implementation

The signal is already computed one frame up and thrown away. In
`parse_packet` (`src/packeteer/parse/core.py`):

```python
declared = _ip_payload_size(ip_hdr, ip_size)
truncated = declared is not None and declared > len(remaining)
if declared is not None and declared < len(remaining):
    remaining = remaining[:declared]
```

Only the `<` branch is used today, to trim Ethernet padding; the `>` branch is
the truncation test, and the comment above it already names the snaplen case.

- Thread `truncated: bool = False` through `_parse_ip_protocol` into
  `_clear_derivable_transport_fields`, including the AH recursion at
  `core.py:876` — AH is transparent, so a truncated packet behind it is still
  truncated.
- In `_clear_derivable_transport_fields`, clear `checksum` (and `length` for
  UDP) and return before any derivation is attempted.
- Rewrite the docstring's last paragraph to say what the code now does.

No public API changes, so no `Breaking:` marker and nothing new to document in
the API reference.

### Why not a `ParsedPacket.truncated` attribute

Filed as [#94](https://github.com/adamkjonsson/packeteer/issues/94)
(unmilestoned) rather than done here. It is an addition, not a fix, so it
wants a minor bump rather than this patch release — and the three entry points
do not have the same information, which is a design question rather than a
line of code.

- `iter_packets` **has** the authoritative signal — `PacketReader._packets`
  passes `PcapRecord`s into `_packet_from_records`, and they carry `orig_len`.
  That is the `len(record.data) < record.orig_len` guard `zpfwire` uses today,
  and it covers cases the IP header cannot see.
- `parse_pcap_file` / `parse_pcap_packet` **cannot**: the record is a
  `(data, ts_sec, ts_frac)` tuple and `orig_len` is dropped before parsing.
- `parse_packet` on raw bytes has only the IP header.

So the attribute would mean "the capture says so" on one path and "the IP
header says so" on the other two unless the record tuple grows a field (a
breaking change) or `PcapRecord` is threaded through. The IP-header test used
here needs none of that and works on every path, including the raw-bytes API.

**Decided (Adam, 2026-08-28): one attribute with the datagram meaning**, since
capture truncation is already reachable through `ParsedPacket.source_records`
on the path that has it. #94 carries the reasoning.

### The gap this leaves

`_ip_payload_size` returns `None` for an IPv6 jumbogram (`payload_length` of
`0`, RFC 2675), so truncation is undetectable there and the old behaviour
persists. Rare enough for a sentence in the docstring rather than code; the
`ParsedPacket.truncated` issue is where it would be closed properly.

A lying IPv4 `total_length` — larger than the bytes present, but not from a
snaplen — is treated as truncation. That is the same answer for the same
reason: the derivation cannot be checked, so "unknown" is the honest result.

### Tests

In `src/tests/test_transport_overrides.py`, beside the #68 tests whose
invariant this restores:

- All four combinations (TCP/UDP × IPv4/IPv6): truncated → neither key in the
  spec, and the parsed header fields are `None`.
- The same packets captured whole still produce no keys (the control that
  proves the test is measuring truncation).
- **Non-regression on #68:** a fragmented datagram's first fragment still
  records `length` 1032 and its checksum. `declared == len(remaining)` for
  every fragment, so the new test must not fire — this is the case most at
  risk from the change.
- A checksum that was wrong on the wire, captured whole, is still kept.
- A packet both truncated **and** corrupt comes out cleared, with the test
  named so the limitation is legible.
- Truncation cut inside the transport header (no transport parsed at all)
  still leaves the payload alone.

### Docs

`docs/packet-spec/format.md`, the `length` and `checksum` subsection: it
currently says the keys appear in "two cases". Add the third thing a reader
needs — that a truncated capture emits neither, and therefore cannot report
corruption.
