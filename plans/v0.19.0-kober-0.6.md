The trigger is external again.
[kober](https://github.com/adamkjonsson/zipline-kober) released `0.6.0` on
2026-10-20 (`a09d92c`). It is the WireGuard release: a protocol a spec can
frame but not read is decoded with the caller's own transform registered
beside the spec. Most of it is outside the dialect (a `zpf` 0.6 port, the
examples, the compiled driver). What the dialect gained is general, and is
what the first strand of this release is about:

| kober 0.6.0 | Where | packeteer 0.18.0 |
|---|---|---|
| A **map parameter**, `{type: {map: [K, V]}}` | document `params:` | Declined with the block, unread |
| **A map entry**, `keys[receiver]` | any expression | **Refused**: *indexing is not allowed* |
| **`fails_as`** | a `transforms:` declaration | Declined with the block, unread |
| **`len(b)`**, the sixth function | any expression | Declined, as every call is |
| **`net:ip`, `net:ethernet`** | a transform's `content_type` | Declined with the transform |

The promise since 0.13.0 is that a spec from either repository loads in the
other, and a kober construct packeteer lacks is *declined out loud, naming
it*. kober 0.6.0's two new examples keep it:

```console
$ packeteer protocol check ../zipline-kober/examples/wireguard/wireguard.yaml
…
wireguard 0.1: 8 error(s), 1 warning(s)        # every error "not supported yet"
$ packeteer protocol check ../zipline-kober/examples/packbits/packbits.yaml
…
packbits 0.1: 5 error(s)                       # likewise
```

`dns.yaml` and `http.yaml` are unchanged since 0.5.0. The new constructs
break the promise only where kober's examples do not happen to go:

```console
$ packeteer protocol check sizes.yaml          # size: {expr: "sizes[kind]"}
error: sizes.yaml:11: units.m.fields[1]: indexing is not allowed in an expression
$ kober check sizes.yaml
p 0.1: ok
```

`wireguard.yaml` loads only because its one map entry is in a transform's
`args`, which packeteer declines without parsing.

**#208** is that break. **#209** is that a declined block is declined unread,
so a typo inside one hides behind the decline, and 0.6.0 gave both blocks
more to get wrong. **#210** is older than 0.6.0 but 0.6.0 moved it: every
call is declined alike, so an invented function looks like a kober one.

**#206** belongs to the same strand from the other side. It was found
checking whether `protocol compile` had the bug kober 0.6.0 fixed in its own
compiler, a field named like a helper the generated code calls. packeteer
does not, but a unit named like a builtin (`value_error` → `class
ValueError`) replaces it for the whole generated module, `none` produces
source that does not parse, and a dunder field (`__init__`) overrides the
dataclass. Reproduced on 0.18.0: the `value_error` spec's bad `const`
raises `TypeError: exceptions must derive from BaseException`.

**The second strand** is two bugs 0.18.0's work turned up and left, neither
to do with kober's dialect:

- **#199**: `stream --json` drops a decoded application section, so
  `stream --json` → `build` gives empty datagrams and segments for every
  built-in and compiled protocol, and says nothing. Reproduced on 0.18.0: an
  HTTP stream's packets carry `ethernet`, `network`, `packet_metadata`,
  `transport`, and no `http` or `payload`.
- **#201**: an AH stream, or an `ESPEncap(icv_len=N)`, is not reproducible
  under `--seed`, because the ICV stand-in is `os.urandom`
  ([ipsec.py:144](../src/packeteer/generate/ipsec.py#L144),
  [:180](../src/packeteer/generate/ipsec.py#L180)).

**#198**, two-way TCP data, was attached and then moved to 0.20.0. It
changes the TCP connection model, sequence and ACK numbers, loss,
retransmission and corruption in both directions, which is several days on
its own and the area #115's bugs live in. 0.18.0 already refuses an `s2c`
message on TCP, naming #198, so nothing is wrong in silence while it waits.
It gets its own plan.

# Part 1 — #209, the declined blocks read before they are declined

## The fix

Both blocks stay **declined**, at the block's line, exactly as today. Before
recording the decline, the loader reads them as kober's loader does and
refuses what kober refuses:

- **A transform declaration** is a mapping, or empty. Keys `params`,
  `fails_as`, `doc`; anything else is an unknown key, naming the allowed
  three. `params` maps names to one of the four expression types. `fails_as`
  is a string.
- **A document parameter** is `name: type`, or `name: {type, secret, doc}`
  with `type` required and `secret` a bool.
- **A parameter's type** is one of the four, or `{map: [K, V]}`: a mapping
  with only `map`, a list of exactly two, `K` `int` or `str`, `V` any of the
  four. kober's messages are the model: *a map is keyed by int or str, not
  bool*; *a map is [key type, value type], and this lists 1 type(s)*.

The model gains what the expression checker needs and no more: the document
parameters' names and types, map or scalar, kept on the loaded spec beside
`unsupported`. Not public API until something outside the checker wants it
([Q2](#q2)) — *corrected below: public.*

**Not done**, as #209 says: `fails_as` against the format's reason classes,
and `net:` against its vocabulary. kober reads both from `zpf`. A
`content_type` is already checked to be a string, and that stays.
([Q3](#q3) asks about `fails_as`'s spelling, which needs no table.)

## Tests

One case per refusal in the lists above, each checked against `kober check`
when written, plus: the long form with a map loads and is declined once; an
empty declaration (`br: {}`, `br:`) loads; a block that is valid reports
only the decline, as today.

## Changelog

`Changed`: a document's `params:` and `transforms:` are checked as kober
checks them before being declined, including kober 0.6.0's `fails_as` and
map parameters. Not **Breaking**: every spec it newly refuses was already an
error, and the only change is that the error is now the real one.

### What #209 corrected

**The parameters are public: `Spec.params`.** The plan kept them private
([Q2](#q2)), but the checker reading a private attribute of `Spec` is
ruff's `SLF001`, and a `# noqa` is a last resort. Settled 2026-10-23 as
public, mirroring kober's model: `Spec.params: Mapping[str, Param]`, and
`Param(name, type, loc, secret)` whose `type` is an `ExprType` or a
`MapType(key, item)`. Both live in `spec.py`; `spec.py` imports `ExprType`
for type checking only, since `expr.py` imports `spec.py`. `ExprType` is
in the API reference for the first time, since `Param.type` exposes it.

**A reference to a document parameter was a leak, and is typed now.**
Found while reading the checker for this part, and older than kober 0.6.0:
`condition: "mode == 1"` with `params: {mode: int}` was reported as *unit
'm' has no field 'mode'* beside the block's decline, the leak #167 and
#174 closed for fields. A reference whose head is no field and is a
document parameter now takes the parameter's declared type, in any scope,
as kober's `_in_unit` does. A map read whole, and a parameter descended
into, are refused in kober's words. A parameter named like a field is
refused, as kober refuses it, since that is what keeps the lookup
unambiguous. kober also counts unit parameters in that clash; packeteer
declines unit parameters without reading them, so only fields are counted.

**`fails_as`'s spelling is checked** ([Q3](#q3), settled as recommended),
in the loader rather than the checker: nothing of a declaration is kept,
so it is checked where it is read. kober reports it from `check`; either
way it is an error.

**Not done: kober's *declared and never used* warning** for a transform
declaration. Every transform is declined, so every declaration is in the
same position, and the warning would say nothing the decline does not.

**A loader message said `_LinedDict`.** The `{map: {int: bytes}}` test
caught it: a YAML mapping where a string, an integer or a list was wanted
was named by the loader's own class, and the same spec in JSON said
`dict`. Older than this release (0.18.0 says *name must be a string, not
_LinedDict*). Every such message now says `dict`, with its own `Fixed`
entry.

**The vendored and shipped specs are unmoved.** kober 0.6.0's four
examples check exactly as before, 8 + 1 / 5 / 19 / 4 + 3, and the suite
passed before any test was added.

# Part 2 — #208, a map entry declined by name

## The fix

- **The parser accepts `name[expr]`.** `ast.Subscript` leaves `_REFUSED`. A
  new node, `Index(table, key)`, as kober's `kober.expr.Index`. Refused at
  parse, in kober's words: a slice (*a slice is not allowed in an
  expression*), a key of several parts (*an index is one expression, not
  several*), and anything indexed but a bare name (*only a map parameter can
  be indexed, by its name: keys[receiver]*). A bare `this`, `parent` or
  `root`, or `true`/`false`, counts as not a name.
- **The checker declines it** at its line, *not supported yet: an entry of a
  map parameter*, recorded in `spec.unsupported`. Its type is the `Declined`
  stand-in, so a field reading it stays quiet, the lesson of #167 and #174.
  The key is still type-checked against the map's key type where #209 gives
  one.
- **An index on anything but a map parameter is refused** ([Q1](#q1)):
  *'kind' is not a map parameter, and only a map parameter can be indexed*,
  as kober's `check` says it.
- **A map parameter read whole** (`keys`, not `keys[x]`) is refused with
  kober's message: *'keys' is a map; an expression reads one entry of it,
  keys[key]*.

`codegen` and the runtime need nothing: a spec with a decline does not
compile, as today.

## Tests

The issue's spec: loads, two *not supported yet* (`params`, the entry),
nothing else. The entry inside a `condition`, a `dispatch` and a `count`.
Each parse refusal. `kind[0]`, a unit parameter indexed, and an unknown name
indexed. The map read whole. A key of the wrong type. `show` marks the field.

## Changelog

`Added`: kober 0.6.0's map entries, `keys[receiver]`, are recognised and
declined. `Fixed`: one was refused as indexing.

### What #208 corrected

**The entry has the map's value type, not a stand-in.** The plan gave it
`Declined`'s quiet. But #209 typed the parameters, and kober types the entry
as the map's values, so `sizes[kind]` with a `map: [int, bytes]` used as a
size is an error in both dialects and is reported. What stays quiet is
everything a decline alone would explain: one *not supported yet* per entry
and nothing else, the issue's acceptance.

**The decline is a checker error, not a `spec.unsupported` record**, as a
declined call already is. Expressions are parsed by the checker, not the
loader, so there is no loaded record to add one to; `show` prints the entry
as written but does not mark it. `compile_spec` still refuses the spec,
since a map entry needs a map parameter and `params:` is recorded. A spec
compiled without `check` that indexes a field meets a refusal in codegen's
renderer, where it would otherwise have crashed.

**`type_of` takes the map resolver as an optional fourth argument**,
`resolve_map`, beside `resolve` for references. `None` means no maps, so
the expression module can still be typed on its own. A new `indexes()`
walks an expression the way `references()` does; `references()` now
yields the key's references, as kober's citation does.

**The derive warning skips an expression with an entry.** `size: {expr:
"sizes[kind]"}` has one reference, `kind`, and would have been told to
`derive: {size_of: body}`. `kind` keys the size; it is not the size.

**Refused at parse, as kober refuses at load:** a slice, a tuple index,
and an index on a dotted path, a scope word, a boolean, or another index
(`keys[0][1]`). A test in `test_protospec_expr.py` had pinned `xs[0]` as
*indexing*; it now pins `xs[1:2]` as *a slice*.

Checked against `kober check` on nine specs: the issue's, the three places
an expression goes, `kind[0]`, a scalar parameter, an unknown name, a key of
the wrong type, a value used as the wrong type, and a key read too early.
Every refusal is kober's message, or the same fault in packeteer's existing
wording where both already had one. kober 0.6.0's four examples check as
before.

# Part 3 — #210, kober's six functions, and nothing else

## The fix

- A table of kober's six function names in `expr.py`, with a comment naming
  the kober version it was copied from (0.6.0), since it is the one place
  that will drift.
- A call to one of them stays declined: *not supported yet: kober's function
  `len()`*.
- A call to anything else is refused: *'frob' is not one of kober's
  functions; there are only endswith(), len(), lower(), startswith(),
  to_int(), trim()*.
- A call whose callee is not a bare name (`a.b()`) keeps today's refusal.

## Tests

Each of the six declined, `frob()` refused, and the WireGuard switch
dispatching on `len(sealed)` pinned in Part 5.

## Changelog

`Changed`: a call outside kober's six functions is refused, not declined.
Not **Breaking**, for the same reason as #209.

### What #210 corrected

**A call on a dotted path is refused, not kept as declined.** The plan kept
today's handling for `a.b()`, which was a decline. kober refuses it, so a
decline claimed a spec was kober's when it is not, the fault #210 is
about. It is refused naming the callee as written, `'a.len'`. kober's own
message here says `'Attribute'`, an AST class name: filed as
[zipline-kober#57](https://github.com/adamkjonsson/zipline-kober/issues/57)
on 2026-10-23, with `'Subscript'`, `'Constant'` and `'BinOp'` for the other
callees that reach it. `'Subscript'` is a regression in kober 0.6.0.

**Arity and keywords are refused too**, since kober refuses both at load:
*len() takes 1 argument(s), got 0*, *to_int() takes 1 or 2 argument(s), got
3*, *len() takes positional arguments only*, in kober's words. So a call
reported as declined is always one kober would accept.

**The arguments are not typed.** #208 typed a map entry before declining it;
a call is still declined at parse, as before, so `len(5)` is declined
rather than refused for its argument's type. Typing calls would mean giving
each of kober's six a signature in packeteer and a checker path for a
construct it cannot build; it waits for a protocol that needs one.
*Reversed by [#211](#part-3b), from kober's review of `.dev1`: the checker
path existed already, #208's, and leaving calls untyped broke #167's promise
for one kind of declined expression and not the other.*

**The table is `expr.KOBER_FUNCTIONS`**, name to (fewest, most) arguments,
public beside `MAX_SHIFT` and `SCOPE_WORDS`, with a comment naming kober
0.6.0's `BUILTINS` as its source. The decline keeps its note: *not supported
yet: kober's function len() — this version has no functions in
expressions*.

Checked against `kober check` on six specs. kober 0.6.0's four examples
check as before; `wireguard.yaml`'s `len(sealed)` reads with the new
wording.

# Part 3b — #211, a call typed before it is declined

*From zipline-kober's review of `0.19.0.dev1` (`e57ac03`), 2026-10-23. The
review found #206, #208, #209 and #210 correct, and filed this.*

## The issue

#210 declined a call to one of kober's six functions at parse, so the call
was never typed. A wrong argument (`len(tag)` on a string) or a misused
result (`lower(tag)` as a size, `to_int(tag)` as a condition) read as *not
supported yet* and nothing else, where kober's `check` refuses each. #208
typed a map entry before declining it; a call was the one declined
expression that did not get the same treatment.

## The fix

- **A call parses**, to a new `expr.Call(name, args)`, once #210's
  refusals have passed: a name in kober's table, no keyword argument, an
  argument count it accepts.
- **`KOBER_FUNCTIONS` holds signatures**: each name to a
  `KoberFunction(params, required, returns)`, copied from kober 0.6.0's
  `BUILTINS`.
- **`type_of` types a call by it**: each argument held to its parameter,
  *argument 1 of len() is str, expected bytes*, and the call given its
  return type instead of *unknown*. Settled 2026-10-23: packeteer's wording,
  as every other type error and #208's key mismatch already read, not
  kober's *needs bytes, got str*.
- **The checker declines each call** after typing it, one *not supported
  yet: kober's function len()* per call, walked by a new `expr.calls()` as
  `indexes()` walks map entries. A type fault inside is reported in place of
  the decline, as #208 does for an entry.
- **The derive warning skips an expression with a call**, as it does one
  with an entry: `to_int(content_length)` has one reference, and no
  `size_of` can answer it.
- **Codegen refuses a call**, for a spec compiled unchecked, as it refuses
  an entry.
- `references`, `indexes` and `calls` share one walk, `_nodes`, which
  descends into a call's arguments.

## Drift

kober's review suggested pinning the table to kober's documented one. The
test cannot import kober, so kober's `docs/format/expressions.md` is
vendored beside the specs, from the same `v0.6.0` tag, and
`TestKobersFunctionTable` reads its *Functions* table: the same six names,
every argument count each takes (`to_int` is listed with one and with two),
and each result type. Parameter types are not in kober's table and are
pinned by `TestCallsAreTyped`. Checked that the test fails when a function
is removed, an optional argument dropped, or a result type changed.

## Checked against kober

The issue's seven, through both checkers: each refused at the fault kober
reports, in packeteer's words. `len(body) == 4` and a size `to_int(tag)`
report only their decline, with no derive warning. kober 0.6.0's four
examples check as before; `http.yaml` keeps its 19, since its calls are all
inside constructs declined whole.

## Changelog

`Changed`: a call to one of kober's functions is typed before it is
declined; `KOBER_FUNCTIONS` maps names to `KoberFunction`. `Added`, folded
into the same entry: `Call`, `calls()`.

# Part 4 — #206, names the generated module needs for itself

## The fix

Refuse rather than rename, as `_RESERVED`
([codegen.py:76](../src/packeteer/protospec/codegen.py#L76)) already does, at
the unit's or field's location and naming the name:

- **A unit whose class name is a Python builtin or keyword.** The camel-cased
  name is held to the builtins ([Q4](#q4)) and to `keyword.iskeyword`, which
  covers `None`, `True` and `False`. `_RESERVED` then lists only what the
  module imports and defines, not which builtins it happens to call.
- **A field or unit name beginning with an underscore.** The generated code
  owns that namespace: `_obj`, `_r`, `_w`, `_parent`, `_root`, and the dunder
  names the class and `object` define. kober's compiler refuses the same
  prefix for the same reason (`kober.pygen.RESERVED_PREFIX`).

**At `compile`, not at `check`**, which keeps the dialects level: `kober
check` accepts `{name: _obj}` and only `kober compile` refuses it, and
packeteer's `check` accepts it today. A spec with such a name still loads,
checks, and builds from the interpreter; only generating a module refuses it.

`none` today reaches the final parse check and is reported as *a bug in
packeteer's compiler*. After this it is refused before any source is written.

## Tests

The issue's: `value_error`, `none` and `exception` as unit names, `__init__`,
`__class__` and `_obj` as field names, each refused with location and name.
And the converse: every spec in `examples/protocols/` and the test suite
still compiles, round-trips a message, and raises `ValueError` on a wrong
`const`.

## Changelog

`Changed`: **Breaking:** `protocol compile` and `compile_spec` refuse a field
or unit name beginning with `_`, and a unit named like a Python builtin or
keyword. A spec that used one must rename it. Until now such a name compiled
unless it collided, and a collision broke the generated module in ways
reported as something else. None of packeteer's or kober's shipped specs is
affected. `Fixed`: a unit named `value_error` no longer replaces
`ValueError` in its module; `none` is refused, not reported as a compiler
bug.

### What #206 corrected

**Two more names broke a module, neither of them underscored.** Checking
which field names actually break a generated module, rather than which
might: a field called `field` failed at import, and one called `list` at
the first decode. A repeated field's default, `field(default_factory=list)`,
runs in the class body, where the field's own class attribute had just
bound the name to `0`. `int`, `bytes`, `len` and the rest are harmless:
annotations are strings, and the decode functions read fields through
`_obj`. Refusing `field` and `list` would have been one more hand-kept list,
the thing #206 closes, so the class body now uses names no spec can take:
`from dataclasses import field as _field`, and
`_field(default_factory=lambda: [])`. That is kober 0.6.0's own answer, an
underscore alias, and the underscore refusal is what makes it safe. The
generated source changes for any spec with a repeated or unit field.

**`_obj`, `_r` and `_w` did not break anything.** The issue listed them.
They are locals of the generated functions, and a field is always reached
as `_obj.name`, never as a local, so a field `_obj` decoded correctly. The
underscore rule refuses them anyway: the namespace is the module's, and
the next helper added to it should not have to check.

**Q4, settled as recommended**: `dir(builtins)` of the running interpreter,
as `_BUILTINS`. A class name is always capitalised, so what can actually
be hit is the exceptions, `Ellipsis`, `NotImplemented` and the three
keywords. The `field` entry left `_RESERVED`, since the module no longer
binds that name.

**`check` still accepts these names**, as the plan said: `kober check`
accepts `{name: _obj}` and only `kober compile` refuses it. The docs gain
*Names `compile` refuses* in `format.md`, linked from the field `name` row
and from `protocol compile`.

# Part 6 — #199, `stream --json` is `parse`'s format by construction

## The bug

`_stream_to_json`
([\_\_main\_\_.py:1685](../src/packeteer/__main__.py#L1685)) is a hand-written
copy of `parse`'s `_packet_to_spec`
([parse/core.py:1400](../src/packeteer/parse/core.py#L1400)), and it has
drifted. On the transport path it writes `pkt.payload` only, and a decoded
packet has `pkt.app` set and `pkt.payload` empty, so it writes neither. It
also lacks the `loopback` and `sll` link layers, `network.declared_length`,
and the payload of a packet with no transport header. And it calls
`to_packet_spec` without `protocols=`, so even once fixed, a compiled
protocol's JSON would not name the module `build` needs, as `parse`'s does.

## The fix

- **One conversion.** `_packet_to_spec` becomes public in
  `parse/to_config.py`, beside `update_config` and `to_packet_spec`, and
  exported from `packeteer.parse` ([Q5](#q5) for its name). `parse` calls it
  as before.
- **`_stream_to_json` shrinks** to that call per packet, plus
  `packet_metadata`'s `direction` and `label`, plus `protocols=` with the
  paths the user gave `--protocol`. That is CLAUDE.md's rule for
  `__main__.py`, and it gives the API what the CLI does: a stream's packets
  to a spec without the CLI.
- Whether the stream-to-spec half becomes public API too (a
  `stream_to_spec(packets)` beside the generators) is left to Q5's answer.

## Tests

The issue's: for each `--payload` (`dns`, `http`, `vpn`, a compiled
protocol, random bytes), `stream --json` → `build` gives the same packet
bytes as `stream --pcap` with the same seed. And `stream --json`'s packets,
less `packet_metadata`, equal `parse` of that pcap. The compiled-protocol
case builds without `--protocol`.

## Changelog

`Added`: the per-packet conversion as public API (Q5's name). `Fixed`:
`stream --json` writes a decoded application section, so `build` no longer
rebuilds empty payloads; it names the protocol modules it was given.

### What #199 corrected

**Q5, settled as recommended**: `packet_to_config(pkt)`, in
`parse/to_config.py` beside `update_config` and `to_packet_spec`, exported
from `packeteer.parse`, and no `stream_to_spec` yet. `parse` calls it where
it called `_packet_to_spec`, which is gone. It moved without a circular
import: `to_config.py` already named `ParsedPacket` for type checking only.

**`_stream_to_json` is the call and the metadata**, nothing else, and the
CLI no longer imports `update_config` or `apply_tunneled` at all. The
protocol paths come from `_spec_protocol_paths`, which `parse` already
used; it now takes the spec file as a parameter, `args.output` for `parse`
and `args.json` for `stream`, so a path is recorded relative to whichever
file is written.

**Seven test modules imported the private `_packet_to_spec`.** They use
`packet_to_config` from `packeteer.parse` now, which is what the API was
missing.

**The round trip, before and after.** A script ran `stream --pcap` and
`stream --json` with one seed, built the JSON, and compared every frame,
for DNS, HTTP, DHCP, VPN, a compiled `sensor`, and random bytes. On
`.dev1` DNS, HTTP, DHCP and `sensor` rebuilt differently and their JSON had
no section; VPN and random bytes, which nothing decodes, matched. Now all
six match, and `sensor`'s JSON carries `protocols: ["sensor.py"]`, so
`build` rebuilt it with no `--load-protocol`. `test_stream_json.py` is that
script, and 9 of its subtests fail on `.dev1`'s source.

**Also as the issue asked**: `stream --json`'s packets less
`packet_metadata` equal `parse`'s on the same pcap, for DNS, HTTP and
random bytes.

# Part 7 — #201, a seeded ICV

## The fix

The ICV stand-in, for AH when no `icv` is given and for ESP's `icv_len`
trailer, is derived from the bytes it stands beside, as the issue proposes:
a `random.Random` seeded from a digest of the authenticated bytes, the way
ESP's payload scramble is already seeded. Content-derived rather than
stream-seeded, so `PacketBuilder.ah()` called directly, with no seed in
reach, is reproducible too, and two packets with different content still
get different ICVs.

The two other `os.urandom` calls in `builder.py`
([:1140](../src/packeteer/generate/builder.py#L1140),
[:1629](../src/packeteer/generate/builder.py#L1629)) are a `PacketBuilder`
asked for random bytes of a size, which no stream reaches. They stay.

## Tests

The issue's: a seeded `stream --ah` twice, and
`generate_*_stream(encap=AHEncap(...))` and `ESPEncap(icv_len=12)` twice,
give identical bytes. Two different payloads give different ICVs. An
explicit `icv` is used unchanged.

## Changelog

`Fixed`: a seeded stream with AH, or an ESP ICV, is byte-identical between
runs, as `--seed` promises. Packet bytes change from 0.18.0's for the same
seed, which was never stable for these.


### What #201 corrected

**AH's stand-in needed the bytes AH protects.** `_build_ah_header` saw
only the header, so it gained a third argument, `protected`, which the
builder already had in hand as the inner data. The stand-in covers the
fixed AH header and those bytes, as a real ICV covers them; ESP's covers
its SPI, sequence and (scrambled) payload. One helper, `_icv_stand_in`,
does both: a `blake2b` digest seeding a `random.Random`, as `_scramble`
already did, with a `person` tag of its own so an ICV is never the
scrambled bytes' prefix.

**Checked before and after**: the issue's `stream --ah … --seed 7` twice,
and `AHEncap` and `ESPEncap(icv_len=12)` through `generate_udp_stream`
twice. All three differed on the branch before this change and match after
it. Three docstrings that said the ICV was random bytes say what it is.

# The sweep, and the release

After zipline-kober's clean review of `.dev2`, as in 0.17.0 and 0.18.0, a
sweep for what this release made untrue: kober versions and function counts
anywhere in the docs and the code, the old *indexing is not allowed*
refusal, `_packet_to_spec`, and the ICV described as random bytes. It found
nothing the parts had not already fixed. The two `os.urandom` calls left in
`builder.py` are the ones Part 7 keeps, and the one *Breaking* entry, #206,
says what a spec must do instead.

The changelog's summary paragraph names `net:` labels as declined but not
checked, which they are not: kober checks them against `zpf`'s vocabulary,
which packeteer does not depend on.

Release, as CLAUDE.md lists it: `[Unreleased]` became `[0.19.0] -
2026-10-23` with a fresh one above it, `.dev2` came off `pyproject.toml`,
the link definitions gained the release, and `v0.19.0` is tagged on the
merge. Then #199, #201, #206 and #208–#211 close, and the milestone.

# Not in this release

- **Building any of it.** A map, `len` or a transform has no use in a
  packet packeteer generates. A transform's inverse (sealing, compressing) is
  already the caller's, through 0.18.0's `stream --udp-tunnel`, which is how
  kober's WireGuard example generates its traffic.
- **`net:` and `fails_as` classes**, which need `zpf`'s tables (Part 1).
- **#198**, two-way TCP data, moved to
  [0.20.0](https://github.com/adamkjonsson/packeteer/milestone/15) on
  2026-10-23. The reasons are under the issue table above. The open design

  `render_tcp_session` with HTTP's two-way messages (#169).
- **kober's copies of packeteer's specs** (`tests/packeteer/`) say 0.16.0.
  `examples/protocols/` has not changed since, so they are accurate; only
  the label is stale, and it is kober's to update.

# Undecided

(q1)=
**Q1 — is `kind[0]` refused, or declined?** *Settled: refused.* kober refuses an index on
anything but a map parameter at `check`. packeteer could decline every
subscript and stay out of it. *Recommended: refuse*, as kober does. Once
#209 reads the parameters it is one lookup, and a spec that indexes a field
is wrong in both dialects.

(q2)=
**Q2 — are the document parameters public?** *Settled: public, as
`Spec.params`; see [What #209 corrected](#what-209-corrected).* #209 keeps them on the loaded
spec for the checker. *Recommended: private for now* (`_doc_params` or
similar). Making them public is a promise about a construct packeteer
declines, and nothing outside the checker reads them.

(q3)=
**Q3 — is `fails_as`'s spelling checked?** *Settled: yes.* kober requires lower-case words
joined by hyphens (`[a-z]+(-[a-z0-9]+)*`), separately from the class check
that needs `zpf`. *Recommended: yes*, since it is a regex and catches
`Decrypt_Failed`. The class check stays out.

(q4)=
**Q4 — which builtins does #206 refuse?** *Settled: the running
interpreter's, as recommended.* `dir(builtins)` of the running
interpreter is complete but moves with the Python version: a unit that
compiles on one Python can be refused on the next, and a module generated
on an older one can meet a builtin it shadows on a newer. A fixed list in
`codegen.py` is stable but must be kept. *Recommended:
`dir(builtins)` of the running interpreter.* The refusal only ever grows,
the message names the builtin, and a fixed list would be the hand-kept
`_RESERVED` problem #206 is closing.

(q5)=
**Q5 — what is the per-packet conversion called, and does a stream get one
too?** *Settled: `packet_to_config`, and no stream function, as
recommended.* #199 makes `_packet_to_spec` public. Its neighbours are
`update_config` (a section into a dict) and `to_packet_spec` (packet dicts
into a spec). *Recommended: `packet_to_config(pkt: ParsedPacket)`*,
matching `update_config`'s word for a per-packet dict, and **no**
`stream_to_spec` yet: one public conversion is enough to make the CLI's a
thin call, and a stream-level function can follow when an API user asks.
