# Plan — v0.13.0: the dialect release

*Written 2026-09-10.*

*Status: **not started**. One open question, [Q1](#q1), which blocks only the
last issue — see [Undecided](#undecided).*

The trigger is external. [kober](https://github.com/adamkjonsson/zipline-kober)
released `0.1.0` on 2026-09-07 and `0.2.0` on 2026-09-10, and its `0.2.0` is
itself a dialect release: it added no decoding, and changed only the surface an
author writes. Three of its strands land on us directly — the shorthands became
the spelling its reference *teaches*, `endian` learned to inherit, and its
format reference now names, in print, the two things that do not transfer from
here.

This milestone is our side of that, and it turned out to have **two strands**
rather than one.

**The dialect surface** — #143, #141, #142, #144 — is the mirror of kober's
`0.2.0` in scope and in kind. Nothing in it changes what packeteer parses,
builds or redacts; a spec gets shorter to write and one key gets renamed.

**Sizing and framing correctness** — #140, #145, #146 — arrived while scoping
the first strand and is not cosmetic at all. Two are bugs where `check` passes
a spec that cannot work, and the third is the size form whose absence is why
the second bug is reachable. These change what packeteer decodes, and the
release notes must not describe this milestone as purely a surface change.

The strands share machinery, which is why they belong in one release: the
width resolver #146 needs is the one #140 must teach about conditional fields,
and the refusal #145 adds is only writable once #146 gives it something to
recommend.

## The claim that shapes this milestone

`docs/protocols/format.md` says this dialect is **a superset of kober's**. That
claim was decided deliberately in
[Q3](user-defined-protocols.md#q3) and it is currently false in both
directions:

```console
$ packeteer protocol check ../zipline-kober/examples/dns.yaml
error: dns.yaml:27: units.message.fields[0]: a field has no key 'bits'; …

$ kober check examples/protocols/rpc.yaml
error: rpc.yaml:24: rpc.message.body: 'on' was renamed to 'dispatch' at 0.1.0
```

Neither project can read the other's shipped examples. That is not a small
gap around the edges of the format — `bits:` is how kober's reference now
writes the commonest field there is, and a switch is the commonest branching
construct we have.

**The asymmetry to keep in view:** kober has already done its half. Its `0.2.0`
recognises our four keys, declines them out loud with a reason, and vendors our
specs into `tests/test_packeteer.py` so the compatibility is a property of two
loaders rather than a sentence in two references. Everything in this milestone
except #140 and #145 is us catching up to work that has already landed on the
other side — and one issue, #143, is something kober's reference explicitly
says is "packeteer's to move".

The two exceptions are ours alone, and both were found by doing the comparison
rather than by using the tool: a key that loads and does nothing, and a size
that passes `check` and decodes nothing. Reading another implementation of the
same format is what surfaced them, which is an argument for #144 independent of
the compatibility it protects.

# Part 0 — the branch and an honest version

One commit, before any issue work.

- **Branch `v_0.13.0` off `main`.** The convention every milestone since 0.8.0
  has used: one release branch, each issue a commit on it, one PR at the end
  (`v_0.12.0` → #135, `v_0.11.0` → #116). The repository requires a PR, so
  nothing here lands on `main` directly.
- **The plan lands first**, as `ea22439` did for 0.12.0. It is the branch's
  first commit, so the reasoning is in the history before the work it argues
  for.
- **`pyproject.toml` to `0.13.0.dev0`.** It reads a bare `0.12.0` today, which
  is the post-release state.

## The one thing to do differently from last time

**The version bump belongs in this commit, not in the first issue's.**

Historically it has not been. `0.12.0.dev0` was set in `8e09c81`, the #122
commit; `0.11.0.dev0` in `82769f9`, the #105 commit. Both were the first
substantive commit on their branch, so the bump was real but incidental.

The cost is small and entirely avoidable: between branching and that first
feature commit, every build made from the branch reports itself as the
*released* previous version. On a branch that lives as long as a milestone —
0.12.0 ran to eighteen issues — that is a window in which a `.devN` build is
indistinguishable from the release it is not. kober states the rule directly
in its own Step 0: first commit on the branch, before anything else, "so every
build from here identifies itself honestly."

There is a second reason specific to this milestone. #143 is breaking, and
`packeteer protocol check` will start refusing specs that pass today (#145 too).
Anyone testing a `.devN` build against their own specs needs the version string
to say what it is, and they will be doing that from the start of the branch
rather than after the eighteenth commit.

# Part 1 — #143, the rename

Do this first, and do it before #141, so that the loader rework in #141 is
written against the final key name rather than migrated afterwards.

## Why this is not obvious

**Our current behaviour is arguably better than kober's**, and the plan should
say so plainly rather than pretend the rename is a straightforward fix.

`on` is a YAML 1.1 boolean, so `on: kind` parses as `{True: "kind"}`. kober
renamed the key and deleted the problem. We kept the key and repaired the
parse in `_restore_on_key`, whose docstring makes the case: requiring `"on"` in
quotes "would work and would be a papercut every author hits exactly once".
That is true, and the repair is narrow and careful — only that mapping, only a
`True` key, only when a real `on` is not already there, `False` left alone,
JSON unaffected.

We are moving anyway because **we are the ones making the superset claim**. A
dialect with two spellings for its most common branching construct is a fork
with a compatibility note. The papercut `_restore_on_key` prevents is paid once
per author; the divergence is paid by every spec containing a switch, forever,
in both directions.

The secondary argument is independent of YAML and would hold even if the trap
did not exist: `dispatch: "header.op"` says what the expression is *for*, where
`on:` is a preposition attached to nothing.

## What changes

- `dispatch:` is accepted. `on:` is **refused with a message naming the
  rename**, not as an unknown key.
- `_restore_on_key` is deleted, along with the `True`-key repair.
- `Switch.on` becomes `Switch.dispatch`. Five readers in-tree: `show.py:211`,
  `check.py:325`, and three in `codegen.py`.
- `_switch` gains the `_reject_unknown` call it does not have today. Without
  it, a kober spec's `dispatch:` reports `missing required key 'on'` — naming
  the key that is absent rather than the one that is present, which is the
  least useful message available.
- `examples/protocols/rpc.yaml` and every `switch` in the reference move.
- The unquoted-`on` note in `docs/protocols/format.md` is **deleted**, not
  amended. The trap stops existing rather than being documented.

**Accepting both spellings is the one option to avoid.** It would make us the
project with two spellings, rather than the ecosystem having two, which is
strictly worse.

Changelog: under `Changed`, leading **`Breaking:`**, saying a spec using `on:`
must rename it to `dispatch:`.

# Part 2 — #141 and #142, one change in two issues

These are separable as work and inseparable as a release. #141 without #142
ships a shorthand that a whole class of spec cannot use.

## #141 — the three rules

Each spelling builds the **identical** `Spec`, so a document may mix them and
nothing downstream can tell which was used.

```yaml
- {name: count,   type: {int: {bits: 8}}}                        # 1. lift the kind
- {name: count,   int: {bits: 8}}

- {name: samples, type: {unit: sample}, repeat: {count: count}}  #    …type and repeat both
- {name: samples, unit: sample, count: count}

- {name: body,    bytes: {size: 4}}                              # 2. bare scalar body
- {name: body,    bytes: 4}
- {name: n,       int: 8}

- {name: qr,      bits: 1}                                       # 3. `bits` names the kind
```

We already have half of rule 2 — a bare `size: 4` is `{fixed: 4}` and a bare
`{unit: sample}` is a name. What is missing is the bare *body*.

**Confined to `loader.py`.** The spec dataclasses do not change, so `check.py`,
`codegen.py`, `show.py` and the runtime are untouched and every existing test
passes unchanged. The work is in `_field`, `_field_type`, `_size_value`,
`_repeat`, `_int_type`, `_unit_ref`, and the key sets at the top of the module.

### The key sets become three

This is the structural part, and the property everything else rests on: **the
three sets share no member.**

| | Keys |
| --- | --- |
| **A field's own** | `name`, `const`, `derive`, `sensitive`, `doc`, the `type`/`repeat` wrappers, and `condition` once #140 lands |
| **A type kind** | `bits`, `int`, `bytes`, `string`, `unit`, `switch`, and the unsupported `computed`, `pointer`, `select` |
| **A repeat kind** | `count`, and the unsupported `until`, `to_end` |

Our three added keys disturb nothing: `const`, `derive` and `sensitive` collide
with no type kind and no repeat kind, so the superset survives the lifting rule
intact. That is worth checking rather than assuming, and a test asserting the
three sets are pairwise disjoint is the cheap way to keep it true as the format
grows.

### Strictness is not weakened

More spellings reads like looser, and it is not. Exactly one key must name a
type kind; at most one a repeat kind (a repetition is optional where a type is
not); two kinds of the same construct is an error; a lifted kind beside its own
wrapper (`count:` with `repeat:`) is an error; a key in none of the three sets
is still an error.

The unknown-key message must **name the set each allowed key belongs to**
rather than printing one flat list. Three labelled groups is what keeps a
misspelled `conditon:` failing usefully once the flat list has tripled in
length.

### Unsupported constructs must lift too

`computed`, `pointer`, `select`, `until` and `to_end` are recorded on
`Spec.unsupported` and reported as *not supported yet*. They must be reported
that way **whichever spelling was used**. A construct we do not implement
becoming an *unknown key* because it was written short would undo the exact
distinction Q3 called for: "this will work later" against "you typed something
wrong".

### The examples move

Both files in `examples/protocols/` are rewritten short. kober's reasoning is
the right one and applies verbatim: an example that does not use the short form
is an argument that the short form is not wanted. That is the mistake kober's
`0.2.0` documentation work existed to undo, and the mistake is cheaper to not
make than to correct.

`docs/protocols/format.md` inverts the same way — each type's entry leads with
the short spelling, and a new section says when the long form is actually
needed: a body carrying a second key (`int: {bits: 4, enum: opcode}`), a type
inside a construct rather than on a field (a switch's cases), and readability.

## #142 — `endian` inherits

Resolves **field → unit → document → `big`**.

The reason this is in the same release and not a later one is not tidiness.
A field needing `endian` must write `int: {bits: 32, endian: little}`, so
**no integer field in a little-endian spec can use `bits:` at all**. Shipping
#141 alone hands the shorthand to wire protocols and withholds it from
everything else — a filesystem structure, a USB descriptor, a capture
container. Both our examples are big-endian network protocols, which is
precisely why the gap is invisible from inside this repository.

`sensor.yaml` holds the only field we ship that could not be written short:

```yaml
- {name: reading, type: {int: {bits: 32, signed: true, endian: little}}}
```

- **`endian` inherits. `signed` does not.** A protocol is little-endian; it is
  not *signed*. Byte order is a property of the format, signedness a property
  of what one field means.
- Resolution happens **at load**, folded into each `IntType`, so a `Spec` built
  from an inherited default compares equal to one with `endian` on every
  integer. `codegen.py`, `check.py` and the runtime need no changes.
- `endian` beside `bits:` at field level stays an unknown-key error.
- Below 8 bits it is meaningless and already ignored, which stays true.

**The cost, and the mitigation that pays it.** A field's meaning now depends on
a distant line: `bits: 32` no longer says how it is read. `packeteer protocol
show` must print the **resolved** byte order, so the question has a one-command
answer that does not involve scrolling to the top of the file. `show.py` prints
int types without byte order at all today, so this is an addition rather than a
change — and it is not optional, it is what makes the feature defensible.

# Part 3 — #140, the guard that was never wired up

`condition` is in `_FIELD_KEYS` (`loader.py:85`), is never read by `_field`,
and is not recorded as unsupported. It loads clean and the guard disappears:

```python
>>> s.unsupported
()
>>> s.units["m"].fields[1]
Field(name='b', type=IntType(bits=8, …), repeat=None, const=None, derive=None, …)
```

The compiled decoder then reads a byte that is not there whenever the guard is
false. This is the precise failure `loader.py`'s own docstring says the module
exists to prevent, and it is worse than a typo: being *in* the key set means
the unknown-key error advertises `condition` as supported while nothing
implements it.

**Full implementation, decided.** The one-line alternative — moving it to
`_UNSUPPORTED_KEYS` — closes the bug and not the gap, and `condition` is the
one unimplemented kober construct that does not hit the wall the others do.
Unlike `pointer`, `select` and `computed`, a guard is **symmetric**: the same
predicate in both directions.

- **decode**: evaluate against fields already read; false means the field is
  absent, consumes nothing, produces no value.
- **encode**: evaluate against the object; false means write nothing.
- **`to_spec`**: omit the key, as `derive` already omits a computed one.

It reads only fields decoded before it, which `check.py`'s forward-reference
check already enforces for every other expression, and it returns a boolean,
which `ExprType.BOOL` already covers.

## Where it bites

A conditional field has **no statically known width**, and two things in the
tree assume every field does.

1. `check.py`'s framing checks.
2. `derive: {size_of: …}` where the target is conditional.

kober hit this from the other side and **refused** a trailing `condition` in
its `fill` width resolver rather than approximating one. That is the precedent
and the right instinct: a guessed boundary is the thing these checks exist to
prevent. Refuse, naming the field responsible.

Concretely this is one line — `_fixed_bits` returns `None` for a conditional
field — and it is why #146 is ordered directly after this issue rather than
before it. See [Part 4](#the-line-these-two-share-with-140).

`sensitive` needs a stated answer rather than an emergent one: a field that is
absent has nothing to redact, so the sanitiser skips it. That is the natural
reading, and the reference should say it rather than leave it to fall out of
the implementation.

Ordering: **after #141**, so `condition` joins a key set that has already been
restructured into three, rather than being added to a flat set that is about to
be rewritten.

# Part 4 — #146 and #145, the fifth size and the bug it explains

kober has five sizes; we have four. The missing one is `fill` — everything
left, less what the fields after it claim — and its absence is not an
inexpressive corner. It is why #145 is reachable.

## #145 — `check` passes a spec that cannot decode anything

Nothing in `check.py` reads `Remaining`. The only references to it outside the
loader are in `spec.py` and `show.py`, so a `{remaining: true}` field is
entirely unconstrained:

```yaml
- {name: count,   type: {int: {bits: 8}}}
- {name: data,    type: {bytes: {size: {remaining: true}}}}
- {name: trailer, type: {int: {bits: 32}}}
```

```console
$ packeteer protocol check rem.yaml
remtest 1.0: ok
```

`data` eats the trailer and `trailer` reads an empty cursor — `need 32 bits at
bit 72, but only 0 remain` — for every input there is. The sharpest statement
of it is that the compiled protocol **encodes a message it cannot decode**,
which is the round trip packeteer exists for, in a protocol `check` called
`ok`.

`conformance.check_protocol` does catch it, but only after compiling and only
with a sample message in hand. This fault is fully determined by the spec, and
`check`'s whole job is the faults that are determined before any data exists.

**The nested case is the one that will be hit.** The rule is not *a `remaining`
field must be last in its unit* — it is **the last thing decoded in the
message**, and the difference is a whole unit away:

```yaml
  m:
    fields:
      - {name: body,    type: {unit: inner}}
      - {name: trailer, type: {int: {bits: 32}}}
  inner:
    fields:
      - {name: data, type: {bytes: {size: {remaining: true}}}}
```

`data` *is* the last field of `inner`, and `inner` is correct as long as
nothing follows it. `read_rest()` reads to the end of the **reader**, not the
end of the enclosing unit, which is what makes the nesting transparent to the
bug. Catching it means propagating terminality through every reference site: a
unit ending in a `remaining` is **terminal**, and referencing a terminal unit
from anywhere but the last position is the same refusal.

A `remaining` under a `repeat` is refused outright — the first element consumes
everything and no later one can be met.

Error, not warning. There is no input for which such a spec works, so there is
nothing for the author to weigh, unlike a `switch` with no `default`.

**kober has the same gap**, filed as
[zipline-kober#31](https://github.com/adamkjonsson/zipline-kober/issues/31).
Its `check.py` has no `Remaining` handling either, and both shapes above
reproduce there. The failure mode differs in a way worth knowing while writing
our check: kober does not encode, so it gets no exception and no broken round
trip — it renders a plausible tree in which the trailer's bytes are cited as
the preceding field's, and marks a complete message `truncated`, which `zpf`
classifies as hole-class and so declares a break the capture never had.

Both projects need the **same rule** — terminality propagated through every
reference site — reached from opposite directions. If the two checks end up
shaped differently, treat that as a sign one of them is wrong.

## #146 — `fill`

```yaml
- {name: count,     bits: 8}
- {name: data,      bytes: {size: {fill: true}}}
- {name: data_type, bits: 32}
```

**The hard part is already written.** `fill` needs a trailing-width resolver
that is total by refusal rather than approximation, and `check.py`'s
`_fixed_bits` / `_fixed_bits_of_type` (lines 667–694) is exactly that, built
for the `input: stream` framing check and used nowhere else. It already sums an
integer's `bits`, a fixed `bytes`/`string`, and a nested unit, and already
returns `None` rather than guessing for a repeat, a dynamic size or a switch.

So the work is a `Fill` in the `Size` union, a loader branch, a `check` call
into a resolver that exists, one arm in `_read_bytes`
(`_r.read_bytes(_r.remaining() - N)`), and a line in `show.py`.

**The encode side is free**, which is what separates this from every other
kober construct we have declined. A `fill` field encodes by writing its bytes,
exactly as `remaining` does; the width computation is decode-only, and the
round trip closes because decode consumed `len(value)` and encode writes
`len(value)`. No compression model, no new derivation — unlike `pointer` and
`computed`, `fill` needs nothing in the encoder at all.

**Refusals**, each naming the field responsible: a trailing width the spec does
not fix, a second `fill` in a unit, a `fill` that repeats, a trailer that is
not a whole number of bytes, and a trailing `condition`. Most fall out of using
`_fixed_bits` rather than needing their own code. kober is more generous in one
place — it resolves a `switch` width where every case and a present `default`
agree, where we return `None` — and staying conservative is fine to begin with.

## `fill` subsumes `remaining` here, and `remaining` stays anyway

This is not true in kober, and the reason it is true here is ours alone. It
should be written into the reference rather than left for a reader to work out.

kober's `remaining` is "everything left **in the run**", and its `types.md`
warns that *a run is not a packet*: under `input: stream` a run holds as many
messages as fit, so the two sizes operate on different extents and both earn
their place.

**packeteer refuses `input: stream` at compile**, so a run is always exactly
one packet payload — one message. With #145 in place, `remaining` is legal only
where the trailing width is zero, and `fill` computes the identical size there.
There is no packeteer spec where `remaining` is legal and `fill` would not do
the same job, and `fill` additionally gets the nested case right that
`remaining` gets wrong.

So `remaining` is kept for **dialect parity, not expressiveness**, and the
reference should say that plainly instead of presenting two forms as a choice
between capabilities.

**The collapse was considered and rejected.** Dropping `fill` and redefining
`remaining` to subtract a static trailer is tidier, needs no new keyword, and
breaks no spec that works today — because every spec that works today has an
empty trailer. That is exactly the trap: the same spec would **silently
mis-decode in kober**, where `remaining` still takes the trailer.
[Q3](user-defined-protocols.md#q3) named this risk in advance — "two dialects
that look identical and differ in semantics, which is worse than either alone"
— and it is the one failure mode this whole milestone exists to close. A
missing keyword fails loudly; a keyword meaning two things fails quietly.

**No checker warning for a final-position `fill`.** An earlier draft of #146
proposed one, naming `remaining` as the better spelling. Dropped: a
final-position `fill` means the same thing in both projects, so it is a style
preference and not a possible bug, and checker warnings should be spent on
things that might be wrong. A line in the reference covers it.

## The line these two share with #140

Once `condition` is implemented, **`_fixed_bits` must return `None` for a
conditional field.** One line, load bearing in two callers at once: #146's
trailer resolution, and the existing `input: stream` prefix check, which would
otherwise compute a fixed offset for a field that may not be there.

kober hit the identical wall from its side and refused a trailing `condition`
rather than approximating one. Landing #140, #146 and #145 in one release is
what puts both callers in view while that line is written.

## Ordering within the part

**#146 before #145.** #145's refusal should say what to write instead, and
`fill` is the answer; without it the message can only say *don't*. If #146
slips, #145 still lands, with a plainer message.

# Part 5 — #144, and a decision being reversed

Do this last. It is what validates Parts 1 to 3, and its second half is
cheapest once #140 exists.

## Reversing Q3

[Q3](user-defined-protocols.md#q3) offered vendoring kober's example specs as
test fixtures and **declined**:

> Vendoring kober's example specs as test fixtures was offered and **not**
> taken: the copies would drift. The compatibility claim is therefore
> documented and reasoned, not enforced in CI — worth knowing when it is
> eventually wrong.

It is now eventually wrong, and the two grounds for declining have both moved:

**"The copies would drift."** kober did it anyway, in `0.2.0`, and the answer
to drift is in *how*: pin the copies to a **released** version, and assert the
**outcome** for each spec rather than merely that it loads — including the
refusals. A test that asserts `http.yaml` is refused *for a stated reason*
fails when the reason changes, which is the drift detector the copies were
supposed to lack.

**"kober is unreleased."** The standing note in the umbrella plan reads "Do not
vendor it and do not depend on it — it is unreleased … release cadence is [the
question]". kober has released twice in four days and versions its dialect.
That rule is about the *library* — 10,500 lines, more than half of it zipline's
citation model — and it stands: we vendor no code and take no dependency. Two
YAML files under `src/tests/kober/`, pinned to `0.2.0`, are fixtures, not a
dependency.

Copies rather than a path into a sibling checkout, for kober's reason: the test
has to run in CI on a machine that has never heard of the other repository, and
a version-pinned copy is a fact about a released dialect where a live path is a
fact about whatever happens to be checked out.

## What the test asserts

After Parts 1 to 3:

- **`dns.yaml` loads and checks.** It will not *compile* — it reports `pointer`
  and `unit.params` as not supported yet — and asserting that exact set is the
  point.
- **`http.yaml` is refused**, and should not be made to load. It is `input:
  stream` and uses delimiter framing, both out of scope by design and already
  documented as such. Assert the specific refusal so it fails if the reason
  ever becomes a different one.

## The other half: keys refused as typos

We decline kober's *constructs* well. Three keys miss that treatment:

| Key | Where | What it is |
| --- | --- | --- |
| `confirm` | unit | Boolean, evaluated once the unit's fields are decoded; the unit is abandoned unless it holds |
| `reject` | unit | The same, inverted |
| `emit` | **field** | Already declined at spec and unit level via `_UNSUPPORTED_KEYS`; on a field it is an unknown-key error for a key we know about two levels up |

`confirm` and `reject` are how a wrong protocol guess becomes an honest failure
rather than a fabricated field tree — which is what the reference already tells
the reader to do with `const`, "because a port claim is weak". A guard spanning
more than one field is exactly the case `const` cannot express.

Once #140 exists, both are the same boolean expression evaluated at a different
point, and the decode side is a raise on a false `confirm`, which is what
`const` already does. **See [Q1](#q1)** — implementing them is not obviously
this milestone's work.

Field-level `emit` is one entry in a frozenset and rides along regardless.

## Release mechanics

The `.dev0` bump is [Part 0](#part-0--the-branch-and-an-honest-version).
Closing out, per CLAUDE.md and in order: rename `Unreleased` to
`## [0.13.0] - YYYY-MM-DD` and add a fresh empty one above it; drop the
`.dev0`; update the link definitions at the bottom of `CHANGELOG.md`; tag
`v0.13.0` on the merge commit, as `v0.12.0` sits on #135's; **then** close the
seven issues and
[milestone v0.13.0](https://github.com/adamkjonsson/packeteer/milestone/7).

Issues close at release, not at merge — work sits on `main` under `Unreleased`
until it ships, and closing earlier claims a delivery that has not happened.
That matters more than usual here: #143 is breaking, so a downstream project
may well be reviewing a `.devN` build while these sit merged and open.

The release is a **breaking minor**, on #143 alone. `CHANGELOG.md` needs its
`Changed` entry led with **`Breaking:`**, saying a spec using `on:` must rename
it to `dispatch:`.

The release notes carry **both strands, and must not lead with the tidier
one**. An author's spec getting shorter is the pleasant half; the half that
matters to anyone already running a compiled protocol is that two specs
`check` previously called `ok` are now refused (#145), one key that silently
did nothing now works (#140), and there is a new size form (#146). `Fixed`
gets #140 and #145; `Added` gets #141, #142, #146 and #144's declines.

Worth flagging in the notes rather than leaving to discovery: **#145 will
refuse specs that currently pass `check`.** Those specs never decoded anything,
so nothing that worked stops working — but the failure moves from run time to
check time, and an author who had not yet run their decoder will experience it
as a regression unless the notes say otherwise.

## Undecided

<a id="q1"></a>
**Q1 — Does #144 implement `confirm`/`reject`, or only decline them by name?**

Declining them by name is two entries in a frozenset and closes the "refused as
a typo" complaint completely: a kober spec using them loads and says *not
supported yet*, which is all #144's vendored-fixture test needs.

Implementing them is more attractive than it looks once #140 has landed — the
expression machinery, the boolean type check and the raise-on-false path all
exist by then — but it is a genuine feature arriving in a milestone that is
otherwise about surface, and it wants its own thinking about what a failed
`confirm` does to an enclosing unit versus what `const` does today.

**Recommendation: decline by name in 0.13.0, and file the implementation as its
own issue.** The argument for implementing gets *stronger* after #140 ships
rather than weaker, so nothing is lost by waiting.

**The consistency objection, and the answer to it.** "It keeps this release one
coherent theme" was the original reason here, and #146 spent it — a size form
is a feature too, and it is in. So the line cannot be *no features in a surface
release*; it has to be drawn somewhere defensible.

Where it is drawn: **`fill` needs no new failure semantics and `confirm` does.**
`fill` is a fourth entry in a list the reference already publishes — a length
comes from a constant, an earlier field, or the rest of the message — and its
one hard part is a resolver we already have. `confirm` and `reject` abandon a
*unit* when a predicate fails, and that wants a decision we have not made:
whether a failed guard raises, as `const` does today, or produces something
weaker, and what either means for an enclosing unit that was midway through
decoding. kober had the vocabulary for it already (`undecodable` is a verdict
its format defines); we would be inventing one.

That is a real distinction and not a post-hoc one, but it is worth writing down
that the theme argument no longer does any work here.

Does not block #143, #141, #142, #146 or #145. Wants an answer before #144
starts.
