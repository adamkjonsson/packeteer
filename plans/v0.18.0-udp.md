# Plan — v0.18.0: UDP as a conversation, a tunnel the caller seals, and two lengths

*Written 2026-10-11.*

*Status: **in progress**. #194, #195 and #196 are done, and the version is
`0.18.0.dev0`; `.dev1` is next. [Q2](#q2) and [Q3](#q3) are settled as
recommended. [Q1](#q1), [Q4](#q4) and [Q5](#q5) are open, each with a
recommendation. See [Undecided](#undecided).*

*Release gate: 0.18.0 is not cut until zipline-kober has evaluated the
solution to each of its issues on a `.dev` build. See
[The release gate](#the-release-gate).*

Six issues. Four of them come from one downstream need, and two are left over
from 0.17.0.

**The UDP strand**: #194, #195, #196, #197. zipline-kober is building a
worked example of decoding an encrypted tunnel: WireGuard, with known keys
and cleartexts, under impairments the test author chooses. Working out how
to generate that stream turned up three things packeteer's UDP path cannot
do, and a fourth it should be able to:

```console
$ packeteer stream --payload dns --protocol udp --protocol-messages dns.json \
    --client-ip 10.0.0.2 --server-ip 10.0.0.1 --packets 40 --packet-loss 0.5 --seed 5 --pcap d.pcap
Wrote 40 packet(s) to d.pcap (link type: 1)         # #194: 40 of 40, loss ignored
# every packet_metadata.direction is "c2s", responses included   # #195
# --gap-jitter never reorders; duplication has no flag            # #196
# sealing in wire order needs the caller's code                   # #197
```

Each issue builds on the one before it. #194 gives a UDP stream impairments
at all. #195 gives it two directions. #196 adds the two impairments a
datagram protocol is built to survive, and they need directions to be
correct. #197 wraps any stream in a tunnel whose payload the caller computes,
and its outer datagrams use all three.

**The leftovers**: #192 and #172.

- **#192** is #191's fault in DNS. `sanitise` changes a DNS-over-TCP
  message's length, and the sequence numbers after it go wrong.
  `test_sanitise_lengths.py` leaves DNS out of its generated streams, and a
  comment there says this is why. #191's invariant test already covers the
  rest.
- **#172** is 0.17.0's Q3. An `http` section cannot keep the order of
  repeated header names across other names. It changes the shape of a
  packet-spec key, so it is **breaking**.

## The order, and why

```
#194 → #195 → #196 → .dev1
     → #197 → .dev2
     → #192 → #172 → .dev3 → docs sweep → release
```

- **#194 first.** It is a bug that is shipping now. zipline-kober's "lossy
  DNS stream" has never been lossy. It also gives `generate_udp_stream` the
  impairment hook that #196 and #197 extend.
- **#195 before #196.** Reordering should only let a datagram overtake others
  going the *same way* ([Q3](#q3)). Written after #195, the reorder pass
  takes direction into account from the start, so it is never written twice.
- **One `.dev1` for the three**, because zipline-kober reviews them from the
  same seat: an impaired, two-way DNS stream over UDP.
- **#197 on its own `.dev2`.** It is the largest item, it is new API surface,
  and it is the one zipline-kober's WireGuard example is waiting on. Its
  outer datagrams reuse #194–#196 unchanged, which is why it comes after them.
- **#192 and #172 last.** They share no code with the UDP strand, and no
  downstream user is waiting on them. #172 goes last because it is the
  milestone's one breaking change to a packet-spec key, and [Q1](#q1) settles
  its shape.

## The release gate

This milestone is one part of joint work across four projects: packeteer,
python-zipline, python-zipline-wire and zipline-kober. **They must work
together**, so a fix that passes packeteer's own tests is not finished until
the project that asked for it has checked it in place.

- **Every issue's solution is evaluated by zipline-kober** on a `.dev` build
  before 0.18.0 is created. The `.dev1`–`.dev3` cuts above are those builds,
  and each one is published for that review, as 0.17.0's `.devN` builds were.
- **What a review finds goes into this milestone** as a new issue and a new
  line in the order above. It does not wait for 0.19.0. 0.17.0 grew from 6
  issues to 22 this way, so the sizing below is a floor.
- **The release steps start only after the last `.dev` is reviewed with no
  comments.** That covers renaming `Unreleased`, dropping `.devN`, and
  tagging. Per the project's rule, issues close at release, not at merge.
- The status table records, for each issue, the `.dev` build it was
  evaluated on.

**Sizing.** #194 is half a day, most of it the refusal paths and the flag
table. #195 is a day: a new API seam, `messages` on `UDPStreamConfig`, and
the direction spelling. #196 is a day. #197 is three to four days: the
module, the CLI, the loading of the wrapper module, and the semantics tests.
#192 is two days. Walking the DNS wire format to rewrite inside `raw` is most
of it. #172 is one to two days, depending on [Q1](#q1). The sweep is half a
day.

# Part 1: #194, UDP impairments that apply

## The bug

`_build_stream_config` gives UDP only `UDPStreamConfig(gap_jitter=…, seed=…)`
([__main__.py:1825](../src/packeteer/__main__.py#L1825)).
`generate_udp_stream` never calls `apply_datagram_impairments`, which already
does the right thing: loss and corruption, with the TCP-only passes ignored.
Only `payloads/vpn.py` calls it. The silence also applies to everything that
reaches `generate_udp_stream` through the CLI: random payloads, built-in
protocols, compiled protocols, and `--sessions N` through
`generate_session_mix`.

**SCTP has the same fault, and the issue does not name it.**
`SCTPStreamConfig` takes no impairment at all, and
[stream.md](../docs/cli/stream.md) says the TCP-only flags are *"silently
ignored for `--protocol udp` and `--protocol sctp`"*. The docs admit it, but
it is still #83's failure mode, and #137 and #169 have since established that
packeteer refuses a flag rather than ignore it. This issue fixes SCTP as
well, by refusing the flags there. It does not implement SCTP impairments.

## The fix

- **`UDPStreamConfig.impairments: ImpairmentConfig | None = None`**, the same
  name and type as `VPNConfig.impairments` and `HTTPRestConfig.impairments`.
  `generate_udp_stream` applies `apply_datagram_impairments` after building
  the datagrams and before middlebox fragmentation. A lost datagram is never
  fragmented, and a corrupted one is fragmented with its corruption.
- **It uses the stream's own `rng`**, after the size and jitter draws. A
  config with no impairments draws nothing, so every existing seeded UDP
  capture reproduces byte for byte.
- **`generate_session_mix` needs nothing.** It `dataclasses.replace`s the
  config per session, so `impairments` rides along, and each session
  gets its own seed.
- **The CLI passes `_impairments_from_args(args)` on UDP**, as it does on
  TCP.
- **A TCP-only flag is refused on UDP and SCTP**, naming the flags. On SCTP,
  `--packet-loss` and `--payload-corruption` are refused too, because SCTP
  applies none. `--payload vpn` currently *warns* and drops the flags. It
  changes to the same refusal, so the rule is the same on every path. That
  is **breaking** for a command line that relied on the warning, and the
  changelog says so.

## Docs

- [stream.md](../docs/cli/stream.md): *TCP-only arguments* splits into
  *Impairments* (a table with a column for each of TCP, UDP and SCTP) and the
  TCP-only rest. The words *"Silently ignored"* go.
- `--packet-loss` help: the duplicate-ACK sentence is TCP's, and the help
  says so.
- `UDPStreamConfig`'s docstring, and the module docstring of `udp_stream.py`.

## Tests

The issue's tests, for a random payload, a compiled protocol and `dns`:

- At `--packet-loss 0.5 --seed N`, fewer datagrams than `--packets` are
  written.
- At `--payload-corruption 1.0`, every data datagram differs from the clean
  run in its last byte, and nowhere else.

Also:

- A UDP run with no impairment flags is byte-identical to the same run
  before the change. The seeded capture is pinned by hash.
- `--sessions 3 --protocol udp --packet-loss 0.5` loses datagrams in every
  session.
- Each TCP-only flag on UDP is refused, and so is each impairment flag on
  SCTP. `--payload vpn --server-rst 0.5` is refused, where it used to warn.
- At the API: `generate_udp_stream(config=UDPStreamConfig(impairments=…))`.

## Changelog

`Fixed`: `stream --protocol udp` applies `--packet-loss` and
`--payload-corruption`. `Added`: `UDPStreamConfig.impairments`. `Changed`:
**Breaking:** a TCP-only impairment flag on a UDP or SCTP stream, and any
impairment flag on SCTP, is refused instead of being ignored. `--payload vpn`
now refuses what it used to warn about. Drop the flag. `Documentation`: the
flag table in `stream.md`.

### What #194 corrected

**There were four TCP-only flags, not three.** `--retransmit-lost` was missing
from `_TCP_ONLY_ANOMALY_FLAGS`, so even `--payload vpn`'s warning did not
mention it. It is in the refused set now.

**A setting of an option is not refused.** `--retransmission-timeout`,
`--rst-propagation-delay` and `--stray-timing-window` change nothing unless
their option is given, and that option is refused already. Refusing them as
well would only add noise. `stream.md` marks them **—**.

**The TCP header options are not impairments, and still have no effect on
UDP or SCTP.** `--window`, `--psh-probability` and `--no-tcp-options` keep
their *TCP-only arguments* table. The docs now say "no effect" where they
said "silently ignored". Refusing them would be the same principle applied
to a different set of flags. If it is wanted, it gets its own issue.

**One refusal for every path.** `_refuse_unapplied_anomalies(args, protocol)`
runs in `_cmd_stream` before the `http`/`vpn` dispatch. `--payload vpn` goes
to the UDP rule whatever `--protocol` says, because it is UDP. A flag counts
as given when its value is not zero, as the vpn check already did, so an
explicit `--server-rst 0` asks for nothing and is accepted.

**The hash pin was checked against the old code**, not just written down.
The same seeded call, with jitter, run from a worktree at `758f35e`, gives
the same SHA-256. `test_a_seeded_clean_stream_is_unchanged` holds it.

**`generate_session_mix` needed nothing**, as planned.
`test_every_session_is_impaired` confirms it.

# Part 2: #195, a UDP datagram's direction comes from its message

## The bug

`generate_udp_stream` labels every datagram `c2s`
([udp_stream.py:290](../src/packeteer/generate/udp_stream.py#L290)), and
calls `payload_fn(i, "c2s")`. The direction is usually in the input already,
in `packet_metadata.direction` of a parsed capture. `_sections_in`
([app/__init__.py:133](../src/packeteer/app/__init__.py#L133)) throws it away
when it pulls the section out of the packet.

**The TCP stream has the same fault.** `_data_chunks` also calls
`payload_fn(i, "c2s")`, so a DNS-over-TCP response travels from the client
too. It is out of scope here ([Q2](#q2)). Sending data from the server means
the emit loop has to send server data and client ACKs, which is a change to
the connection model, not to a payload seam.

## The design

`payload_fn(index, direction) -> bytes` cannot carry a direction *out*: the
generator chooses the direction and asks for bytes. Nothing in the issue
needs the generator to choose. The messages know their own direction, so the
seam is a list of messages, as `HTTPRestConfig.messages` already is for HTTP
(#169).

- **`app.protocol_conversation(proto, messages, transport) -> list[AppMessage]`**,
  beside `protocol_messages` and `protocol_payload_fn`, with the same
  signature. Each `AppMessage` (from `generate/payloads/base.py`, which
  already has `direction`, `data` and `label`) carries the encoded bytes and
  the element's direction. `protocol_payload_fn` becomes a thin wrapper over
  it, and its behaviour does not change.
- **`UDPStreamConfig.messages: Sequence[AppMessage] | None`**. When it is
  set, datagram `i` is `messages[i % len(messages)]`, sent in its direction:
  for `s2c` the addresses, ports and MACs are swapped. Cycling, because every
  `--payload` cycles (0.17.0's Q1). It overrides `payload_fn`, and setting
  both is a `ValueError`. Labels stay `DATA[i]`, so impairment labels
  (`CORRUPT[i]`) read as they do today.
- **Where a direction comes from**, per element:
  - a whole packet uses `packet_metadata.direction`. If that is missing, the
    element is `c2s`, as today;
  - a wrapped section carries a `direction` key beside the section:
    `{"dns": {...}, "direction": "s2c"}` ([Q2](#q2));
  - a bare section is `c2s`, as today.

  A direction that is not `c2s` or `s2c` is refused with the element's
  index.
- **Found while planning: the wrapped form ignores its other keys.**
  `_sections_in` takes `element[proto.name]` and drops everything beside it,
  so `{"dns": {...}, "drection": "s2c"}` is accepted in silence. That is
  #137's failure mode again. The wrapped form now refuses any key other than
  the protocol's name and `direction`.
- **The CLI** uses `messages` for `--protocol udp`, and stays on `payload_fn`
  for TCP. On TCP, an element that says `s2c` is refused, naming
  [Q2](#q2)'s follow-up issue. That is better than sending it the wrong way
  in silence.

`UDPSession`/`render_udp_session` already swap endpoints for `s2c`. The
datagram builder should share that code with them rather than copy it.

## Tests

- **The issue's test**: a parsed DNS capture with queries and responses is
  replayed through `stream --protocol udp --payload dns --protocol-messages`.
  Every response leaves from the server's address and port, and `parse` of
  the result gives back the same direction sequence.
- A wrapped section with `"direction": "s2c"`. A bare section stays `c2s`. A
  misspelt sibling key is refused, and so is a bad direction.
- Impairments still apply per datagram, in both directions.
- The same input on `--protocol tcp` with an `s2c` element is refused.
- `protocol_payload_fn` output is unchanged for every existing test.

## Changelog

`Added`: `UDPStreamConfig.messages`, `app.protocol_conversation`, and the
`direction` key in the wrapped form. `Changed`: a UDP stream replayed from a
parsed capture keeps each datagram's direction. Output changes for the same
command line, but the old output was wrong. `Fixed`: an unknown key beside a
wrapped section is refused rather than ignored.

### What #195 corrected

**`parse` writes no direction.** The issue and this plan both say the packet
spec that `parse` writes carries `packet_metadata.direction`. Only
`stream --json` writes it. Read as planned, a parsed capture would have
replayed all `c2s` again. So a packet without a direction is now read from
its addresses, at replay time, and `parse` output is unchanged:

- the side on one of the protocol's `ports` is the server;
- when neither side is, or both are, the first sender in the flow is the
  client. That is counted over every packet, so for TCP it is whoever sent
  the SYN.

Changing `parse` to write a direction would affect what every downstream
project reads. It is not needed here.

**`protocol_payload_fn` refuses a reply at the API, not only the CLI on
TCP.** A `payload_fn` sends everything from the client, over any transport,
so the API is where the refusal belongs. The message names
`protocol_conversation` for UDP and #198 for TCP. This is **breaking** for an
API caller replaying a parsed capture with replies through it. The
changelog says so.

**`protocol_messages` refuses a `"direction"` key.** Its one caller,
`--payload http`, takes a message's direction from its `type`. A
`"direction"` there would be read by nothing. The walker is shared, so the
refusal is a flag on it.

**`AppMessage` labels are `dns[3]`**, so `protocol_conversation`'s list
renders as it is through `render_udp_session`. The stream generator ignores
the label and keeps `DATA[i]`, as planned.

**The endpoint swap is shared.** `_build_directed_udp_packet` in
`udp_stream.py` is what both `generate_udp_stream` and `UDPSession.build`
call.

**Found while testing, and not this issue: `stream --json` drops a decoded
app section.** `_stream_to_json` copies only `pkt.payload`, so a DNS
datagram's JSON has no `dns` key and no payload at all. That is the same on
`main` at `27b05f7`. It needs an issue of its own.

**Tests** are `test_udp_directions.py`: each source of a direction, the
inference both ways, every refusal, the generator's swap, and the issue's
acceptance test. A DNS conversation is streamed, parsed, and replayed from
the parse output, and every response leaves from port 53. The same capture
on TCP is refused, naming #198.

# Part 3: #196, reordering and duplication

## The bug

- **`--gap-jitter` never reorders a UDP stream.** Each gap is
  `gap + uniform(0, jitter)` added to a running cursor, so timestamps only
  increase, and the re-sort after it changes nothing. The help says *"packets
  are re-sorted by timestamp"*, which implies reordering that cannot happen.
- **Duplication is API only.** `ImpairmentConfig.duplicate_probability`
  exists, `apply_impairments` honours it on TCP, but no CLI flag sets it, and
  `apply_datagram_impairments` does not read it.

## The fix

Two new fields on `ImpairmentConfig`, and two passes in
`apply_datagram_impairments`. The new passes run **after** loss and
corruption, so a seeded capture that uses only those two reproduces as it
did after #194.

- **`reorder_probability: float = 0.0`, `reorder_depth: int = 3`.** With
  probability P a datagram is held back and delivered after the next K
  datagrams **going the same way** ([Q3](#q3)), where K is uniform in
  `1..reorder_depth`. Its timestamp moves to just after the K-th datagram's
  (`_alloc_usec`), so the capture order is the delivery order. A datagram
  with fewer than K behind it goes to the end of its direction. The label is
  `_derive_label("REORDER", …)`.
- **`duplicate_probability`**, read by the datagram pass. It reuses
  `_apply_duplication` as it stands: a verbatim copy 1 µs later, labelled
  `DUP[…]`, and it runs last because it is what the capture point saw. On
  UDP a network duplicate and a capture-point duplicate look the same (there
  is no TSval to tell them apart), so one pass serves both. Its type hints
  widen from `TCPStreamPacket` to any stream packet.
- **CLI**: `--reorder PROB`, `--reorder-depth K`, and `--duplicate PROB`,
  with INI keys in `_STREAM_PARAMS` and `stream_config_template`.
  `--duplicate` applies to **TCP too**, since `apply_impairments` already
  honours it. `--reorder` is datagram-only. TCP refuses it with the #194
  refusal, because a reordered segment changes what the receiver
  acknowledges, and that is a separate feature.
- **`--gap-jitter`'s help and `UDPStreamConfig.gap_jitter`'s docstring** say
  what the option does: it lengthens gaps, and on a one-way flow nothing
  overtakes anything. To reorder, use `--reorder`.
- `ImpairmentConfig.any_post_pass` learns `reorder_probability`, so
  `_impairments_from_args` does not return `None` for a reorder-only
  command line.

## Tests

The issue's tests:

- At `--reorder 0.3 --seed N`, the payload order in the pcap is a
  non-identity permutation of the messages given, with the same multiset.
- At `--duplicate 0.3`, some payloads appear twice, and none is missing.

Also:

- Reordering never lets a datagram overtake one going the other way.
- No datagram moves more than `reorder_depth` places within its direction.
- Timestamps are strictly increasing in the output.
- `--duplicate` on TCP gives `DUP[…]` copies with identical bytes.
- `--reorder` on TCP is refused.
- With both flags at 0, the RNG draws nothing, so the hash pin from #194
  still holds.

## Changelog

`Added`: `--reorder`, `--reorder-depth`, `--duplicate`, and the matching
`ImpairmentConfig` fields. `apply_datagram_impairments` reads
`duplicate_probability`. `Fixed`: `--gap-jitter`'s help no longer suggests it
reorders.

### What #196 corrected

**"Delivered after the next K" is a queue, not a timestamp.** The plan
moved a held datagram's timestamp to just after the *K*-th datagram's
original one. When that one is itself held, nothing actually overtakes the
first, and the label would say `REORDER` about a datagram still in place.
`_reorder_datagrams` instead walks the flow. A held datagram waits for *K*
**deliveries** in its direction and follows the *K*-th, so it is overtaken
by exactly *K*. If the flow ends first, it follows the last delivery, and if
nothing was delivered after it, it stays where it was and keeps its `DATA`
label. So `--reorder 1.0` holds everything, delivers nothing past anything,
and gives the clean stream: a test pins that.

**Q3's rule is "K counts only its own direction"**, which is what the
implementation does. A held request still lands after replies that were
emitted in the meantime, because with a fixed list of messages, delaying a
request does not delay the reply that follows it in the list. That is a
property of replaying a list, not of reordering, and it is the same for
loss.

**`--retransmit-lost` did nothing on a plain TCP stream.** It was found
while wiring `--duplicate` into the same function. `_build_stream_config`
built `TCPStreamConfig` field by field and left out both
`retransmit_lost` and `duplicate_probability`, so only `--payload http`,
which goes through `_impairments_from_args`, ever saw them. The same seeded
command gave the same 47 packets with or without the flag. It is fixed here
because it is the same fault as #194, in the line this issue was already
changing, and the changelog lists it under `Fixed`.

**#194 missed the INI template.** `stream.ini.template` still said the
impairment options are "silently ignored for udp and sctp" and that `vpn`
warns, and it tagged `packet_loss` and `payload_corruption_probability`
"[TCP only]". It is corrected here, with entries for the three new keys.

**`--gap-jitter` means different things per protocol, and is documented, not
changed.** On TCP it is a per-packet capture delay that *can* overtake. On
UDP and SCTP it lengthens gaps and cannot. Making UDP's match TCP's would
change every seeded UDP capture, and `--reorder` now covers the need.

**Reorder runs before duplication**, so a held datagram's copy is captured
after the reordered original. Both run after loss and corruption, so
#194's hash pin still holds, and so does a seeded capture that uses only
those two.

**`_apply_duplication` serves UDP unchanged.** Only its type hints widened,
to a `TypeVar` over both stream packet types.

# Part 4: #197, a UDP tunnel the caller seals

## What it is

The generated stream's packets (IP only, no layer 2, as for GRE and
IP-in-IP) become the payloads of outer UDP datagrams between two tunnel
endpoints. The outer payload comes from the caller's code. packeteer does no
cryptography, and this issue does not change that: the caller's object does
the sealing.

## Why it is not an encap

Every `StreamEncap` is applied at **build time**, packet by packet, inside
the generator's emit loop, before the impairment passes have run. #197's
first rule is that the wrapper sees each inner packet **once per time it is
sent, in wire order**: a retransmission again, a lost packet never. Only a
pass over the *finished, impaired, time-sorted* inner stream can do that. It
is a stream-to-stream function, not an encap descriptor:

```python
class TunnelWrapper(Protocol):
    def wrap(self, inner: bytes, direction: str, timestamp: float
             ) -> Sequence[tuple[str, bytes]]: ...

@dataclass
class UDPTunnel:
    src_ip: str
    dst_ip: str
    port: int
    wrapper: TunnelWrapper
    src_port: int | None = None      # None → port, as WireGuard runs
    ttl: int = 64

def tunnel_stream(
    stream: TCPStream | UDPStream | SCTPStream | CombinedStream,
    tunnel: UDPTunnel,
    *,
    include_ethernet: bool = True,
    client_mac: str = …, server_mac: str = …,
    encap: EncapSpec = None,                 # layer-2 tags on the outer packet only
    impairments: ImpairmentConfig | None = None,
    seed: int | None = None,
) -> UDPStream
```

The issue names it `UDPTunnelEncap`. [Q4](#q4) asks whether to keep a name
that suggests it goes in `encap=`, which it cannot. The recommendation is
`UDPTunnel` and `tunnel_stream`. They live in a new module,
`generate/udp_tunnel.py`, re-exported from `packeteer.generate`.

## The semantics, from the issue's four points

1. **Wire order, after the inner flow's impairments.** The inner stream is
   generated with `include_ethernet=False` and no encap, then sorted by
   timestamp, and `wrap` is called once per packet. A lost inner packet is
   not in the stream, and a retransmission is. Stateful wrappers (counters,
   a rekey after N packets) are correct by construction.
   - **Inner `--duplicate` is refused with a tunnel.** It is the capture
     point seeing a packet twice, and the capture point is outside the
     tunnel, so the wrapper would seal a packet the sender sent once. Use
     the outer duplicate instead.
   - Inner `--mtu` fragments are wrapped one by one, as a real tunnel does
     with fragments it receives.
2. **Outer impairments apply after wrapping**, through
   `apply_datagram_impairments`, so corruption lands on the sealed bytes and
   breaks an authentication tag. Losing an outer datagram loses everything it
   carried. Inner and outer impairments are separate questions, so they get
   separate flags ([Q4](#q4)).
3. **Direction maps to the endpoints.** A returned `c2s` travels
   `src_ip → dst_ip`, and `s2c` travels the reverse. The direction comes from
   what `wrap` *returns*, not from the inner packet, so a handshake reply
   from the far endpoint can be emitted while sealing a `c2s` packet.
4. **Seeded and reproducible.** Outer impairments draw from an RNG of their
   own, derived from the seed, so adding `--tunnel-packet-loss` never changes
   the inner flow. The wrapper gets nothing random from packeteer.

**Timestamps.** The first datagram returned by `wrap` takes the inner
packet's timestamp, and each further one takes the next free microsecond
(`_alloc_usec`). An empty return is allowed: the wrapper swallowed the
packet, for example while it buffers a handshake.

**`timestamp` is in `wrap`'s signature**, which the issue's version does not
have ([Q4](#q4)). A WireGuard model needs it to rekey after a time, or to
emit a keepalive after an idle period, as well as after N packets. Adding it
later would break every wrapper that had been written by then.

**Labels.** Each outer datagram is `TUNNEL[<inner label>]`, and further ones
from the same call get `TUNNEL[<inner label>]+1`, `+2`. Outer impairments
derive their labels from these as usual.

## The CLI

```console
packeteer stream --protocol udp --payload dns --protocol-messages dns.json \
    --udp-tunnel 198.51.100.7 203.0.113.9 --tunnel-port 51820 \
    --tunnel-module wg_seal.py --tunnel-arg keylog=keys.json \
    --tunnel-packet-loss 0.05 --tunnel-corruption 0.02 --seed 7 --pcap wg.pcap
```

- `--udp-tunnel SRC DST` is one more tunnel in `_parse_stream_encap`'s
  mutually exclusive set. Layer-2 tags (`--vlan`, `--mpls`, …) apply to the
  outer packet. Combining it with another tunnel is refused, as two tunnels
  are today.
- `--tunnel-port PORT` (required with `--udp-tunnel`) and `--tunnel-src-port`.
- `--tunnel-module FILE` (required) and `--tunnel-arg KEY=VALUE`
  (repeatable). The module defines
  `make_wrapper(args: dict[str, str]) -> TunnelWrapper`. **A module is code
  and is run as code**, as with `--load-protocol`, and the help says so.
  Loading lives in the API, as
  `udp_tunnel.load_wrapper(path, args) -> TunnelWrapper`, so `__main__.py`
  only calls it. A missing `make_wrapper`, or a result without a `wrap`
  method, is refused, naming the file.
- `--tunnel-packet-loss`, `--tunnel-corruption`, `--tunnel-reorder`,
  `--tunnel-reorder-depth`, `--tunnel-duplicate`: #194–#196's datagram
  impairments on the outer flow.
- `--json` works unchanged: the outer datagrams are parsed as whatever claims
  the port, which is usually a raw payload.
- **Works with every payload**, `http` and `vpn` included, and with
  `--sessions N`: one tunnel carries every session, as a real VPN does.

## Example and docs

- `examples/udp_tunnel/xor_seal.py`: a toy wrapper with a per-direction
  counter, a two-message "handshake" on the first call, and a rekey every N
  packets. It uses no real cryptography, says so, and the tests run it.
- A guide page, *Tunnelling through your own code*, that walks through the
  example and the four semantics.
- `stream.md`: a new section and the flags. The API reference gets
  `udp_tunnel`.

## Tests

- **Wire order**: the wrapper records every call. With inner
  `--packet-loss 0.3 --retransmit-lost`, every retransmission is wrapped
  again, no lost-and-never-retransmitted segment is wrapped, and the calls
  arrive in timestamp order.
- **Outer corruption** changes only sealed bytes: unwrapping with the toy
  wrapper's inverse fails exactly for the `CORRUPT[…]` datagrams.
- **Direction**: an inner `s2c` packet goes `dst_ip → src_ip`. A wrapper that
  returns a handshake reply in the other direction has it sent that way.
- **Reproducible**: the same seed gives a byte-identical capture. Adding
  `--tunnel-packet-loss` leaves the wrapper's call sequence unchanged.
- Several datagrams per call get increasing timestamps. An empty return
  sends nothing.
- Refusals: inner `--duplicate`, a second tunnel, a missing `--tunnel-port`,
  and a module without `make_wrapper`.
- `--payload http` and `--sessions 3` through a tunnel.
- At the API, with no CLI: `tunnel_stream(generate_tcp_stream(…), UDPTunnel(…))`.

## Changelog

`Added`: `UDPTunnel`, `TunnelWrapper`, `tunnel_stream`, `load_wrapper`; the
`--udp-tunnel`, `--tunnel-*` flags; the example and the guide page.

# Part 5: #192, DNS keeps its length under `sanitise`

## The bug

`_Replacer.dns_label` maps each distinct label to `label{N}`
([sanitise.py:415](../src/packeteer/sanitise.py#L415)), whose length is
rarely the original's. Over TCP the segment changes size and every sequence
number after it is wrong. There is a second cause, independent of the first:
`app/dns.sanitise` drops `raw` whenever it changes anything (#130), and the
rebuild compresses names packeteer's way. For 234 of 516 real pointers that
is not the sender's way, so the length can change even when every label
keeps its own.

## Decided by #191's reasoning: same length, sender's compression ([Q5](#q5))

#191 chose "redact at the same length" over "renumber `seq` and `ack`", and
the same reasons apply here. Renumbering is flow-aware code next to the
reassembly that #187 ruled out of scope, and it would also have to rewrite
SACK blocks. So:

- **Same-length synthetic labels.** For a label of length *n*, the *k*-th
  distinct one (case-folded, as now) becomes *k* in lower-case base 36,
  zero-padded to *n*. The mapping stays consistent and injective while
  *k* < 36ⁿ. Only one-character labels can run out (36). When they do,
  further ones wrap around and a `sanitise` warning says that distinct
  one-character labels now share a replacement. The `labelN` spelling goes
  away. It is user-visible: `docs/cli/sanitise.md`,
  `docs/guide/sanitising.md` and `docs/internals/sanitiser.md` all show it.
- **Rewrite inside `raw`, keep `raw`**, as #184 did for HTTP headers. A walk
  over the DNS wire format (header, questions, RRs, and the names inside
  CNAME, NS, PTR, MX and SOA rdata, which is the set `_sanitise_dns_rdata`
  already covers) replaces each label's bytes in place, and each A/AAAA
  address with `r.ip`. It zeroes the ID when `dns_ids` is set. Pointers are
  left alone: lengths do not change, so their targets do not move. The
  decoded fields are redacted the same way, so `raw` and the fields agree.
- **Fallback.** A message the walk cannot follow, such as one that is
  truncated or has a pointer loop, has `raw` dropped as today and is rebuilt
  from the redacted fields. Its length can then change. As with #184's HTTP
  fallback, this is the rare malformed case, and it is documented.
- DHCP's hostname option uses `dns_label` too, and gets the same-length
  mapping for free. It is UDP, but a fixed length is better there too.

## Tests

- **The issue's case**: 6 DNS-over-TCP segments carrying
  `www.shop.example.com` keep 40 bytes each, and no segment overlaps the one
  before it.
- **The invariant**: `test_sanitise_lengths.py` adds DNS over TCP to its
  generated streams, real names included. The comment that excludes it goes.
  The real corpus already runs through it.
- `raw` survives `sanitise`, and contains no original label. Its pointers
  still resolve. `parse` of the output decodes the same names as the fields
  say.
- The 37th one-character label warns.
- A compressed message whose sender compressed differently from packeteer
  keeps its exact length.

## Changelog

`Fixed`: `sanitise` keeps a DNS message's length, so a DNS-over-TCP stream
keeps its sequence numbers. `Changed`: a redacted DNS label is a same-length
base-36 string instead of `labelN`, and a DNS section keeps its `raw`, which
is redacted in place.

# Part 6: #172, headers in order, names repeated ([Q1](#q1))

## Where 0.17.0 left it

0.17.0 covered more of this issue than the issue describes:

- **Input**: a header's value may be a list (#181), one line per item. So
  `"Transfer-Encoding": ["gzip", "chunked"]` already sends two lines.
- **Round trip**: `raw` (#178) carries a captured message's exact bytes,
  whatever its header order.
- **Parse**: a repeated `Set-Cookie` becomes a list, and any other repeated
  name is folded to `a, b`.

**What remains is order across names.** `A: 1`, `B: 2`, `A: 3` cannot be
written without `raw`, and comes out of `parse` as `{"A": "1, 3", "B": "2"}`.
It also matters for `sanitise`'s #184 fallback, which rebuilds from the
fields and regroups.

## Recommended shape ([Q1](#q1))

- **Section, input**: `headers` accepts an array of `[name, value]` pairs,
  in order, **and** the object form as today. The object form stays because
  every hand-written spec and every 0.17 `parse` output uses it.
- **Section, output**: `parse` and `stream --json` write the pairs form,
  always. One output shape, so consumers have one thing to read. This is the
  **breaking** half: a reader of `parse` output that does
  `section["headers"]["Host"]` breaks.
- **Message classes**: `HTTPRequest.headers`/`HTTPResponse.headers` become an
  `HTTPHeaders`. It is an ordered multi-map in the style of
  `email.message.Message`:
  - `items()` gives the pairs;
  - `get_all(name)` gives every value;
  - `[name]` and `get(name)` are case-insensitive and return the values
    joined with `, `, except `Set-Cookie`, which returns its first value;
  - `add(name, value)` appends a line, and `[name] = v` replaces every line
    with that name.

  It is built from a `dict` (with list values) or from pairs, so
  `HTTPRequest(headers={"Host": …})` keeps working. That keeps the
  Python-side break small: code that indexes, iterates names, or builds from
  a dict still works, and code that checks `isinstance(headers, dict)` or
  stores lists into it does not.
- **Parse** keeps every line as a pair, folding nothing, so `raw` is needed
  only for byte-level differences: spacing after the colon, a missing reason
  phrase. Fewer messages need `raw`.
- **Internal users** move to the new type: `_is_chunked`, `_sanitise_http`,
  the `Content-Length` lookup in `parse_http`, the encoder, the REST
  generator's header builders, and `_headers` in `app/http.py`.

## Tests

- `A: 1`, `B: 2`, `A: 3` round-trips through section → capture → `parse` →
  section, without `raw`.
- The object form still loads, with list values too. A malformed pair (not
  two strings, or an empty name) is refused, naming its index.
- `HTTPHeaders`: case-insensitive lookup, `get_all`, built from a dict and
  from pairs, `Set-Cookie`'s first value.
- `sanitise --http-headers` on a pairs section redacts every line of a
  sensitive name, at the same length (#191).
- The #184 fallback no longer regroups.
- `test_http_raw.py`'s expectations: messages that needed `raw` only for
  order now do not.

## Changelog

`Changed`: **Breaking:** an `http` section's `headers` is written as an array
of `[name, value]` pairs. The object form is still accepted on input. Readers
of `parse` output must read pairs. **Breaking:** `HTTPRequest.headers` and
`HTTPResponse.headers` are an `HTTPHeaders`. Indexing and building from a
dict still work. `Added`: `HTTPHeaders`. `Fixed`: a repeated header name
keeps its lines and their order through `parse`.

# Undecided

| Q | About | Recommendation |
|---|-------|----------------|
| [Q1](#q1) | #172: the `headers` shape | Pairs out, both in; `HTTPHeaders` multi-map in the classes |
| [Q2](#q2) | #195: spelling an `s2c` bare section; TCP | **Settled as recommended**: sibling `direction` key; TCP is #198 |
| [Q3](#q3) | #196: what a reordered datagram may overtake | **Settled as recommended**: same direction only |
| [Q4](#q4) | #197: names, `wrap`'s signature, outer flags | `UDPTunnel` + `tunnel_stream`; `timestamp` in `wrap`; separate `--tunnel-*` flags |
| [Q5](#q5) | #192: same length vs renumbering | Same length, rewriting inside `raw` |

### <a name="q1"></a>Q1: the `headers` shape

The options are (a) pairs out and both shapes in, (b) pairs only, in and out,
or (c) keep the object, and fold or list as today, leaving order to `raw`.
(c) is not breaking, but it does not fix the issue. (b) breaks every
hand-written spec for no gain. *Recommendation: (a)*, with `HTTPHeaders`
rather than `list[tuple[str, str]]` in the classes, so Python callers keep
`headers["Host"]`.

### <a name="q2"></a>Q2: spelling an `s2c` bare section, and TCP

A `direction` key *inside* the section would collide with #137's refusal of
keys a protocol does not read, and with a compiled protocol's field named
`direction`. Beside it, in the wrapped form `{"dns": {...}, "direction":
"s2c"}`, it collides with nothing, and the wrapped form already exists.
*Recommendation: beside it.* Separately, DNS over TCP sends its replies
client to server for the same reason. *Recommendation: file it as its own
issue*, because it changes the TCP emit loop, and refuse `s2c` on TCP until
then.

### <a name="q3"></a>Q3: what a reordered datagram may overtake

Reordering happens on one path, so a datagram can overtake others going the
same way. Across directions, "overtaking" a reply means arriving before the
request that caused it. That is causally impossible at the server, and
misleading in a capture taken at one point. *Recommendation: same direction
only.*

### <a name="q4"></a>Q4: #197's names, `wrap`'s signature, and the outer flags

- **Name.** `UDPTunnelEncap` reads as something `encap=` accepts, and it
  cannot be one ([Part 4](#part-4-197-a-udp-tunnel-the-caller-seals)).
  *Recommendation:* `UDPTunnel` + `tunnel_stream`.
- **`wrap(inner, direction, timestamp)`**: the timestamp lets a wrapper
  model time-based rekeys and keepalives, and adding it later breaks every
  wrapper. *Recommendation:* include it.
- **Outer impairments**: reuse `--packet-loss` etc. for the outer flow, or
  add separate `--tunnel-*` flags. Inner and outer loss are different
  questions, and both are worth asking in one capture. *Recommendation:*
  separate flags.

### <a name="q5"></a>Q5: same length, or renumber

Renumbering `seq`/`ack` per direction would cover every future
length-changing redaction, including #184's HTTP fallback. But it is
flow-aware code that also has to rewrite SACK blocks, and #191 turned down
the same option. *Recommendation: same length*, with the in-`raw` rewrite,
which also keeps the sender's compression over UDP.

## Not in this milestone

- **DNS over TCP replies sent from the client**: TCP data in both directions
  (Q2). Its own issue.
- **SCTP impairments.** #194 makes SCTP refuse the flags instead of ignoring
  them. Implementing them is its own issue, if anyone asks.
- **TCP reordering** (`--reorder` on TCP). It needs the receiver's
  acknowledgements recomputed, as `_reacknowledge` does for corruption.
- **Re-expressing `--esp` on #197's seam.** The issue says it is not needed.
- **A wrapper hook at the end of the stream** (`finish()`), for a trailing
  keepalive or close. Add it when a wrapper asks for it.
- **Outer fragmentation** of tunnel datagrams larger than an MTU.
