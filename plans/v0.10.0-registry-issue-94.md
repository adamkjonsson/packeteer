The registry — #96 through #103 — is the main part. It is the first milestone of
[plans/user-defined-protocols.md](user-defined-protocols.md), taken from that
plan's summary depth to implementation depth, and it contains **no YAML, no
compiler, and no new packet-spec keys**. #94 rides along because it adds a
field to the same dataclass the registry work is already editing, and doing
both at once means touching `ParsedPacket` once rather than twice.

## The constraint that shapes this milestone

**It must not change what DNS, DHCP or HTTP do.** Everything here is a
refactor with one small API addition on top; the acceptance criterion is that
every existing test passes unchanged. That is what makes it safe to ship
before deciding whether the compiler in v0.11.0 is ever built — and it is why
the work is ordered so that the registry exists, and is tested, before
anything dispatches through it.

It is also worth doing on its own terms, independent of the YAML work:

- It removes a standing CLAUDE.md violation. `_build_dns_from_spec`,
  `_build_dhcp_from_spec` and `_build_http_from_spec`
  ([__main__.py:216–330](../src/packeteer/__main__.py#L216)) are packet-spec ↔
  object mapping living in the CLI, which the project instructions forbid
  twice over: "keep `__main__.py` as lean as possible", and "all functionality
  implemented in the CLI is easily available from the API".
- It deletes four copies of the same three-branch ladder.
- It gives users a documented way to plug in a hand-written protocol, which
  today requires editing four files inside the library.

# Part 1 — the registry

## What is hardwired today

Every reference below is a place that names `dns`, `dhcp` and `http`
literally, and would have to be edited again for a fourth protocol.

## The contract

New top-level module `src/packeteer/protocols.py`:

```python
@dataclass(frozen=True)
class AppProtocol:
    """One application-layer protocol packeteer can parse, build and serialise."""

    name:     str                     # "dns" — also the packet-spec section key
    over:     str                     # "udp" | "tcp" | "either"
    ports:    frozenset[int]
    messages: tuple[type, ...]        # the dataclasses update_config dispatches on

    decode:    Callable[[bytes, str], object]      # (payload, transport) -> message
    encode:    Callable[[object, str], bytes]      # (message, transport) -> payload
    to_spec:   Callable[[object], dict[str, Any]]  # message -> spec section
    from_spec: Callable[[dict[str, Any]], object]  # spec section -> message
    sanitise:  Callable[[dict[str, Any], Any, Any], None] | None = None


def register(proto: AppProtocol) -> None: ...
def registered() -> tuple[AppProtocol, ...]: ...
def for_port(port: int, transport: str) -> AppProtocol | None: ...
def for_section(name: str) -> AppProtocol | None: ...
def for_message(obj: object) -> AppProtocol | None: ...
```

The three built-ins fill it in as `over="either"` (DNS, ports 53 and 5353),
`over="udp"` (DHCP, 67 and 68), `over="tcp"` (HTTP, 80 and 8080) — which is
exactly what the three `_try_parse_*` functions check today, one with an
`isinstance(t, (TCPHeader, UDPHeader))` and two with a single-transport
`isinstance`.

The `transport` string threaded through `decode` and `encode` is what DNS
needs for its 2-byte TCP length prefix (RFC 1035 §4.2.2) — today that is the
`tcp=` keyword on `PacketBuilder.dns`. Making it part of the contract rather
than a per-protocol keyword is what will later let a compiled protocol declare
`over: either` without special-casing.

`register` refuses, with a message naming what collided:

- a `name` colliding with a reserved packet-spec key. The list is the `##`
  headings of `docs/packet-spec/format.md`: `ethernet`, `arp`, `sll`, `sll2`,
  `mpls`, `pseudowire`, `pppoe`, `etherip`, `ipip`, `gre`, `vxlan`, `geneve`,
  `gtpu`, `ah`, `esp`, `network`, `transport`, `payload`, `metadata`,
  `packet_metadata`;
- a `name` already registered;
- a port already claimed for an overlapping transport (`either` overlaps both);
- a message type already claimed.

## Where it lives, and what may import what

This is the part to get right first, because two modules in the tree are
deliberately import-light and the registry must not spoil that.

- **`src/packeteer/protocols.py` imports only the stdlib.** It holds
  callables, never protocol modules. Both `generate` and `parse` need it, and
  `parse` already imports `generate` (`parse/dns.py` imports `generate.dns`),
  so the registry has to sit below both.
- **`src/packeteer/__init__.py` stays empty (0 bytes).** That is why
  `import packeteer.pcap` does not drag in the parser today, and registering
  the built-ins there would end it.
- **`sanitise.py` and `filter.py` import nothing from packeteer** — both are
  stdlib-only and operate on spec dicts. `sanitise.py` may import
  `packeteer.protocols` (stdlib-only, so no cycle), but it must **not** import
  `packeteer.app` at module level.

That last point has a trap in it. `packeteer.sanitise.sanitise(spec)` called
directly, without `parse` or `generate` ever being imported, would find an
empty registry and silently sanitise no app sections — a real regression in
the one command where silence is harmful. **`_sanitise_app_layers` therefore
imports `packeteer.app` lazily, inside the function**, the way
`_try_parse_dhcp` already does `from .dhcp import parse_dhcp` today. It is one
line, and it is load-bearing; it gets a comment saying so and a test that
imports `packeteer.sanitise` alone and checks a DNS section is still
sanitised.

`parse/__init__.py` imports `packeteer.app` at module level, so the built-ins
are registered whenever the parser is used.

**Corrected in #97: `generate` cannot.** The modules in `app/` import
`packeteer.generate.dns` and friends at module level, so importing `app` from
`generate/__init__.py` is a cycle, and it fails on exactly that. `generate`
reaches the registry lazily from `PacketBuilder.app` instead, which means
`import packeteer.generate` alone leaves the registry empty — documented in
the `packeteer.app` docstring and pinned by a subprocess test.

## The assembly layer

New package `src/packeteer/app/` — `dns.py`, `dhcp.py`, `http.py`,
`__init__.py`. Each module assembles one `AppProtocol` from parts that already
exist, and owns the two functions that currently have nowhere good to live:

- **`from_spec`** — moved out of `__main__.py`, made public as
  `packeteer.app.dns.from_spec`. Roughly 115 lines across the three. This is
  the CLAUDE.md fix, and it is the only code in this milestone that moves
  rather than being wrapped.
- **`to_spec`** — a public wrapper over the existing `_apply_dns`
  ([to_config.py:719](../src/packeteer/parse/to_config.py#L719)) and its two
  siblings, returning the section instead of mutating a config:

  ```python
  def to_spec(msg: DNSMessage) -> dict[str, Any]:
      config: dict[str, Any] = {}
      _apply_dns(config, msg)
      return config["dns"]
  ```

`app/__init__.py` calls `register()` for the three, in a fixed order.

## The five dispatch sites, rewritten

**1. Decode.** [core.py:868–870](../src/packeteer/parse/core.py#L868) becomes
one lookup, and the three `_try_parse_*` functions
([core.py:497–559](../src/packeteer/parse/core.py#L497)) and three port
frozensets are deleted:

```python
if decode_app and isinstance(t, (TCPHeader, UDPHeader)) and remaining:
    transport = "tcp" if isinstance(t, TCPHeader) else "udp"
    proto = (protocols.for_port(t.dst_port, transport)
             or protocols.for_port(t.src_port, transport))
    if proto is not None:
        try:
            pkt.app = proto.decode(remaining, transport)
            pkt.app_protocol = proto.name
            remaining = b""
        except (ValueError, struct.error, UnicodeDecodeError):
            pass        # not ours after all — leave the bytes as payload
```

Two behaviours to preserve deliberately:

- **Destination port wins over source port**, matching the `or` above. Today
  all three functions test `src_port not in PORTS and dst_port not in PORTS`,
  so either matches and there is no precedence to preserve — but there will be
  once users register protocols, so it is worth fixing the order now and
  testing it.
- **A decoder that raises leaves the payload alone.** That is what the three
  `except` clauses do today, and it is what makes a port collision survivable.
  The set of caught exceptions is the union of the three existing ones.

The three built-ins' ports do not overlap, so collapsing three sequential
attempts into one lookup cannot change which protocol decodes a packet. Worth
asserting in a test rather than reasoning about again later.

**2. Object → spec.** The `isinstance` ladder in `update_config`
([to_config.py:874–878](../src/packeteer/parse/to_config.py#L874)) keeps its
header branches and loses its three app branches:

```python
proto = protocols.for_message(layer)
if proto is not None:
    config[proto.name] = proto.to_spec(layer)
    return config
```

**3. Spec → builder.** Both sites
([__main__.py:650](../src/packeteer/__main__.py#L650),
[951](../src/packeteer/__main__.py#L951)) become one call to a new API
function — which is the point, since the loop must not live in the CLI:

```python
def apply_app_section(
    b: PacketBuilder, spec: dict[str, Any], transport: str,
) -> PacketBuilder | None:
    """Encode whichever registered protocol's section *spec* carries."""
```

It returns `None` when no section matches, so the caller falls through to
`_apply_payload_spec` as it does today. Home: `packeteer/app/__init__.py`.

**Two app sections in one packet spec becomes an error.** Today the `elif`
chain at [__main__.py:951](../src/packeteer/__main__.py#L951) silently prefers
`dns`, and the `if`/`return` sequence at
[650](../src/packeteer/__main__.py#L650) does the same. A spec carrying both
is already meaningless; with registration order deciding it, silent precedence
becomes arbitrary as well as invisible. This is the one behaviour change in
the milestone and it needs a `Changed` entry.

**4. Sanitise.** [sanitise.py:563](../src/packeteer/sanitise.py#L563) becomes
a loop over `registered()`, with the lazy import described above.

**5. Builder.** One generic method beside the three existing ones:

```python
def app(self, msg: object) -> "PacketBuilder":
    """Set the payload to a serialised message of any registered protocol."""
```

It resolves the type through `for_message`, infers the transport from the
layer stack already on the builder, and raises `TypeError` naming the type
when nothing is registered for it.

## What does not change

Worth stating, because the temptation to tidy will be there:

- **`.dns()`, `.dhcp()` and `.http()` stay exactly as they are.** They are
  documented, they have keyword arguments of their own (`tcp=`), and
  rewriting them as `app()` wrappers buys nothing.
- **`ParsedPacket.dns` / `.dhcp` / `.http` stay**, populated alongside `.app`
  for the built-ins. They are released public API. Keeping them is what makes
  this milestone free of `Breaking:` markers.
- **`_apply_dns` / `_sanitise_dns` and their siblings stay where they are**
  — see [Q1](#q1).
- **No packet-spec keys change.** A registered protocol's section key is its
  name, and the three built-ins keep the names they have.

- A toy protocol registered in a test, then driven end to end: built from a

## Undecided

<a id="q1"></a>
**Q1 — Do the built-ins' implementations move into `app/`, or only their
dispatch?** Moving `_apply_dns` out of `to_config.py` and `_sanitise_dns` out
of `sanitise.py` would give one file per protocol and a cleaner model, at the
cost of ~400 lines of churn in two of the most carefully tested modules in the
project — and `sanitise.py` is stdlib-only today, so moving `_sanitise_dns`
into `app/dns.py` would drag `_Replacer` and `SanitiseOptions` across a module
boundary that currently has nothing crossing it.

*Recommendation: dispatch only.* `app/dns.py` references the existing private
helpers; only `from_spec` actually moves, because it has to. Revisit when a
generated protocol exists to compare against — that is the point at which the
right split becomes visible rather than guessed.

<a id="q5"></a>
**Q5 — Does a user protocol get its own `ParsedPacket` attribute?**
`pkt.app` is honest and statically typed; `pkt.sensor` is what people will try
first, and costs a `__getattr__` plus a hole in the annotations.

*Recommendation: `pkt.app` only*, with `pkt.app_protocol` as the
discriminator. It keeps `ParsedPacket` fully annotated, as CLAUDE.md requires.

# Part 2 — #94, `ParsedPacket.datagram_truncated`

Filed out of #92, which is why it exists: that fix cleared
`transport.checksum` on a truncated capture, which removed a false positive on
every packet but merged "derivable" and "unknowable" into one absent key. A
consumer acting on the checksum verdict — `zpfwire` drops segments a receiver
would have dropped — cannot currently tell them apart on the
`parse_pcap_file` path.

## Verified

The condition is already computed and already thrown away, in `parse_packet`
([core.py:1054](../src/packeteer/parse/core.py#L1054)):

```python
declared = _ip_payload_size(ip_hdr, ip_size)
truncated = declared is not None and declared > len(remaining)
```

It is threaded into `_clear_derivable_transport_fields` and discarded. Keeping
it on the packet is most of the work.

**The meaning is settled** (Adam, 2026-08-28, on #94): the *datagram* sense —
the IP header declares more payload than the packet holds — not the capture
sense. Capture truncation is already reachable through
`ParsedPacket.source_records`, whose `PcapRecord`s carry `orig_len`, on the
one entry point that has them. The datagram sense is reachable no other way,
and it works on every entry point including raw `parse_packet(bytes)`.

## Implementation

- `datagram_truncated: bool = False` on `ParsedPacket`, beside
  `payload_offset`.
- Set from the value `parse_packet` already computes.
- Carried into tunnelled inner packets the way `payload_offset` is — an inner
  packet is truncated if its own IP header says so. Note the outer and inner
  answers can differ, and the inner one is the one that matters for the inner
  transport's cleared fields.

## The spec marker

`ParsedPacket` alone leaves `packeteer parse` output ambiguous, so the spec
needs a marker too. **Recommendation: `packet_metadata.truncated`**, `true`
only when set — it describes how the capture was taken rather than what the
packet's bytes say, which is what `packet_metadata` is already for
(`packet_num`, `timestamp_s`). Putting it in `network` would wrongly imply a
field on the wire.

`build` ignores packet-spec keys it does not recognise
([__main__.py:825](../src/packeteer/__main__.py#L825) reads with `spec.get`),
so this is additive on the round trip.

## Tests

- Set for all four transport/IP-version combinations on a truncated capture,
  clear on the same packets captured whole — reusing the helpers added to
  `test_transport_overrides.py` in 0.9.1.
- Clear for every fragment of a fragmented datagram, which declares exactly
  what it carries.
- Set on the inner packet of a truncated tunnelled capture.
- `False` for an IPv6 jumbogram, with the test named for the limitation.
- `packet_metadata.truncated` present in the spec, and absent when whole.

## Changelog

`Added`, referencing #92 for why it is needed.

## Known limit, to document rather than fix

`_ip_payload_size` returns `None` for an IPv6 jumbogram (`payload_length` of
`0`, RFC 2675), so the flag stays `False` there. The same limit #92 has.

## Cross-cutting

- **Dependencies.** #96 and #97 gate everything else: #98–#101 each dispatch
  through the registry, and #102 needs somewhere for #98's result to land.
  #103 comes last because it documents the finished shape. #94 is independent.

- **The issues carry the detail, not just a pointer.** Each of #96–#103
  repeats the line references and the reasoning it needs, so a reader picking
  one up does not have to read this plan first. Where they disagree with this
  file, this file is the one to update.

- **Semver.** Additions and one behaviour change, no removals — a minor bump,
  no `Breaking:` markers. Keeping `ParsedPacket.dns` and the three builder
  methods is what buys that; if either is dropped later it is a `Breaking:`
  entry in whichever release does it.

- **Version.** `pyproject.toml` goes to `0.10.0.dev0` at the start of this
  work.

- **Relationship to v0.11.0.** Nothing here presumes the compiler will be
  built. The one place this milestone is shaped by it is the `transport`
  argument on `decode` / `encode`, which exists so that a protocol can later
  declare `over: either` without special-casing — and which the built-in DNS
  needs anyway.

- **zpfwire.** #94 is what lets them drop the local
  `len(record.data) < record.orig_len` guard, and it is worth telling them
  that the flag means the datagram sense rather than the capture sense, since
  their current guard measures the other one.

- **Release.** Both close at release with the milestone, not at merge.
