# Plan — v0.14.0: the downstream release

*Written 2026-09-12.*

*Status: **all six issues done**, on `v_0.14.0`. The documentation sweep
([Part 7](#part-7--the-documentation-sweep)) and the release to go. Every
question settled as recommended — see [Undecided](#undecided).*

0.12.0 made a user's protocol first-class and 0.13.0 made the spec dialect
shared with kober. This is the first release shaped by what happened when
those were **used**. Three of the six issues were found downstream, all
against 0.12.0: [zpfwire](https://github.com/adamkjonsson/zpfwire) could not
ask whether a link type is supported (#138), kober's decoder tests fed a
generated stream that carried nothing (#137), and the registry's flat `app`
accessor turned out to be worse than the three-name convenience it was meant
to replace (#139). The other three are remainders of earlier milestones that
have waited for a release with room: the per-layer half of #71 (#74), the
compression half of #130 (#131), and the timestamp half of #88 (#90).

Two strands, and one bug at the join.

**What a caller can ask** — #139, #138, #74. Each is a fact packeteer already
holds and a caller cannot get at without re-deriving it: *which* protocol
decoded a packet, by its own name; whether a link type is one the parser
knows; where a header sits in the frame. None changes what packeteer decodes.
All three are additive API, and the third is the one nobody has asked for yet.

**What generated traffic looks like** — #131, #90. Both are the #87 pattern:
a decoder tested only against packeteer's output is never shown a compression
pointer, and never shown a TCP timestamp. Both change the bytes of every
generated capture, which is why they are worth doing and why they go last.

**#137** is the bug between them: `--protocol-messages` is the path that
carries content into a generated stream, and it accepted the shape `parse`
writes while building empty messages from it. The run *looked* like a decoder
test and tested nothing.

## The order, and why

```
#137 → #138 → #139 → #74 → #131 → #90 → docs sweep → release
```

- **#137 first.** It is the only bug, it is small, and it is on the path
  kober's decoder tests use today. A `.dev0` build with it fixed is useful to
  a downstream project before anything else here lands.
- **#138 second** for the same reason on the other consumer: zpfwire has an
  inference it wants to delete.
- **#139 before #74.** #139 turns a protocol name into an attribute name and
  adds a test that every public name on `PacketBuilder` and `ParsedPacket` is
  reserved. #74 adds a public name to `ParsedPacket`. With #139 in place the
  test fails the moment #74 forgets to reserve it, which is precisely the
  failure the test exists for.
- **#131 and #90 last, and adjacent.** Both change generated bytes. Every test
  that asserts on a seeded capture's content is touched in one window rather
  than two, and the release notes can say once that captures generated by
  0.14.0 differ from 0.13.0's.
- **#90 is the largest by a distance** and the only issue that changes how the
  impairment passes work rather than what they are handed. If the milestone
  has to ship before it is finished, **#90 is what moves**, not the five ahead
  of it. The plan is written so nothing earlier depends on it.

- **The documentation sweep is its own step, after the last issue and
  before any release preparation** — [Part 7](#part-7--the-documentation-sweep).
  Each issue updates the pages it touches; the sweep is the pass that reads
  the whole of `docs/` and `README.md` against what the branch now does,
  which is a different job from any one issue's. 0.13.0's sweep (`4624f84`)
  found a transcript two releases stale and a superset claim that had gone
  wrong for reasons that release did not cause; nothing per-issue would have.

Sizing, honestly: #138 and #137 are each a short day; #139 and #74 a day or two
each; #131 two to three days including the encoder tests; #90 is a week's work
and has the most that can go wrong. The sweep is a day, and is not the place
to economise — it is the last thing a reader of the release sees and the first
thing they judge it by.

# Part 1 — #137, a section that is not a section

## The bug, precisely

`_protocol_payload_fn` in `__main__.py` reads a JSON array and hands each
element to `proto.from_spec`. Every `from_spec` — the three hand-written ones
in `packeteer/app/` and the one `codegen.py` emits — treats a key it does not
recognise as an absent field. That is right for a **partial** section and
wrong for a section in which **nothing** is recognised: the difference between
"this message has no questions" and "this is not a section" is gone by the
time `encode` runs.

The wrapped shape `{"dns": {…}}` is the natural mistake because it is what
`parse` emits — more precisely, `parse` emits a *full packet spec* per packet,
with `dns` beside `network` and `transport`. Feeding that array straight back
in is the obvious way to replay captured messages through an impaired stream,
and it is the path into this bug.

## Two fixes, and the second is the one that matters

**1. Unwrap what `parse` writes.** If an element carries the protocol's own
name as a key whose value is an object, that object is the section — whether
it is the only key (`{"dns": {…}}`) or one of several (a whole packet spec).
This makes `packeteer parse … | packeteer stream --protocol-messages` a
round trip by construction. `packeteer.app.apply_app_section` already does
exactly this lookup for `build`; the same rule serves both.

**2. Refuse a section with no recognised key.** A non-empty section none of
whose keys the protocol recognises is a `ValueError` naming the keys it saw
and the keys it expected. An **empty** section stays a default message —
`{}` is an explicit request for one, and refusing it would break a spec that
legitimately wants a bare header.

The second fix lives in `from_spec`, not in the CLI, and that is deliberate:

- The CLI cannot write it. It does not know a protocol's keys; only the
  protocol does.
- It fixes `packeteer build` too, which has the same silent path through
  `apply_app_section`.
- **`packeteer.conformance.check_protocol` can enforce it.** A new check
  feeds `{"no_such_key": 0}` and expects `ValueError`, so a compiled protocol
  and a hand-written one are held to the same rule. That is what makes the
  fix a property of the registry rather than of three files.

For the three built-ins, each `from_spec` gains a literal set of the keys it
reads and one guard at the top. For compiled protocols, `_emit_entry` in
`codegen.py` emits the same guard from the entry unit's field names.

## The API side

`_protocol_payload_fn` is CLI-only, which sits badly with the first rule in
`CLAUDE.md`. The part worth lifting is small: *sections → cycling payload
function for a protocol over a transport*. Put it in `packeteer.app` beside
`apply_app_section` — it is the same job on a list — and have the CLI call
it. The file reading and error printing stay in `__main__.py`; the unwrap and
the encode do not.

## Changelog

Under `Fixed`. This changes behaviour — a section that built a default message
now raises — but the input was never valid and the output was never right, so
it is a fix, not a **Breaking** change. Say plainly that `parse` output now
round-trips into `--protocol-messages`.

## Tests

- The wrapped form and the full-spec form both encode the inner section.
- A section with no recognised key raises, for each built-in and for a
  compiled protocol; `{}` does not.
- `check_protocol` fails a protocol whose `from_spec` swallows an unknown
  section — build one deliberately.
- `kober`'s specs under `src/tests/kober/` still pass conformance after the
  codegen change.

Docs: `docs/cli/stream.md` (the round trip is now a feature — show it),
`docs/guide/adding-a-protocol.md` (the rule a hand-written `from_spec` must
follow), `docs/api/conformance.md`.

### What #137 corrected

**"Feed `parse` output straight back in" was not one shape but three, and the
plan named the wrong one.** It reasoned about `{"dns": {…}}` and a whole
packet spec as elements of an array. What `packeteer parse` actually writes
is a *document* — `{"metadata": …, "packets": […]}` — so the natural path
(`parse … --output msgs.json`, then `--protocol-messages msgs.json`) would
have been refused as "not a JSON array" and the round trip the fix promised
would not have existed. The document shape is now accepted too, and the CLI
test feeds the unedited file back.

**A parsed capture is mostly not messages.** Its packets include the
handshake and every ACK, none of which carries the protocol's section. The
plan's rule — refuse any element with no recognised key — would have refused
the first SYN. A packet that carries no section is *passed over*; a file in
which nothing carries one is refused, so the silence is bounded to the
packets between messages and never to the whole file. Telling a packet from
a bare section is done by its link/network keys (`ethernet`, `network`, …),
**not** by `_RESERVED_NAMES`: #139 will grow that set to attribute names
such as `timestamp` and `ip`, which a bare section could use as fields, and
a section mistaken for a packet is skipped in silence — the failure mode
this issue exists to remove. Ruff's `SLF001` on the private access is what
prompted the second look.

**Conformance accepts any codec error, not `ValueError` alone.** The plan
said the check "expects `ValueError`". The property is that `from_spec`
*refuses*, and the suite's own broken-protocol fixture refuses with
`KeyError` (`s["data"]` on a section without it). Insisting on the type
would have failed a protocol for choosing a different honest exception; the
check accepts the same set `check_protocol` already treats as a protocol's
own failures, and the built-ins raise `ValueError` with the helpful message.

**The CLI's private error tuple went with it.** `_ENCODE_ERRORS` in
`__main__.py` existed only for this path; the set and the comment explaining
why `AttributeError` is in it moved to `packeteer.app`, where the API that
needs them now lives. `__main__.py` lost an import and a function body.

# Part 2 — #138, a question the parser can already answer

The `if link_type == …` ladder in `_parse_link_layer`
([`parse/core.py:445`](../src/packeteer/parse/core.py)) is the definition of
"supported", and it is not readable from outside.

## Where it lives

The issue offers `packeteer.pcap.SUPPORTED_LINK_TYPES` or
`packeteer.parse.supports_link_type`. **Both, and both in `parse`.**

Not `pcap`: `pcap.py` is I/O, and `write_pcap` will happily write link type
147. Support is a property of the parser, and the constant belongs next to
the ladder it describes. `pcap.py` keeps the `LINKTYPE_*` numbers, which are
pcap's.

```python
# parse/core.py
SUPPORTED_LINK_TYPES: frozenset[int] = frozenset({
    LINKTYPE_ETHERNET, LINKTYPE_RAW, LINKTYPE_LINUX_SLL, LINKTYPE_LINUX_SLL2,
    LINKTYPE_NULL, LINKTYPE_LOOP,
})

def supports_link_type(link_type: int) -> bool: ...
```

The ladder tests membership **first**, so the set cannot drift from the code:
an unsupported type reaches the warning branch by failing the set, not by
falling off the end of the `if`s. Adding a link type then means adding it to
the set, and a test that every member parses a minimal frame without
`UnsupportedLinkTypeWarning` — and that a non-member (`147`, `LINKTYPE_USER0`)
warns — keeps the set honest in the other direction.

## Saying it up front

The issue's best line: a capture whose link type is unsupported yields nothing
at all, and saying so before reading a packet beats a warning per file.
`PcapInfo` gains `link_type_supported: bool`, `format_pcap_info` prints it, and
`packeteer info` therefore says it — the CLI reaches it through the API,
which is the right direction.

`_choose_link_type` in `info.py` tries a candidate set that is a subset of
the supported set — it leaves out the two loopback types, and nothing says
whether that is deliberate. It probably is: a 4-byte family word is easy to
score against by accident. Leave the set alone, and add the comment that
says so, so nobody "fixes" it by substituting `SUPPORTED_LINK_TYPES`.

Changelog: `Added`. Docs: `docs/api/parser.md`, `docs/guide/parsing.md`
(next to the existing unsupported-link-type note), `docs/cli/file-info.md`.

### What #138 corrected

**The docs gap was larger than a missing pointer.** The plan sent the sweep
to "the existing unsupported-link-type note" in `docs/guide/parsing.md`.
There is none: the guide never mentions link types beyond metadata, and
`docs/api/parser.md` documented `UnsupportedIPProtocolWarning` in full while
`UnsupportedLinkTypeWarning` — 0.12.0's — appeared nowhere in `docs/`. The
parser reference now has a *Link types* section that lists the six, shows
the predicate, says why the `is None` inference is wrong, and finally
autodocs the warning; the pcap guide's wrong-link-type section points at it.

**The `file-info` note named the symptom.** With an unsupported link type the
report already ended with "no packets contained an IP layer — the capture
may be malformed", which is the #123 mistake one level up. The note now
names the cause when it is known and offers the symptom only when it is not.

**`_LINKTYPE_NAMES` in `info.py` was two behind.** `DLT_NULL` and `DLT_LOOP`
parsed since 0.12.0 but printed as bare numbers on the report; the CLI's
`--link-type` accepted `null` and `loop` by name. Both names are on the
report now — small, but it is the kind of thing #138's test (every member of
the set decodes a fixture frame cleanly) is positioned to keep noticing.

# Part 3 — #139, a protocol by its own name

## What is being decided

`pkt.dns` is a better API than `pkt.app`, and the issue's argument is right:
the code after `pkt.app` almost always checks `app_protocol` anyway. The fix
is to make the per-name attribute the general rule, on both front doors:

```python
pkt.sensor                       # Reading(…) when pkt.app_protocol == "sensor", else None
PacketBuilder().udp(dst_port=9000).sensor(msg)
```

`.app()`, `pkt.app` and `pkt.app_protocol` are untouched. Additive.

### <a name="q1"></a>Q1 — the three declared fields stay

The issue says `_LEGACY_APP_ATTRS` "stops being a special case", and taken
literally that is not available: `dns`, `dhcp` and `http` are declared
dataclass fields, a declared field shadows `__getattr__`, so `_try_parse_app`
must still `setattr` them. The choice is:

- **(a) Keep the three as declared fields.** They stay typed — `pkt.dns` is a
  `DNSMessage | None` to mypy, `pkt.sensor` is `object`. The set stays, but
  the comment changes: it is no longer *legacy, drop at 1.0*; it is *the three
  with a typed spelling*. Behaviourally there is no privilege left.
- **(b) Delete the fields and route everything through `__getattr__`.**
  Uniform, and breaks `ParsedPacket(dns=…)`, `replace(pkt, dns=…)`, and every
  type checker's view of the three most-used attributes, for no behaviour a
  user can see.

**Recommendation: (a).** The issue's own reservation test assumes it (`public
- {"dns", "dhcp", "http"}`), and the 1.0 note on `_LEGACY_APP_ATTRS` gets
deleted rather than acted on — the thing marked for removal turned out to be
the model.

## The mechanics

**`ParsedPacket.__getattr__`** as the issue sketches it, with one guard it
does not mention: **a name beginning with `_` raises `AttributeError` before
touching the registry.** `copy.deepcopy`, `pickle` and `dataclasses` all
probe dunders (`__deepcopy__`, `__getstate__`, `__reduce_ex__`) through
`getattr`, and a lookup that consulted `for_section` for each would be slow
at best and wrong the day someone registers a protocol whose name a dunder
happens to match. `__dir__` adds the registered names.

**`PacketBuilder.__getattr__`** returns a one-argument layer method, same
guard, same `__dir__`. It imports `register_builtins` inside the function for
the same cycle reason `.app()` does. It can do what `.app()` cannot — check
that the message belongs to the protocol named — and the `TypeError` message
should say which protocol the message *does* belong to when there is one.
`info.py` uses `getattr(pkt, attr)` on real attribute names only; nothing in
the tree does dynamic lookup on a builder.

**`register()` validates the name.** `isidentifier()`, not a keyword, no
leading underscore, and not reserved. This is **Breaking**: a name like
`my-sensor` registers today and will not tomorrow. The message must say the
name is about to become an attribute, which is why the rule exists.

**`_RESERVED_NAMES` grows.** It reserves packet-spec keys today; from here it
also reserves every public name on the two classes. Enumerating them rather
than trusting the issue's list found three the issue missed — **`ip`, `tcp`
and `udp`** are builder methods and are not reserved — plus `loopback` and
`vlan`, which the issue lists. The full set to add:

```
app  app_protocol  build  datagram_truncated  fragment  fragment_header
hop_by_hop_options  icmp  icmpv6  ip  ipip  loopback  payload_offset  sctp
source_records  tcp  tick_hz  timestamp  ts_frac  ts_sec  tunneled  udp  vlan
```

`protocols.py` imports only the standard library, so the list stays literal
and the issue's test keeps it honest:

```python
public = {n for n in dir(PacketBuilder) if not n.startswith("_")}
public |= {n for n in dir(ParsedPacket) if not n.startswith("_")}
self.assertLessEqual(public - {"dns", "dhcp", "http"}, protocols._RESERVED_NAMES)
```

`dir()` rather than `fields()` so the `timestamp` property is counted. This
is the test #74 runs into.

**`packeteer protocol check` refuses the name early.** Today a spec whose
`name:` is `ethernet` passes `check`, compiles, and fails on import with
`ProtocolError`. With attribute names in play the reserved list triples, so
the failure has to move to `check`. Factor the rule into one private
`protocols._name_problem(name) -> str | None` that `register()` and
`check.py` both call — `protospec` may import `protocols`, which imports
nothing back.

## What is not in it

- **A `.pyi` for the compiled module**, so mypy can see `.sensor`. The issue
  defers it until asked; agreed. Say in the docs that `__dir__` fixes the
  REPL and nothing fixes static analysis yet.
- **`--name-prefix` on the compiler.** Not until a collision happens.

Changelog: `Added` for the accessors; `Changed` with **Breaking:** for the
name rule, saying what a caller with a non-identifier name must rename to.

Tests: the accessor on a hit, a miss (`None`), an unregistered name
(`AttributeError`), a leading underscore (never consults the registry);
`.sensor(wrong_message)` is a `TypeError`; the reservation test above;
`register()` refuses each kind of bad name; `check` reports a reserved or
non-identifier `name:` at the spec's line.

Docs: `docs/guide/parsing.md` §"Any protocol, not just the three" inverts —
lead with `pkt.sensor`, then `.app` for generic code;
`docs/guide/generating.md` the same for the builder;
`docs/guide/adding-a-protocol.md` and `docs/protocols/format.md` state the
name rule; `docs/api/protocols.md`.

### What #139 corrected

**The name rule is public, not private.** The plan had a private
`protocols._name_problem()` shared with `check.py`. Calling a private
function across modules is exactly what ruff's `SLF001` refuses, and the
project's rule is that a `noqa` is asked about, not written. The honest
answer was that the rule is a legitimate API — a tool generating protocols
wants to validate a name before writing anything — so it is
`protocols.check_name(name)`, raising `ProtocolError`, parallel to #137's
`check_section`. `register()` calls it; the checker catches it.

**A test pinned the behaviour being reversed.** `test_app_dispatch.py`
asserted `not hasattr(pkt, "sensor")` — "only the three built-ins get one;
everything else uses `.app`" — which is the 0.12.0 decision this issue
overturns. It inverts rather than being deleted: the same fixture now
asserts `pkt.sensor is pkt.app`.

**`_transport_name`'s error named `.app()`** — "so `.app()` needs a `.tcp()`
or `.udp()` layer" — which was true when it was the only caller. A `.both()`
call on an `either` protocol would have been told to fix `.app()`. The
message now names both spellings.

The reserved list, enumerated rather than trusted, was as the plan said:
twenty-three names, `ip`/`tcp`/`udp` among them. The reservation test passed
first time, which is the point of writing the list from `dir()` rather than
from memory.

# Part 4 — #74, where each header sits

## The case that was missing when it was deferred

#74 was deferred for want of a use, and the plan for #139 found one by
accident: **when a protocol decodes the payload, `payload_offset` is `None`**,
because `payload` is empty. A tool that can cite where a TCP payload sits in
the file loses that ability the moment the payload is a DNS message — which
is when it most wants to say "the message at file offset X".

The issue's other three cases stand: verifying a checksum against captured
bytes, citing a header, and tunnelled packets where nothing can be found by
arithmetic.

### <a name="q2"></a>Q2 — fields or a mapping

- **Typed fields** — `ip_offset`, `transport_offset`, and then one per
  tunnel and link layer. Discoverable and typed, and there are seventeen
  header attributes on `ParsedPacket`. Two fields recreates this issue for
  the third layer someone needs, the way #71 → #74 happened.
- **One mapping** — `offsets: dict[str, int]`, keyed by the name of the
  `ParsedPacket` attribute the header is on (`"ip"`, `"transport"`, `"gre"`,
  …) plus `"app"` for a decoded message. Scales without API growth, and the
  key set is self-documenting: it is the attributes that are set.

**Recommendation: the mapping**, named `offsets`. `payload_offset` stays as it
is — released API with a documented `None` rule — and is not duplicated in
the map. `"app"` is the entry that closes the gap above.

## Mechanics

The values are already known: `offset` in `parse_packet` and `base` in
`_parse_ip_protocol` and the tunnel helpers are exactly the numbers to
record, at the line each `pkt.<layer> =` assignment happens. `_shift_offsets`
rebases every value in the map alongside `payload_offset`, so the
outer-frame convention holds at any depth. `mpls` records the first label.
`"app"` is the transport payload's start, recorded in `_try_parse_app` on
success.

`offsets` joins `_RESERVED_NAMES` — #139's test insists.

Not written to the packet spec, like `payload_offset`; it is provenance about
a frame, not a description of one.

Changelog: `Added`. Tests: one per layer against a hand-built frame, the
tunnelled case at two depths, the `"app"` entry on a decoded DNS packet, and
the padded-frame case that motivated `payload_offset`'s own rule. Docs:
`docs/guide/parsing.md` §"Where the payload was in the frame" grows a
sibling section; `docs/api/parser.md`.

### What #74 corrected

Nothing of substance — which is itself the finding. The plan said the
values were already known at each `pkt.<layer> =` assignment and that the
work was recording them; it was, and the twenty tests passed on the first
run once the fixture code was right. Two small things worth recording:

- **`_try_parse_app` had no offset to hand.** It was called with the payload
  bytes only; `"app"` needed the payload's position, so it gained a `base`
  argument from the one caller that has it. That the app decode was the one
  place the offset had *not* been threaded is the concrete form of the gap
  the issue was reopened for.
- **The reservation test from #139 was the first thing to run.** `offsets`
  went into `_RESERVED_NAMES` in the same edit, so it never fired — but it
  was written for exactly this commit, and this is the first field added to
  `ParsedPacket` since it existed.

# Part 5 — #131, DNS that compresses

## What #130 settled and what it did not

Fidelity is `dns.raw`'s job and stays that way: **`raw` set means write
`raw`**. This issue is about the bytes packeteer produces when it is
*generating*, and the argument is the #87 one — a decoder tested against
packeteer's DNS has never seen a pointer.

## The encoder

`_encode_name` becomes context-aware: a dict of *label-suffix → offset*
filled as names are written, consulted for the longest suffix already
present, pointing backwards only, skipped when the target exceeds the 14-bit
field (`0x3FFF`). Names inside RDATA count for the types RFC 1035 lets
compress — CNAME, NS, PTR, MX, SOA — and **not** for TXT, A, AAAA or raw
RDATA, where a pointer would be a bug (RFC 3597 §4). The root name is a
single zero byte and never a pointer.

Two details that decide whether the round trip is lossless:

- **Match case-sensitively.** RFC 1035 permits a case-insensitive match, and
  a pointer resolves to the *target's* spelling. A message with `Example.COM`
  and `example.com` would come back with one spelling, and
  `from_spec(to_spec(parse(encode(m)))) == m` — the conformance rule — would
  fail. Exact matching keeps it lossless at the cost of a pointer real
  senders might emit. Right trade.
- **The RDATA length is the compressed length.** `_encode_rr` writes
  `RDLENGTH` after encoding RDATA, so the context's offset must be advanced
  through the 10-byte fixed part before RDATA names are written. Easy to get
  wrong by one; the test that parses what was encoded catches it.

### <a name="q3"></a>Q3 — compress by default

The issue leaves this open. **Recommendation: on by default**, with
`compress: bool = True` on `_build_dns_message`, `_build_dns_message_tcp`
and `PacketBuilder.dns()`. The registry `encode(msg, transport)` has a fixed
signature by design and always compresses; no packet-spec key is added until
someone asks for uncompressed output from a spec.

The argument for *on* is not only realism. **The parser's `raw` rule gets
better.** `parse/dns.py` keeps `raw` when `_build_dns_message(msg) != data`.
Today that is every compressed message, which is nearly every real response.
With a compressing default encoder, every message whose sender chose the
same targets we do rebuilds from fields and carries no `raw` — the 282 of 516
pointers #130 measured say that is roughly half. Those messages become
hand-editable in a spec, which the `raw` docstring presents as the cost of
fidelity. The other direction is small: a real *uncompressed* response would
now gain `raw`, and a query with one name has nothing to compress either way.

The rule must stay **one encoder**: `raw` is set when the *default* rebuild
differs, because the default is what `build` will run. Trying both
settings in the parser would report fidelity `build` cannot deliver.

## What changes visibly

- Every generated DNS message with a repeated suffix — which is every
  response — changes bytes. Tests asserting on DNS bytes and any committed
  generated capture with DNS in it (`testcases/dns_example.pcapng`) need
  regenerating or re-asserting. Say so in the changelog.
- `testcases/real/MANIFEST.md` records that the committed `dns.pcapng` has no
  compression because `sanitise` drops `raw`. After this, re-running the
  original capture through `sanitise` would produce a compressed corpus file.
  That needs the unsanitised original, which is not in the repository —
  **Adam's call whether to refresh it**; the test suite gets its compression
  coverage from encode → parse round trips regardless, and the manifest entry
  is updated either way to say the gap is now closable.

Changelog: `Changed` — not breaking, but a visible byte change for every
generated DNS message, called out as such — and `Added` for the keyword.

Tests: encode → parse equals the original for a message exercising every
compressible RDATA type; pointers appear (`0xC0` prefix) and only point
backwards; a message pushed past 16 KiB over TCP stops emitting pointers
past `0x3FFF` and still parses; `compress=False` reproduces 0.13.0's bytes;
`raw` wins over `compress`; the parser's `raw` is empty for a message
packeteer compressed itself. `test_dns_compression.py` already tests the
parser's side and is the file to extend.

Docs: `docs/api/packet-builder.md`, the module docstring in
`generate/dns.py` (which currently says compression is not used), the
`DNSMessage.raw` docstring, `docs/guide/generating.md`, the manifest.

### What #131 corrected

**#130's fixture was the canonical pointer.** `test_dns_compression.py`
hand-built a response whose answer name was `0xC00C` — offset 12, the
question — described as "the shape no encoder that writes names in full can
produce". True, and it is also exactly the pointer this encoder produces, so
the moment compression landed the fixture re-encoded from its fields, `raw`
stayed empty, and six tests that existed to pin `raw` failed for the right
reason. The fixture is now a *non-canonical* pointer — `example` written as
a label followed by `0xC014`, pointing at `com` alone where the whole name
was available at 12 — which is legal, which packeteer's encoder would never
choose, and which is therefore the case `raw` exists for. One of the
replaced tests asserts the canonical encoding of the same message carries
no `raw`, which is #131's half of the property.

**The corpus number is not the plan's number, and points the other way.**
The plan quoted #130's measurement — 282 of 516 pointers across 476 real
messages match a canonical encoder — to argue roughly half of real captures
would *lose* `raw`. That holds for a live capture. The committed
`testcases/real/dns.pcapng` is not one: it was sanitised in 0.12.0, when
sanitise rebuilt every redacted message *uncompressed*, so all 238 of its
messages re-encoded from fields under the old encoder and 119 of them —
the ones with a repeated name — now **gain** `raw` under the new one. Nothing
in the suite depended on it and the manifest says so; the honest fix is the
one the manifest already named, re-running the original through `sanitise`,
which is Adam's call because the original is not in the repository.

**"Compressed message, in practice" was the wrong gloss on `raw`.** The
packet-spec reference described `raw` as being present for "a compressed
message, in practice"; it is present for a message compressed *differently*
from packeteer's encoder, which after this change is a narrower and more
useful statement. The protospec table's line that packeteer's DNS encoder
"declines to compress" was a justification for not implementing `pointer`
in specs; the justification survives (a compression model is a protocol's
own), the sentence did not.

`RDLENGTH` had to become the *compressed* length, patched in after the
RDATA is written — the plan flagged the off-by-one risk, and the
parse-what-was-encoded test is what would have caught it. It passed first
time.

# Part 6 — #90, a connection that negotiates timestamps

The largest item, and the plan for it is longer because the issue's
four-point analysis is right and each point has a decision inside it.

## Where the current output stands

`default_syn_options()` deliberately omits timestamps, because a connection
that advertises them on the SYN and never sends one is a worse tell than a
SYN without them. So the constraint that shapes everything is: **once
negotiated, every segment carries one.** Both emit loops —
`generate_tcp_stream.emit` and `TCPSession._emit` — attach options to the
handshake only, and the HTTP payload generator goes through `TCPSession`, so
there are exactly two loops to change and the payload generators come free.

### <a name="q4"></a>Q4 — the switch is the SYN

No new config knob. **Timestamps on the handshake options are what turns them
on**, which is what negotiation means: if both `client_options` and
`server_options` carry `timestamps`, every later segment does; if either
lacks it, none do (RFC 7323 §3.2). `default_syn_options()` gains
`timestamps=(0, 0)`, and the generator treats a SYN's TSval as the clock's
starting value with `0` meaning *pick one* — the same convention
`client_isn=None` uses. `--no-tcp-options` therefore already turns them off,
and a caller who wants options without timestamps passes a `TCPOptions`
without them. The one-line test `test_timestamps_are_not_advertised` in
`test_syn_realism.py` inverts.

## The four points

**1. Per-segment options.** `emit` takes the handshake options as today and,
for every other segment, builds `TCPOptions(timestamps=(tsval, tsecr))`
itself — `tcp.py` already lays that out as `NOP NOP TS` per RFC 7323 and
`test_tcp_option_layout.py` proves it.

**2. The clock.** `_TCPEndpoint` gains `ts_base: int` (the 32-bit start,
seeded like the ISN) and `ts_recent: int` (the latest TSval that **arrived**
from the peer, RFC 7323's name for it). TSval is `ts_base + elapsed_ms`
where elapsed is measured from the packet's own capture timestamp, so
`--gap-jitter` shows up in it the way it would on a real host. TSecr is the
sender's `ts_recent`, `0` on the SYN. `ts_recent` updates in `emit` **only
when `delivered`**, which is the receiver-side state #85 added, so after a
loss the echo is the last value that actually got through.

**3. What a copy carries.** This is the structural change the issue
predicted. `_apply_retransmission`, `_apply_corruption` and
`apply_loss_recovery` build their copies with `dataclasses.replace(pkt,
ts_sec=…, label=…)`, which copies `raw` verbatim — and a retransmission with
the original TSval is exactly what RFC 7323 §4.1 rules out, since RTT
measurement across a retransmission depends on the copy carrying the time it
was actually sent. The
copies have to be **rebuilt**, not copied. Everything needed is in reach:
`flow` (endpoints, window, encapsulation), `pkt.direction`, `pkt.flags`,
`pkt.seq`, `pkt.ack`, and the payload as `pkt.raw[-pkt.payload_len:]`. One
helper in `impairments.py`, `_rebuild(pkt, flow, options)`, replaces the
three `replace(...)` calls for anything that is a retransmission; the
corrupted copy itself keeps its original options, since it *is* the original
transmission with a flipped byte.

The fresh TSval is the clock at the retransmission's timestamp — computable
from the per-direction `(ts_base, base_usec)` the passes need handed to them
on `FlowEndpoints`. The fresh TSecr is the latest opposite-direction TSval
before that instant, which is a scan over `packets` of the kind
`apply_loss_recovery` already does for its `reference`. That scan needs the
TSval readable from a packet, so **`TCPStreamPacket` gains
`timestamps: tuple[int, int] | None = None`**, mirroring `TCPOptions`. It is
additive and it is what a hook author would want anyway. Every `make(...)`
call passes it.

The `ACK-RECOVER` in `apply_loss_recovery`, the server RST, and the stray
pass all build packets from scratch with `options=None`. The recovery ACK is
this connection's segment and must carry a timestamp when the connection
negotiated one. The RST need not: RFC 7323 §3.2 requires the option on every
**non-RST** segment, and a bare RST is what a stack that has torn its state
down sends. A stray is by definition another connection's segment, and a
bare one is as plausible as any. Leave the RST and stray passes alone.

**4. Twelve bytes a segment.** Two consequences, one of them not in the
issue. Every seeded capture changes, alongside #131's. And
`max_payload` defaults to `1460` — the MSS — so a full segment with a
12-byte option region is 1472 bytes of TCP payload plus options, which puts
the frame at 1526 on a 1500-byte MTU. A real stack sends 1448. **When
timestamps are on, the generator caps a data segment's payload at
`mss - 12`.** Left uncapped, the most realistic default would generate
frames no interface would have carried.

### <a name="q5"></a>Q5 — `TCPSession` too

`TCPSession` is the second emit loop and the one the HTTP payload generator
uses. It gets the same clock and the same per-segment rule, or the two
front doors disagree about what a connection with timestamps looks like.
The standalone `tcp_handshake()` and `tcp_teardown()` helpers in
[`session.py`](../src/packeteer/generate/session.py) build their segments
with no options at all and are not a connection; leave them.
**Recommendation: both loops in the same commit** — a milestone where
`stream` negotiates timestamps and `--payload http` does not is half done.

Changelog: `Changed`, not breaking, with a plain statement that generated TCP
captures differ from 0.13.0's and why; `Added` for
`TCPStreamPacket.timestamps`. Say what `--no-tcp-options` now also removes.

Tests: every non-SYN segment carries `NOP NOP TS` when negotiated and no
option when not; TSval is monotonic per direction and tracks the packet
timestamps under jitter; TSecr on each segment equals the last delivered
TSval from the peer, including across a loss; a retransmission has a larger
TSval than its original and the same seq; a corrupted copy has the
original's; the recovery ACK carries one; the cap holds a full-MSS stream
under 1514 bytes a frame; `--no-tcp-options` produces the 0.13.0 layout;
the HTTP payload path negotiates too. Parse each generated capture back with
`parse_packet` rather than asserting on option bytes by hand.

Docs: `docs/guide/generating.md` §TCP options, `docs/api/stream-generators.md`,
`docs/cli/stream.md`, the `TCPOptions.timestamps` and `default_syn_options`
docstrings (the "deliberately absent" paragraph is deleted, not amended — the
constraint it described no longer exists).

### What #90 corrected

**The passes need no clocks handed to them.** The plan put per-direction
`(ts_base, base_usec)` on `FlowEndpoints` so the passes could stamp what
they build. Reading the code showed that the SYN and SYN-ACK already carry
everything: each has a TSval and a timestamp, and that pair *is* that side's
clock. `_clocks_from(packets)` recovers both from the handshake, so
`FlowEndpoints` is untouched and — the part that matters — the HTTP payload
path, which builds its `FlowEndpoints` in a different function from the
sessions it impairs, is in step without any plumbing. A connection that did
not negotiate gives `None`, and the passes copy verbatim as before.

**`raw[-payload_len:]` is wrong for a small payload.** The plan proposed
slicing the payload off the end of `raw` to rebuild a retransmission. A
frame below the 60-byte Ethernet minimum is padded *after* the payload, so
a two-byte sensor reading would have been rebuilt from two bytes of zeros.
The rebuild reads the payload back through the parser instead
(`_tcp_payload`), descending through any tunnel encapsulation; a test with
one- and two-byte payloads pins it.

**The monotonic clamp had an off-by-first.** The clock is clamped so capture
jitter cannot make TSval run backwards, and the first draft initialised
"last value sent" to `0` — so a seeded start above 2³¹ looked like a
2³¹-step retreat and every server TSval came out as `0`. Visible in the
first smoke test, in every `TSecr` on the client side; `ts_last` starts as
`None`.

**The RST and stray passes were right to leave alone**, for a reason the
plan half-stated: RFC 7323 §3.2 requires the option on every *non-RST*
segment, so a bare RST is not merely tolerable but ordinary.

**One test pinned "a retransmission is a byte-identical copy"** —
`test_corrupt_differs_by_exactly_one_byte` — which is the property this
issue exists to break. It now holds for a connection without timestamps,
beside a new test asserting the fresh stamp for one with them. And
`test_timestamps_are_not_advertised` inverted, as the plan predicted.

**Seeded reproducibility on the HTTP path was a near miss.** `TCPSession`
draws its ISNs from the unseeded module `random` unless given; the HTTP
path passes seeded ISNs to stay deterministic. Had the clock start followed
the ISN's source, every seeded HTTP capture would have stopped reproducing.
It draws from `loss_rng` instead — the session's one seeded generator —
and only when a clock is actually needed, so a session without timestamps
consumes exactly what it did before.

Limitation recorded, not fixed: the corruption pass does not model that a
receiver drops a corrupted segment and so never *sees* its TSval; the next
ACK's echo would in reality skip it. The pass did not model the dropped
segment's effect on the acknowledgement number either, and this follows it.

# Part 7 — the documentation sweep

After #90 (or after whichever issue is last, if #90 moves) and **before**
anything in the release checklist. One commit, like `4624f84` for 0.13.0,
with a message that says what was found — including what was found already
correct, since that is what tells the next sweep where not to look.

## What a sweep is, as distinct from an issue's docs

Every issue above lists the pages it touches, and those edits land with the
issue. The sweep is not a second copy of that list. It is a read of **every
page** with three questions: does it describe what the code does *now*, does
it still describe the *old* behaviour somewhere the issue did not think to
look, and does a page written before this milestone make a claim the
milestone has since falsified? The 0.13.0 sweep's finding — the superset
key count had drifted because kober adopted `const` — was of the third kind,
and no issue in that milestone could have caught it.

## Where this release's changes will have leaked

Each of these is a place where a page can be *correct about its own subject*
and wrong about something this release changed underneath it.

- **Every `pkt.app` / `pkt.dns` example** (#139). Six pages show one today:
  `docs/guide/parsing.md`, `docs/guide/generating.md`,
  `docs/guide/adding-a-protocol.md`, `docs/api/packet-builder.md`,
  `docs/protocols/index.md`, and `README.md`. After #139 the guidance is
  *lead with the protocol's own name, use `.app` for generic code*, and every
  page that shows the old shape without saying that is now teaching the
  second-best API. The README's quick start uses `.dns(...)`, which is still
  right; whether it should also show `pkt.sensor` for a compiled protocol is
  a README decision, below.
- **Every claim that DNS is written uncompressed** (#131). The
  `generate/dns.py` module docstring says so in its first paragraph; the
  `DNSMessage.raw` docstring, `docs/packet-spec/format.md`'s DNS section and
  `testcases/real/MANIFEST.md` all reason from it. #131 edits the ones it
  knows about; the sweep greps for `compress` and reads every hit.
- **Every description of TCP options on the handshake** (#90).
  `docs/guide/generating.md` §TCP options, `docs/cli/stream.md`'s
  `--no-tcp-options` row, `docs/api/stream-generators.md`, and the
  "deliberately absent" reasoning in `default_syn_options`.
  `docs/reference/packet-sizes.md` is a per-header table and already lists
  the Timestamps option at +10, so it is not wrong — but any worked frame
  total elsewhere that adds 20 for a data segment's TCP header now adds 32,
  and the `mss - 12` cap from #90 is worth a line on that page, since it is
  where a reader goes to ask why a full segment is 1448 bytes.
- **Every unsupported-link-type note** (#138): `docs/guide/pcap.md`'s
  wrong-link-type section, `docs/cli/file-info.md`, and `docs/api/parser.md`
  — which documents `UnsupportedIPProtocolWarning` in full and
  `UnsupportedLinkTypeWarning` not at all, a gap from 0.12.0 that #138
  should close because the link-type question is now its subject. Each
  should point at `supports_link_type` rather than leave the warning as the
  only signal.
- **`payload_offset`'s section in `docs/guide/parsing.md`** (#74) says the
  offset is the way to cite bytes; with `offsets` beside it the section
  needs to say which to use when, and the `None`-when-decoded case is the
  motivating example.
- **`--protocol-messages` in `docs/cli/stream.md`** (#137) describes the
  file as "a JSON array of packet-spec sections"; after #137 it is also a
  `parse` output, and the page should show the round trip rather than
  merely permit it.

## Transcripts and version strings

Three pages embed generated output that carries a version:
`docs/cli/protocol.md` (twice) and `docs/protocols/index.md` say `packeteer
0.13.0`. They must say `0.14.0` — regenerated, not edited, so the rest of
the transcript is checked at the same time. The 0.13.0 sweep found one of
these two releases behind; the lesson was that no test reads a version out
of a doc, and that is still true. The `Generated by packeteer …` header line
in the compiled-module transcript is the same string.

`docs/protocols/index.md`'s `packeteer protocol show` transcript and
`docs/cli/protocol.md`'s compiled-module excerpt are worth rerunning even
where the version is the only visible difference: #139's name validation
touches `check`, and #137's guard is emitted into every compiled `from_spec`,
so the excerpt of a compiled module has a new block in it.

## `README.md`

The README is read by people who will never open `docs/`, so it is held to a
different standard: not *complete*, but *not wrong* and *not missing the
headline*. Three things to check:

- **"Main features"** has a bullet for *Your own protocols* and none of it is
  wrong after #139, but `pkt.sensor` is the strongest one-line demonstration
  this milestone has that a compiled protocol is a peer of the built-ins. One
  sentence in that bullet, or one line in the Python quick start.
- **"Supported protocols"** says DNS is parsed, built and sanitised. After
  #131 "built" means built the way a resolver builds it; whether the bullet
  says *compressed* is a judgement about what a README reader wants to know
  — probably yes, in two words, because the point of #131 is that a decoder
  tested against packeteer's DNS is now shown real DNS.
- **Nothing in it describes 0.13.0's behaviour as current** where this
  release changed it: no transcript with a bare SYN, no note about
  uncompressed names, no `pkt.app` shown as the only way in.

## Module docstrings are documentation

`packeteer.protocols`, `parse/core.py`, `generate/dns.py`, `generate/tcp.py`
and `generate/tcp_stream.py` all carry module docstrings that state
behaviour, and Sphinx renders them into `docs/api/`. The sweep reads them as
pages, not as code comments. `_LEGACY_APP_ATTRS`'s comment is the obvious
one (#139's Q1 rewrites it); `generate/dns.py`'s opening paragraph is the
next.

## What the sweep is not

Not the place to write the missing page. If it finds a gap that is not this
release's doing — as 0.13.0's found `protospec` had no API reference — the
rule from `3fb11c2` applies: *the release changes X, which is a poor moment
to ship with X undocumented*. Fix it if it is this milestone's subject; file
it if it is not; do not defer it on the grounds that it was already missing.

Changelog: `Documentation`, one entry, naming what was found stale rather
than listing pages. Then, and only then, the release checklist.
