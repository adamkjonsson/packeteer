*Written 2026-09-28.*

*Status: **everything through #189 done**, released for review as
`0.17.0.dev7` (`1166866`, reviewed on the branch). kober's review of it
filed **#190** and **#191** — see [Part 7g](#part-7g). #190 and #191

The trigger is external again.
[kober](https://github.com/adamkjonsson/zipline-kober) released `0.5.0` on
2026-09-28. It is a transform release: two new field types, two new top-level
keys, string-dispatched switches, and an `examples/http.yaml` that inflates
gzip bodies. All six issues in this milestone were filed from the kober side
against 0.16.0. Five are dialect alignment. One (#169) is a CLI bug kober ran
into while building the corpus for its transform phase.

**The dialect strand** — #167, #168, #166, #170, #171 — is about the promise
0.13.0 made: a spec from either repository loads in the other, and a kober
construct packeteer lacks is *declined out loud, naming it*. Today that
promise is broken in both of its halves:

```console
$ packeteer protocol check ../zipline-kober/examples/http.yaml     # kober 0.5.0
error: http.yaml:155: units.message.fields[8].switch.cases: a switch case value must be an integer, not 'chunked'

$ packeteer protocol check src/tests/kober/http.yaml               # kober 0.2.0, vendored
…
http 1.0: 17 error(s), 2 warning(s)
```

The new `http.yaml` does not load at all. The old one loads and reports 17
errors, of which 6 are type errors the spec does not have, plus a warning that
names a declined field. The vendored copies are pinned to kober **0.2.0**, three
releases behind, so the dialect test has not seen any of this.

**The generator strand** — #169 — is the issue's larger option, chosen
deliberately: `--payload http --protocol-messages FILE` *sends* the given
messages, rather than being refused. kober's pipeline needs gzip-encoded HTTP
responses in lossy streams and currently gets them through a one-field `blob`
spec that costs it `--mss` and both directions.

**The review strand** — #174, #175, #176 — is what kober found in
`0.17.0.dev1`. One is the last leak through a stand-in that #167 missed, one
is a spelling kober takes and packeteer never did, and one is two small
wording faults. All three are dialect work, and all three land before #169.

**#178** is what kober found in #169 at `0.17.0.dev2`: the structured `http`
section cannot carry exact bytes, and a repeated header is dropped on parse.
It is the other half of #169's purpose, exact HTTP bytes in an impaired
stream, and it lands before the sweep.

**#180 and #181** are what kober found in #178 at `0.17.0.dev3`: an `http`
section's `type` accepts any value, and three edges of `raw` — an empty one,
bad hex reported in Python's words, and a repeated `Set-Cookie` folded into
one line.

**#182, #183 and #184** are what kober found in #181 at `0.17.0.dev4`: a
header list item that is not a string goes out as Python's repr, an empty
`raw` in a `dns` section is still read as absent, and a sanitised HTTP
message loses its wire shape when `raw` is dropped.

**#185** is what kober found at `0.17.0.dev5`, and it predates this release:
`sanitise --payload` leaves an HTTP body as captured, and the PII scan does
not read it.

**#186–#189** are what kober found in #185 at `0.17.0.dev6`: a crash on a
cut-off chunked trailer, a head split in the wrong place, framing lost when a
body spans segments, and data left in chunk extensions and trailers.

**#190 and #191** are what kober found at `0.17.0.dev7`: a fourth spelling of
the blank line that ends a head, and redaction to `[redacted]` changing a
TCP payload's length, so a sanitised stream gains gaps the capture never had.

## What kober 0.5.0 changed, measured against 0.16.0

Diffed `v0.2.0..v0.5.0` over kober's `loader.py`, `spec.py`, `expr.py`,
`check.py`, `docs/format/` and `examples/`. 0.3.0 and 0.4.0 changed no spec
surface; everything below is 0.5.0.

| kober change | Where | packeteer 0.16.0 |
|---|---|---|
| `transform: {from, with, limit, args, type, content_type}` | field type, switch case | Unknown key — #170 |
| `concat: repeated.member` | field type, switch case | Unknown key — #170 |
| `transforms:` — non-core transform names and their parameters' types | document | Unknown key |
| `params:` — document parameters, `{name: {type, secret, doc}}` | document | Declined, but as *unit parameters* — see #168 below |
| `switch` on a `str` dispatch, with string case keys | switch | Refused at load — #171 |
| long enum form `{doc, members}` | `enums` | Misread as values — #166 (predates 0.5.0) |
| `startswith`, `endswith` | expressions | Declined like every call; only the docs' *"kober's three functions"* is stale |
| `remaining`/`fill` reference-site rule (kober 0.3.0) | check | packeteer's since 0.13.0; nothing to do |

**#168 and kober 0.5.0 cross.** #168 was filed against kober 0.4 and says
kober has no document-level `params`. Since 0.5.0 it does — with a different
meaning (values supplied when a decode is set up, such as a key) from the unit
`params` packeteer's note describes. So #168's fix is not "take `params` and
`emit` off the document": `emit` goes, `params` stays with its new meaning,
and `transforms` joins it.

# Part 1 — #167, a stand-in nothing believes

## The bug

`loader._one_type` stands in for a declined type kind with
`BytesType(size=Remaining())` ([loader.py:566](../src/packeteer/protospec/loader.py#L566)),
so loading finishes and the checker reports every fault at once. The stand-in
has a type, and the checker believes it. The vendored `http.yaml`:

| Count | Finding |
|---|---|
| 11 | *not supported yet* — honest |
| 6 | type errors on expressions reading a `select` or `computed` field — `a size is bytes, expected int`, `the operand of 'not' is bytes`, … |
| 2 | warnings — `'body' is sized by 'content_length', which nothing derives` |

**The warnings are a second leak the issue did not name.** `content_length` is
a `select`; its stand-in has no `derive`, so the size-derivation check warns
about it. A declined field cannot be derived in any spelling, and the warning
sends the author to add something that would not help. Same fix.

`test_a_stand_in_is_not_reported_as_a_remaining` already guards the leak
through the *size*. This is the leak through the *type*.

## The fix

A dedicated stand-in type — `Declined` in `spec.py`, carrying nothing — that:

- **the expression checker treats as compatible with anything**, in every
  operand position and as every result: a `Ref` to a declined field has the
  unknown type, and an operator over an unknown operand yields the unknown
  type rather than an error. A comparison of an unknown with an int is a
  bool, as it would have been;
- **the framing checks treat as reading nothing they can reason about**:
  no *would have no bytes left*, no *has no fixed width*, no *nothing derives*
  on or because of it;
- **codegen never meets**, because a spec with any `unsupported` entry
  already stops at `check`.

It is not a `FieldType` the public model advertises for anything else. A
consumer walking a loaded spec sees `Declined` exactly where `spec.unsupported`
has an entry at the same path.

## Tests

- **The issue's assertion**, on the vendored `http.yaml`: every finding's
  message is *not supported yet*. It lands against the 0.2.0 copy here and is
  carried to the 0.5.0 copy in Part 6.
- Each of the six error shapes and the warning, minimised to one spec apiece,
  so a regression names which path leaked.
- `test_a_stand_in_is_not_reported_as_a_remaining` still passes unchanged.

## Changelog

`Fixed`: a spec with a declined construct no longer reports type errors or
derive warnings on expressions that read it; each declined construct is one
message, its own.

### What #167 corrected

**The vendored `http.yaml` went from 17 errors and 2 warnings to 11 errors**,
every one *not supported yet*. `dns.yaml` is unchanged at 4 errors and 3
warnings. Its warnings are true: `rdlength` and `length` are real integers
that nothing derives, which is why its test still holds errors only and
`http.yaml`'s now holds every finding.

**`Declined` carries the construct's name, not nothing.** A switch arm's line
in `protocol show` has no *not supported yet* marker of its own, so with a
stand-in that says nothing the arm would read `case 1: ?`. It reads
`case 1: select`, and a field reads `n: computed` where it read `bytes[rest]`.

**An operator over an unknown operand keeps its own result type.** The plan
had it yield the unknown type. But the operator decides the result: `n + 1`
is an int and `n > 0` a bool, whatever `n` turns out to be. Only a bare
reference to a declined field is `ExprType.UNKNOWN`. That is also what keeps
a real fault beside one reportable: in `n and k` with `k` an int, `k` is
still held to bool.

**Five leak paths, not two.** Beyond the type errors and the derive warning,
the old stand-in could produce:
- a `const` or `derive` error on a declined field, or a `size_of` naming one;
- a `fill` error when a declined field was in its trailer;
- *is not a unit* for a dotted path through a `pointer`;
- *unit is never referenced* for a unit reached only through a `pointer` —
  the bug kober fixed on its side as its #52.

Each has a minimal case in `TestADeclinedFieldSaysOneThing`, and so does each
kind of real fault that must still be reported beside a declined field. All of
them failed against the old code. The last needed the stand-in to remember
something: `Declined.units`, the units its body names, which reachability
follows. Recursion and run-relative extent do not, because those are
questions about size, and a declined construct has none.

**`compile_spec` compiled a declined construct.** It assumes a checked spec,
and a caller that skipped `check` got a module in which a `computed` field
was an opaque `bytes` field reading to the end of the message. With
`Declined` it would have crashed instead. It now refuses the spec, naming the
construct as `check` does.

**Declined sizes and repeats keep their old stand-ins.** Delimiter framing is
still `remaining` inside a real `string`, and `until` is still no repeat. The
field's value type is right in both cases, and `_stands_in_for_unsupported`
already guards the shape checks against them.

# Part 2 — #168, and kober's new document keys

## The fix

`_SPEC_KEYS` ([loader.py:88](../src/packeteer/protospec/loader.py#L88))
spreads `_UNSUPPORTED_KEYS` — `params` and `emit` — into the document level.
It becomes kober 0.5.0's document keys plus packeteer's two:

| Key | Document level, after |
|---|---|
| `emit` | **Unknown key.** A typo in both dialects; kober refuses it too |
| `params` | Declined: *document parameters, supplied when a decode is set up* — kober 0.5.0's meaning, not the unit one |
| `transforms` | Declined: *declarations of the transforms a spec uses* |

The unit and field levels do not change: `emit` is declined on a unit and a
field, `params`/`args` on a unit, `confirm`/`reject` on a unit.

`_UNSUPPORTED_KEYS` splits accordingly — a document table and a unit table —
so no key reaches a level by being spread into a set that is not its own. That
spreading is the bug's actual cause.

## Tests

- A top-level `emit:` is an unknown key, with the known keys listed.
- A top-level `params:` in kober 0.5.0's shape and a `transforms:` are each
  declined once, naming the construct.
- A unit `params:` is still declined as unit parameters.

## Changelog and docs

`Fixed`: a top-level `emit` is an unknown key, as in kober; `params` at the
top level is declined as kober 0.5.0's document parameters. `Added` (to the
recognised set): top-level `transforms`. The table in
[format.md](../docs/protocols/format.md) — *Keys that are kober's alone* —
gets `emit` at `unit, field`, and rows for document `params` and
`transforms`.

### What #168 corrected

**Nothing, beyond the plan's own `Added`.** The split is two tables,
`_UNSUPPORTED_DOC_KEYS` and `_UNSUPPORTED_UNIT_KEYS`, and `_UNSUPPORTED_KEYS`
is gone, so no key can be spread into a level again by accident. A field's
`emit` reads its note from the unit table, since it means the same thing.

**The document keys report their own line.** They were recorded at the
document's location, line 1. Each now carries its value's line, as a unit
does.

**The shapes are not checked.** A declined document `params` or `transforms`
is recorded whatever its body, as a declined `select` is. kober checks them,
and a spec with a malformed one fails `kober check`, which is where an author
writing for kober finds out. Part 4 checks `transform`'s shape, because a
field that uses one is kober's commonest new construct, where these two
blocks are declarations.

# Part 3 — #166, the long enum form

## The fix

`_enum_def` ([loader.py:438](../src/packeteer/protospec/loader.py#L438)) reads
the body straight as the member mapping. It learns the long form, by the
pattern a unit already uses for `doc` beside `fields`:

- a body with `members` → the members are under it, and `doc` is the enum's;
  any other key is unknown;
- otherwise → the body is the members, as now;
- a body with `members` **and** integer keys → refused by name, as a mix of
  the two forms.

`EnumDef` gains `doc: str | None = None`. `packeteer protocol show` prints it
the way it prints a unit's.

## Tests

The long form loads and names its members; the doc reaches `show`; the mix is
refused; the short form is unchanged. A case in `test_kober_dialect.py` of its
own, since neither vendored spec writes the long form — which is why nothing
saw this.

## Changelog and docs

`Fixed`: the long enum form loads. `Added`: `EnumDef.doc`. The Enums section
of `format.md` shows both forms.

### What #166 corrected

**The rule is kober's, checked against its loader.** kober's `_enum` treats
anything without `members` as the short form, and with `members` allows only
`members` and `doc`. packeteer does the same. Where kober would report a
stray key as *unknown* or a `doc` as *not an integer*, packeteer names the two
mistakes the forms invite: a member written beside `members`, and a `doc` in
the short form.

**A fault in a member is reported under `enums.NAME.members`**, and the
enum's own location stays the enum's.

**An aside while testing: both dialects put `enum` inside the integer's
body**, `int: {bits: 4, enum: opcode}`. `{bits: 4, enum: opcode}` on the field
is refused in both, and kober's `types.md` says so. No gap there.

# Part 4 — #170, `transform` and `concat` declined by name

## The fix

Both join `_UNSUPPORTED_TYPES`, so they are known type kinds — on a field, and
as a switch arm — and each is declined once at its own line:

- `transform` — *bytes after a named transform (decompression, decryption);
  building one needs the inverse transform*;
- `concat` — *one member of every element of a repetition, joined*.

Their shape is still checked, so a typo inside a declined construct is still a
typo: `transform` requires `from`, `with` and `limit` and allows only
`{from, with, limit, args, type, content_type}`; `concat` must be a
`repeated.member` string. Their stand-in is Part 1's `Declined`, which is why
this follows #167.

**Building** a transform — compressing or encrypting on the way out — is not
this issue. `format.md` says so in the *not supported yet* table.

## Tests

The issue's own spec: one finding per construct, both *not supported yet*,
nothing else. A `concat` as a switch case. A `transform` missing `limit` is a
shape error, not a decline.

## Changelog

`Added`: `transform` and `concat` are recognised and declined by name, so a
kober 0.5.0 spec using them loads and is checked.

### What #170 corrected

**The shape rules are kober's loader, read rather than inferred.** kober's
`_transform` also refuses a `limit` that is not positive, and parses `type` as
a field type. packeteer does both. A `transform`'s `type` is built for its
faults only, so a construct this version lacks nested inside it is recorded
and reported like any other.

**#167 paid for itself here.** A unit reached only as a transform's `type`
is not reported as unreachable, because `Declined.units` remembers it. Before
#167 that would have been a new leak for this issue to close.

**kober 0.5.0's `http.yaml` now stops at one error**, the string switch case
at line 155, which is #171. The loader got past every `concat` and
`transform` in it.

# Part 5 — #171, a switch dispatched on a string

## Decided: accept, check, decline

kober switches on strings because its expression language has no conditional
and refuses a switch on a bool. Every string switch that exists — both of
`http.yaml`'s — dispatches on a `select` or on a header value through
`lower`/`trim`, all of which packeteer declines. The only string dispatch
packeteer could *build* is a fixed-width ASCII tag (PostgreSQL's one-byte
message type, a RIFF chunk's four characters), and every such protocol is
already writable as an integer switch with an `enum`. Building string
dispatch would buy readability for a construct with no current user, at the
cost of codegen, an encoder that picks a case by exact string equality, and
padding questions. It becomes its own issue when a protocol asks for it.

## The fix

- **The loader accepts string case keys.** `_int_key` for switch cases
  becomes a key reader for either type; enum keys stay integer-only. One
  switch may not mix the two.
- **The checker holds the keys to the dispatch's type** — string keys need a
  `str` dispatch, integer keys an int one — and, when the dispatch is a
  fixed-width string field, holds each key's length to that width, which is
  cheap and catches the `"fmt "` missing its space.
- **A string-dispatched switch is declined** at its line: *not supported yet:
  a switch dispatched on a string*. Its stand-in is `Declined`, so fields
  reading it stay quiet, and the rest of the spec is checked.
- **A switch whose dispatch is itself declined** reports only the dispatch's
  decline and its own — not a type mismatch against `Declined`.

`Switch.cases` becomes `Mapping[int | str, FieldType]` in the public model.

## Tests

The issue's spec: loads, one *not supported yet* for the switch, nothing
else. Mixed keys refused. String keys under an int dispatch refused, and the
reverse. A key the wrong length for its fixed-width dispatch refused.

## Changelog

`Added`: string switch cases are recognised and declined. `Changed`:
`Switch.cases` keys are `int | str` — not **Breaking** for a spec, but a
consumer that type-narrows the model's keys should know.

### What #171 corrected

**The attribute is `Switch.arms`, not `Switch.cases`.** The plan named the
spec key. The model's attribute is what changed type.

**The switch keeps its real type; it gets no stand-in.** The plan gave it

**A key is kober's `_case_key`, read rather than inferred**: an integer where

## #174 — the last leak through a stand-in

**The bug.** #167 closed five leak paths and missed the sixth: the terminal
rule. `_check_remaining` and `_check_run_relative` refuse *any* field after a
`remaining`, including a declined one that reads nothing where it stands. A
`computed` after a `remaining` is correct — it reads no byte — and kober
accepts it. The `transform` case is the one that matters: a header, a sealed
payload sized `remaining`, then the transform that opens it is the shape
kober's tunnel example is written in and its docs teach. That spec is told to
change a size that is right.

**The fix.** One predicate, `_reads_nothing(field_type)`, kober's
`kober.check._reads_nothing` exactly:

- a `Declined` field reads nothing. Every construct packeteer declines as a
  type — `computed`, `select`, `pointer`, `concat`, `transform` — is one
  kober classifies that way;
- a `Switch` reads nothing when every case, and its default if it has one,
  reads nothing: the `content` switch in kober's `http.yaml`, whose arms are
  all transforms;
- anything else reads.

It is applied wherever "decoded after it" is asked:

- `_check_remaining`: the field that would be starved is the first one after
  the `remaining` that **reads**. None → no error.
- `_check_run_relative`: likewise, for a run-relative unit referenced from a
  field followed only by fields that read nothing.
- **`fill`'s trailer, for agreement.** Today a trailer holding a declined
  field skips the `fill` check entirely (#167's guard), which is lenient in
  the wrong place: a genuinely variable field beside a declined one goes
  unreported. With the predicate, a field that reads nothing has width 0
  in `trailing_width`, and the check runs on the rest. The issue observes
  that the two rules disagree about the same field; after this, one
  predicate answers for both.

### What #174 corrected

**Nothing in the design.** `_reads_nothing` is kober's, and one predicate now
answers for all three rules. The `remaining` and run-relative rules name the
first field after that *reads*, which the old rule got wrong in a second way:
with `remaining`, then a `computed`, then a real byte, it blamed the
`computed`.

**The `fill` guard narrowed rather than went.** A trailer field that stands
in for a declined *size* or *repeat* — delimiter framing, `until` — still
skips the check. Its width is unknown, where a field that reads nothing has
width 0, so only the declined type kinds are measured.

**`_fixed_bits` gives width 0 for a field that reads nothing**, whatever its
`repeat` or `condition`. That also reaches the stream prefix proof, where a
`computed` before the length field no longer breaks the fixed offset, and
that is right for the same reason.

**The reference says it now.** `format.md`'s *measured against the message*
section defines "decoded after it" as read from the input after it, and
names the constructs that may follow.

**Tests.** The issue's five variants, one each: `computed`, `select`,
`concat`, `transform`, and a `switch` of transforms after a `remaining`,

- **the tunnel spec**, in `test_kober_dialect.py`, as the issue asks: only

## #175 — a bare integer is an expression

**Wider than the issue.** kober's `_expr` takes a bare integer as a literal
in *every* expression position and refuses a boolean by name. packeteer reads
all four positions as text: `count`, `size: {expr: …}`, `dispatch`,
`condition`. `count: 2` is the one a spec author meets, but `dispatch: 0` or
`{expr: 4}` are the same refusal, and one helper fixes all four.

**The fix.** `_expr_source(value, loc, what) -> str` in the loader: text is
returned as it is, an integer becomes its literal, and a boolean or a float is
refused with the YAML hint `_yaml_hint` already gives. The message names what
was expected — *an integer or an expression*, not *a string*. The model is
unchanged: `Count.expr`, `FromExpr.expr`, `Switch.dispatch` and
`Field.condition` stay source text, so nothing downstream can tell which
spelling was used. That is the rule the shorthands follow.

`condition: 1` then loads and is refused by `check` as an int where a bool is
wanted, which is right and is what kober does. A negative literal count loads
too, as in kober. Whether `count: -1` should be refused is a question for both
projects, and not this issue.

### What #175 corrected

`condition`, `size: {expr: …}`, `dispatch` and `count`. A `transform`'s
`args` are expressions too, but they are declined and their values are not
read. The refusal says *must be an integer or an expression*, where it said
*must be a string*, which was only true of packeteer.

**Tests.** `count: 2`, `repeat: {count: 2}`, `{expr: 4}` and `dispatch: 0`

# Part 7 — #169, `--payload http` sends the given messages

## The bug

`_cmd_stream` routes `--payload http` to `_generate_http_payload_stream`
before `--protocol-messages` is ever read
([__main__.py:1968](../src/packeteer/__main__.py#L1968)). The flag is accepted
and dropped — #137's shape.

## Why this is smaller than it looks

- **`http` is already a registered protocol**
  ([app/http.py](../src/packeteer/app/http.py)) with a `from_spec` building an
  `HTTPRequest` or `HTTPResponse` from a section. Every shape
  `--protocol-messages` takes for other protocols — bare sections, sections
  under `"http"`, a `packeteer parse` document — already works for it.
- **Its sections round-trip exactly.** `body` is hex and written verbatim;
  the encoder adds `Content-Length` only when no framing header is present.
  A gzip body with `Content-Encoding: gzip` goes out byte for byte, and a
  chunked one keeps its framing, because `parse_http` keeps it.
- **The generator already renders a message list.**
  `generate_http_conversation` returns `list[AppMessage]` — direction, bytes,
  label — and `render_tcp_session` does the handshake, MSS, loss and teardown.
  Given messages are that list, supplied instead of generated.

## The fix — API first

- **`HTTPRestConfig.messages: Sequence[HTTPRequest | HTTPResponse] | None =
  None`.** The config is the content-knobs object, so it belongs there. When
  set, the random-content knobs (`methods`, `resources`, `hosts`, `base_path`,
  `error_rate`, `chunked_rate`, `chunk_size`, `trailer_rate`) do not apply;
  `syn_options` and `impairments` do.
- **Direction from type**: a request is client→server, a response
  server→client.
- **A transaction is a request and the responses after it**, so
  `requests_per_connection` cuts the list into connections as it cuts
  generated traffic. A list starting with a response is refused, naming the
  index.
- **The list cycles** to reach `requests` transactions, as
  `protocol_payload_fn` cycles to reach `--packets` — a shorter list must not
  silently shorten the stream, and `--payload dns` and `--payload http` should
  not disagree about that ([Q1](#q1)).
- **Headers are not rewritten.** `Connection: keep-alive`/`close` are sent as
  written; given messages mean exact bytes.
- **Sessions replay the list**; the seed still drives ISNs, stagger and
  impairments.
- **`app.protocol_messages(proto, messages) -> list[object]`**: the up-front
  decode `protocol_payload_fn` already does, factored out and public, so the
  CLI and an API caller turn a sections file into messages the same way.

## The CLI

- `_generate_http_payload_stream` reads `--protocol-messages` through
  `app.protocol_messages(http.PROTOCOL, …)` and passes the result in the
  config. `__main__.py` gains a few lines, not logic.
- The help text for `--protocol-messages` stops calling `http` special.
- **No flag accepted in silence.** `--error-rate`, `--chunked-rate`,
  `--min-chunk`, `--max-chunk` and `--trailer-rate` default to `None` on the
  command line, so a flag the user set is distinguishable before
  `_apply_stream_defaults` fills them; any of them with `--protocol-messages`
  is refused, saying it does not apply to given messages. The same keys set
  in a `--config` file are refused too, naming the file key ([Q2](#q2)).

## The port-clash message

Also in the issue: a spec whose `ports` clash with a registered protocol's
fails with *"generated module does not import (ProtocolError: …); this is a
bug in packeteer's compiler, not in the spec"*
([codegen.py:196](../src/packeteer/protospec/codegen.py#L196)). The clash is
the spec's. It is checked before codegen, as a spec error at the `ports:`
line naming the protocol that holds the port.

## Known limit

`headers` is a dict, so a message with a repeated header name — two
`Transfer-Encoding` lines, which kober 0.5.0's `http.yaml` now reads as one
list — cannot be expressed. Documented, not fixed here: fixing it means

`Added`: `HTTPRestConfig.messages`, `app.protocol_messages`, and

# Part 7b — #178, exact HTTP bytes

kober reviewed `0.17.0.dev2` (cited as `8531b14`, PR #177's merge of
`fff4e8a` into `main`) and confirmed #174–#176. With the earlier review,
everything this release does on kober's behalf checks out against kober
0.5.0, and #178 is the one open item.

## What it is

#169 works for well-formed HTTP. kober's compressed-body corpus goes through
at `--mss 200` byte-exact in both directions, and 25 of 25 bodies inflate.
What is missing is **exact** bytes. The structured `http` section is rebuilt
by the encoder, which normalises what real traffic does not:

| Sent | On the wire |
|---|---|
| `Transfer-Encoding: gzip` then `Transfer-Encoding: chunked` | only `Transfer-Encoding: chunked` |
| `CONTENT-LENGTH:2` | `CONTENT-LENGTH: 2` |
| `Transfer-Encoding:  Gzip,  Chunked ` | `Transfer-Encoding: Gzip,  Chunked` |
| `HTTP/1.0 204` (no reason phrase) | `HTTP/1.0 204 ` |

The first row changes what the message means: RFC 7230 §3.3.1 reads two
`Transfer-Encoding` headers as one list, and with `gzip` gone the body is
framed differently. The rest are the shapes a decoder's tests need, and
kober's HTTP spec has a test for each.

**The dropped header is a parse bug too, not only an input one.**
`parse_http` builds `headers` as a dict, so a repeated name keeps its last
value and the first is lost — in `packeteer parse` output as well, silently.

**The corpus is unaffected.** All four HTTP messages in the real-capture
corpus re-encode to their exact bytes, so a `raw` written only when needed
changes none of its parse output.

## The fix — decided

Both of the plan's questions were settled as recommended:
- **`parse` writes `raw` for non-canonical HTTP.** More than the issue asks,
  but it is DNS's precedent, and it is what makes a capture replay exactly.
- **A repeated header is combined, not refused.** Refusing could only happen
  at parse time, where it would make real traffic fail to parse.

### 1. `raw`, as DNS has it, in all three places

- **The message.** `HTTPRequest` and `HTTPResponse` gain `raw: bytes = b""`,
  documented as `DNSMessage.raw` is. `encode` returns it as it is when set,
  and it wins over the structured fields.
- **The section.** `from_spec` reads a `raw` key, in hex. Direction comes
  from an explicit `type` beside it, else from the bytes: a start line
  beginning `HTTP/` is a response, anything else a request. When the bytes
  parse, the structured fields are filled from them, so labels and
  `--requests` grouping see a real method and status. Bytes that do not
  parse, deliberately malformed ones, are still sent, with the type their
  start line gives. `_SECTION_KEYS` gains `raw`.
- **Parse.** `decode` sets `raw` only when re-encoding the decoded message
  would not reproduce the message's bytes, and `to_spec` writes it then, as
  `_apply_dns` does. The comparison is against the message itself — start
  line, headers, separator, and the body `parse_http` kept — not the rest of
  the segment.
- **Sanitise.** `sanitise` drops `raw` whenever it changes the section,
  exactly as for DNS. This is the part that matters for safety: a redacted
  `Authorization` header left in `raw` would be written back verbatim, and
  would redact nothing.

### 2. A repeated header is combined

`parse_http` joins a repeated field's values with `", "` in order, as RFC 7230
§3.2.2 allows for any field defined as a list. `Transfer-Encoding: gzip` and
`Transfer-Encoding: chunked` become `gzip, chunked`, which means the same
thing. The combined form re-encodes to different bytes, so `raw` is written
and the wire keeps both lines.

`Set-Cookie` is the one field RFC 7230 names as not combinable. It is joined
the same way in the structured form, which is lossy for it alone, and `raw`
carries it exactly. Headers as a list of pairs is #172, and stays out of this
milestone: it is a breaking change to a packet-spec key.

## Tests

- **The issue's table**, row by row: each message round-trips through
  `decode` → `to_spec` → `from_spec` → `encode` to its exact bytes.
- **`{"raw": …}` alone** is enough for `--protocol-messages`: a request and a
  response from bytes, in the right directions, byte-exact on the wire at a
  small `--mss`, with an explicit `type` and without.
- **Malformed bytes** that do not parse are still sent, typed by their start
  line.
- **A canonical message gets no `raw`**, and neither does anything in the
  real-capture corpus: the parse output of `http_body.pcap` and `tcp_v4.pcapng`
  is unchanged.
- **Repeated headers**: `gzip` then `chunked` parses to `gzip, chunked` with
  `raw` set, and `raw` reproduces both lines.
- **Sanitise**: a section with `raw` and an `Authorization` header comes out
  with the header redacted and no `raw`. One with nothing to redact keeps its
  `raw`.

### What #178 corrected

**The design held.** `raw` sits in the same three places as DNS's: the
message, the section, and the parse and sanitise hooks, with the same rule
for dropping it. The corpus check held too: no message in it gains a `raw`,
and a test pins that.

**`Content-Length` was matched by two spellings only**, `Content-Length` and
`content-length`, so `CONTENT-LENGTH:2`, one of the issue's own rows, never
trimmed its body. The combining pass already keys headers by their
lower-case name, so the lookup uses that, and it is under `Fixed` with the
repeated header.

**`raw` is the message, not the segment.** A Content-Length body can be
followed by the next message in the same segment, and `raw` holds only the
start line, headers, separator and the body `parse_http` kept. A test pins
that.

**A `raw`-only section decodes its bytes for the fields**, then carries the
bytes as given, even when they were canonical, since they were given to be
sent. A `type` that disagrees with the start line wins, and so do bytes that
do not parse: both are sent as given, as the type asked for.

**Header redaction is opt-in** (`SanitiseOptions.http_headers`). With it off
nothing changes, so `raw` stays; with it on, a redacted `Authorization`
takes `raw` with it and the secret does not reach the wire. Both are tested,
as is a section with nothing to redact keeping its `raw`.

**Through the CLI at `--mss 200`**, a `raw`-only file with two
`Transfer-Encoding` lines and a gzip body arrives byte-exact in both
directions, split over 18 server segments.

## Changelog

`Added`: `raw` on HTTP messages and sections. `Fixed`: a repeated header is
combined rather than dropped, and a non-canonical HTTP message now rebuilds
byte for byte from `packeteer parse` output. No `Security` entry: the
sanitise rule ships in the same change as the key, so no release ever
carries a `raw` that survives redaction.

milestone, all four findings reproduced on `v_0.17.0` before planning:

```text
#180    {"raw": <a response>, "type": "respnse"}  → built as an HTTPRequest
#181.1  {"raw": ""}                                → GET / HTTP/1.1\r\n\r\n
#181.2  {"raw": "zz"}                              → non-hexadecimal number found in fromhex() arg at position 0
#181.3  Set-Cookie: a=1; Expires=Wed, 21 Oct …    → {'Set-Cookie': 'a=1; Expires=Wed, 21 Oct …, b=2'}
        Set-Cookie: b=2
```

## #180 — `type` is `request` or `response`

**The bug.** `from_spec` reads a section as a response when `type` is
`"response"` and as a request otherwise, so any other value is a request.
That was true of structured sections in 0.16.0. Since #178 it matters more,
because `type` overrides the direction a `raw` start line gives: one
misspelling sends a response's exact bytes from the client, and the run
reports success.

**The fix.** `type` must be `"request"` or `"response"`. Anything else is
refused by name, *http: type must be 'request' or 'response', not
'respnse'*, which reaches the CLI as *message 1: …* through
`protocol_messages`. An absent `type` keeps its meaning: for `raw`, the start
line decides; otherwise the section is a request.

**Tests.** The issue's two misspellings, `respnse` and `reqest`, each refused
naming the value, with and without `raw`. An absent `type` still infers from
a `raw` start line and still makes a structured section a request.

### What #180 corrected

**Nothing in the design.** The check sits before `raw` is read, so it holds
for both kinds of section. `Response`, capitalised, is refused too: the
spelling is exact, as every other packet-spec key is. The CLI's message reads
*message 1: ValueError: http: type must be …*, with the class name in it
because `protocol_messages` reports every section error that way, including
*not a http section*. Dropping it is a change to all of them, and not this
issue.

## #181 — three edges of `raw`

### 1. An empty `raw` is refused — decided

`{"raw": ""}` was taken as absent, and a default `GET / HTTP/1.1` went on the
wire in its place, which contradicts `raw` winning over the fields. **Refused**
as *http: raw is empty*, rather than sent as nothing: a message of no bytes is
not a message in a TCP stream, and `parse` never writes an empty `raw`.

### 2. Bad hex is reported in packeteer's words

`bytes.fromhex`'s own message names neither the protocol nor the key. The
same call reads HTTP's `body` and DNS's `raw`, so all three move to one
helper, `_hex(section, key, protocol)`, which says *http: raw is not hex:
non-hexadecimal number at position 0*. DNS's `raw` is not in the issue, but it
is the same fault in the same kind of key, and one helper fixes it.

### 3. A header value may be a list — decided

**The bug.** #178 combined a repeated header with `", "`. That is right for a
list-valued header, and the plan knowingly accepted it for `Set-Cookie`,
which RFC 7230 §3.2.2 names as the exception. The review showed the cost is
larger than the plan said. A cookie's `Expires` contains a comma, so the
folded value is ambiguous. And `sanitise --http-headers` drops `raw` as it
redacts, so a capture with two `Set-Cookie` lines is rebuilt with one: a
different number of headers than the decoder under test saw on the wire.

**The fix: a header's value may be a list of strings**, one line per item, in
order.

- **Encoding.** `_build_http_message` writes each item of a list as its own
  line under the same name. A string is one line, as now. The
  `Content-Length` and `Transfer-Encoding` presence checks see a name
  whatever its value's shape.
- **Parsing.** A repeated `Set-Cookie` becomes a list. Every other repeated
  header is combined as #178 made it, since for them the combined form means
  the same and a string is what every consumer expects. With `Set-Cookie`
  held apart, the fields rebuild such a message exactly, so it no longer
  needs `raw` on that account.
- **Input.** Any header may be written as a list, so two `Transfer-Encoding`
  lines can be written without `raw`.
- **Sanitise.** A sensitive header that is a list is redacted item by item,
  `["[redacted]", "[redacted]"]`, which keeps the line count. That is kober's
  point.
- **The model.** `HTTPRequest.headers` and `HTTPResponse.headers` become
  `dict[str, str | list[str]]`. That goes under **Changed**: a consumer that
  assumed a string meets a list only where the old output was wrong.

**#172 is mostly covered.** It asked for headers as a list of pairs so a name
could repeat. List values give that without changing the format for anyone
else. What they do not give is order across names, `A, B, A`, which is what
keeps #172 open. Its issue gets a note when this lands.

**Tests.**
- The issue's cookie with an `Expires` round-trips through the fields alone,
  two lines, no `raw`.
- A list-valued `Transfer-Encoding` on input encodes as two lines.
- `sanitise --http-headers` on two `Set-Cookie` lines leaves two redacted
  lines.
- A repeated non-cookie header still combines to a string.
- An empty `raw`, and bad hex in `raw`, `body` and DNS's `raw`, each refused
  naming protocol and key.

### What #181 corrected

**The hex helper is public**, `packeteer.protocols.section_bytes`, beside
`check_section`, since it is the same kind of `from_spec` guard and a
hand-written protocol wants it too. It says which character is wrong and
where, or that the digits are odd in number, rather than Python's message.

**Hex is read in more places than the plan named**: DHCP's option `data` and
`trailer`, DNS RDATA's nested `data`, and a compiled protocol's `bytes`
fields. The plan's three — HTTP `raw` and `body`, DNS `raw` — are done. The
rest have the same fault. They are left for an issue of their own, since the
nested ones want a path in the message, `answers[2].data`, which one key
cannot give.

**An empty DNS `raw` keeps its meaning**, absent. It is not in the issue,
`b""` is `DNSMessage.raw`'s default, and nothing was ever sent in its place.

**The design held for list values**, and it removed one reason for `raw`: a
message whose only oddity was a repeated `Set-Cookie` now rebuilds from its
fields, so `parse` no longer writes `raw` for it. The encoder, the parser and
`sanitise` were the only three places that read a header's value, which is
what kept the change to three.

## Changelog

- #180 under `Fixed`: a misspelt `type` is refused rather than read as a
  request.
- #181.1 and .2 under `Fixed`. #181.3 under `Added` (list-valued headers) and
  `Changed` (the model's header type, and a repeated `Set-Cookie` in `parse`
  output becoming a list). #178's `Fixed` entry about combining gets a
  clause saying `Set-Cookie` is kept apart, since it is still unreleased.

# Part 7d — #182, #183 and #184, what the review of `.dev4` found

kober reviewed `0.17.0.dev4` (`26edd4f`) on the branch, with no PR to
`main` this time. Three issues, all on this milestone, all reproduced on
`v_0.17.0` before planning:

```text
#182  "Set-Cookie": [["a=1"]]   → Set-Cookie: ['a=1']
      "Set-Cookie": [{"x": 1}]  → Set-Cookie: {'x': 1}
      "Set-Cookie": [true]      → Set-Cookie: True        (not in the issue)
#183  {"raw": "", "id": 7}      → a DNS message built from id, raw ignored
#184  Set-Cookie, Content-Length, Set-Cookie   → sanitise → the two Set-Cookies together
      Transfer-Encoding ×2, Set-Cookie         → sanitise → one Transfer-Encoding line
```

## #182 — a header value is a string, or a list of them

**The bug.** #181 writes a list item with `str()`, so a nested list or a
dict goes on the wire as Python spells it, and the run reports success.
Those are bytes the section did not say, which is what #181 set out to stop.

**The fix.** `from_spec` accepts a header value that is a string, an integer
taken as its digits as now, or a list of those. Anything else is refused,
naming the header and, in a list, the item: *http: header 'Set-Cookie' item 0
must be a string, not list*. A boolean is refused too, though Python counts
it as an integer, since YAML writes `yes` as one and `True` is no header
value anyone meant. An empty list stays no line, as now.

**Tests.** Each shape in the issue's table and the two above: a nested list,
a dict and a boolean, as an item and as the value itself, each refused
naming header and item; strings, integers and an empty list unchanged.

### What #182 corrected

**`headers` itself is checked too**: an array where an object belongs was an
`AttributeError` out of `.items()`, and is now *http: headers must be an
object, not list*. A `null` or a float value is refused like a boolean.

**`headers` beside a `raw` is not checked.** `raw` wins, and those headers
are never read, let alone sent, so refusing a bad one would refuse a section
for something with no effect.

## #183 — an empty `raw` is refused for DNS too

**The bug.** #181 refused an empty `raw` for `http` and, by this plan's own
call, left `dns` reading one as absent. kober's point is the better one: a
`raw` that is present says to send exactly its bytes, in either protocol,
and building a message from the other fields instead is output the author
did not write. It is how kober gets a compressed DNS response into a
stream, so an empty one is a mistake in whatever wrote the file.

**Safe to change.** Nothing in packeteer writes an empty `raw`: `parse`
omits it when there is none, and `sanitise` deletes the key rather than
blanking it.

**The fix.** The check moves out of `app/http.py` into a helper beside
`section_bytes`, `section_raw(name, section) -> bytes | None`: `None` when
`raw` is absent, the bytes when it is present, and the same refusal for both
protocols when it is empty — *dns: raw is empty; give the message's bytes,
or leave raw out to build the message from the other fields*. A protocol
with a `raw` key later has one call to make.

**Tests.** `{"raw": ""}` refused for `dns` with the message; for `http` as
before, now through the shared helper; an absent `raw` unchanged for both.

### What #183 corrected

**Nothing in the design.** `section_raw` is public beside `section_bytes`,
returns `None` for an absent `raw`, and HTTP's own empty check is gone into
it. The two changelog entries became one, since #183 finishes what #181
started. #181's plan note that an empty DNS `raw` "keeps its meaning" is left
as written, as a record of the call this issue reversed.

## #184 — sanitise redacts inside `raw` — decided

**The bug.** `sanitise --http-headers` drops `raw` whenever it redacts, and
the message is rebuilt from its fields, which group a repeated header under
one name and combine every repeated header but `Set-Cookie`. Nothing changes
meaning under RFC 7230, but a sanitised capture stands in for a real one,
and a decoder's tests are about exactly this shape: kober's HTTP spec has a
test for two `Transfer-Encoding` lines, and after sanitising the capture no
longer has that case. #181's changelog claim that a message "keeps its
number of lines" was only half true.

**The fix: redact within `raw`, and keep it.** When a section has `raw` and
header redaction is on, `sanitise` rewrites the value of each sensitive
header line in the raw bytes to `[redacted]` and leaves every other byte as
it was: order, repetition, spacing, line endings, the body. The structured
`headers` are redacted the same way, so the two agree, and `raw` stays, so
the rebuilt message is the captured one less its secrets.

- **Which lines.** The header block is the bytes before the first blank
  line, split on its line endings, CRLF or bare LF. A line is a sensitive
  header when its name, before the colon and case-insensitively, is in the
  set `_sanitise_http` already uses. Its value — after the colon and any
  whitespace, up to the line ending — becomes `[redacted]`; the name, the
  colon and the spacing after it are kept.
- **The fallback is today's behaviour.** Anything the rewrite cannot read
  with certainty drops `raw` as #178 does, and the message is rebuilt from
  its redacted fields: bytes with no header/body separator, a start line
  that does not parse, a header line without a colon, and above all an
  obs-fold continuation line — one beginning with whitespace — since a
  secret folded onto it would survive a line-by-line rewrite. The rule is
  that `raw` survives sanitise only when every line of its head was read.
- **What else changes in `raw`.** Nothing. A body is not redacted today
  either, and redacting headers shortens or lengthens only the head, so no
  length the message declares — `Content-Length`, chunk sizes — is
  affected.
- **DNS keeps dropping `raw`.** Its names are compressed, and a redacted
  name cannot be written in place.

**Docs.** `sanitise`'s help and the CLI page say what happens to an HTTP
message: redacted in place when its head can be read line by line, rebuilt
from its fields otherwise, with what rebuilding changes — repeated headers
grouped, and every repeated header but `Set-Cookie` combined. #181's
changelog entry is corrected in place, since it is still unreleased.

**Tests.**
- The issue's two cases keep their shape through `sanitise --http-headers`:
  `Set-Cookie` lines apart around `Content-Length`, and two
  `Transfer-Encoding` lines, each sensitive value `[redacted]`, every other
  byte unchanged.
- Spacing kept: `Authorization:Bearer x` becomes `Authorization:[redacted]`,
  and one with two spaces keeps them.
- Bare-LF line endings kept.
- Each fallback, a folded line above all, drops `raw`, and the secret does
  not reach the wire either way.
- With nothing to redact, `raw` is unchanged, as now.

### What #184 corrected

**The design held, fallback and all.** `_redact_raw` reads the head
`parse_http` reads, splitting on the same separator, and rewrites only the
value of a sensitive line: `Authorization:Bearer x` becomes
`Authorization:[redacted]`, `Host:  h` keeps its two spaces, bare-LF endings
stay bare. It returns `None` for anything it cannot read, and `sanitise`
then drops `raw` as before. Of the fallbacks, a folded continuation line and
a line without a colon are tested, and in both the secret does not reach the
wire.

**It only runs when something was redacted**, the same condition #178 used
to decide whether to drop `raw`. With nothing sensitive in the message, or
header redaction off, `raw` comes back byte for byte.

**Through the CLI**, `stream` with `raw` sections then `packeteer sanitise
--http-headers` gives back `Set-Cookie`, `Content-Length`, `Set-Cookie` in
that order, each cookie `[redacted]`. That is the issue's first case, which
used to come back regrouped.

**Four places said `sanitise` drops `raw`**: `HTTPRequest.raw`'s docstring,
the `http.raw` reference, and #178's and #181's changelog entries. #181's
"keeps its number of lines" was only half true. All four are corrected in
place, and the `--http-headers` help and the sanitise CLI page now describe
both outcomes.

## Changelog

- #182 and #183 under `Fixed`.
- #184 under `Changed`: `sanitise` now redacts an HTTP message's `raw` in
  place rather than dropping it. #178's entry, which says `sanitise` drops
  `raw` whenever it redacts, and #181's, which says the line count is kept,
  are corrected in place, since both are still unreleased.

# Part 7e — #185, an HTTP body that `--payload` did not zero

kober reviewed `0.17.0.dev5` (`00a5ddb`) on the branch. One issue, on this
milestone, reproduced on `v_0.17.0` before planning:

```text
stream --payload http --protocol-messages login.json   (a login request, a response with an email)
sanitise login.pcap --payload --http-headers
  → POST /login … Host: [redacted] … user=alice&password=hunter2!!
  → HTTP/1.1 200 OK … Set-Cookie: [redacted] … {"email":"a@b.com"}
```

The headers are redacted, and both bodies go out as captured, with no
warning, whether the messages were `raw` or structured. **It is not new**:
v0.16.0 does the same. It is the failure `_warn_undecoded` exists to prevent
for undecoded frames — a sanitised file, and one that merely looks
sanitised — reached another way, and it is why this goes under `Security`.

## Why

- **`--payload` zeroes a packet's top-level `payload`** and its SCTP chunk
  fields, and nothing else. Once `parse` has decoded a TCP payload into an
  `http` section, the message is rebuilt from that section — its `raw`, or
  its fields — and neither `body` nor `raw` is touched.
- **The PII scan reads every string in a section**, but `body` and `raw` are
  hex, so the text of a body is never scanned. That is where a password or an
  email is likeliest to be.

## The fix — decided as recommended

### 1. With `--payload`, the body is zeroed

In the `http` sanitise hook, when `options.payload` is set:

- **`body`** is zeroed, and so is **the body part of `raw`**, the bytes after
  the head's separator. The length is kept, so `Content-Length` stays true
  and the head needs no change. Zero is `0x00`, as `--payload` zeroes
  everything else.
- **A chunked body keeps its framing.** When `Transfer-Encoding` names
  `chunked` last, the body is walked chunk by chunk — size line, data, CRLF,
  down to the last chunk — and only the data bytes are zeroed. Size lines,
  extensions and CRLFs stay, so the message still parses and a decoder's
  chunk walk still has something to walk.
- **Trailer fields keep their values.** They are headers, not body. That
  `--http-headers` does not reach them is a separate question, filed rather
  than folded in.
- **A body the walk cannot read is zeroed whole**, at the same length. The
  message may stop parsing, but nothing of the body survives, which is what
  `--payload` asks for.
- **The head in `raw` is untouched** by this step. `--http-headers`, when set
  too, has already redacted it in place (#184).

### 2. With `--scan-pii`, the body is scanned as text

The scan runs **before** the body is zeroed, as the payload scan does. (The
plan first had it after; see *What #185 corrected*.) A body, `body` or the
body part of `raw`, is decoded as UTF-8 and scanned like a
`utf8` payload, with the packet's number in the warning. A body that does not
decode is not scanned. That includes one compressed by `Content-Encoding`.
packeteer inflates bodies nowhere else, and this is documented as a limit
rather than grown into a decompressor.

The scan needs the packet's number, which a protocol's `sanitise` hook does
not receive. So the driver asks the section for its body text: an
`http`-specific step in `_sanitise_app_layers`, beside the existing
string scan.

### 3. Scope — HTTP only

kober notes the same question applies to any app section with opaque bytes.
DHCP option data and DNS RDATA are not *payload* in the sense `--payload`
means, and a compiled protocol already says what to redact through
`sensitive:`. They are left for an issue of their own, beside the one for the
hex wording #181 left behind.

## Tests

- **The pin kober asks for.** After `sanitise --payload`, a capture contains
  no byte sequence of any original HTTP body, for `raw` sections and
  structured ones, length-framed and chunked. It is checked through the CLI,
  `stream` then `sanitise`, as the issue reproduced it.
- `Content-Length` still matches the zeroed body, and a chunked body still
  parses, with its chunk sizes as they were.
- A malformed chunked body is zeroed whole.
- `--scan-pii` warns about the email in the issue's response body, as a
  `PersonalDataWarning` naming the packet, with `--payload` as without it.
  (Corrected; see *What #185 corrected*.)
- A gzip body is zeroed by `--payload` and not scanned.

### What #185 corrected

**The scan runs before the body is zeroed, not after.** The plan had it
after, so that with `--payload` it would find nothing. But the payload scan
has always run first — *before `_sanitise_payloads`, which may zero the
bytes this reads* — and the sanitise page says to combine the scan with
`--payload` "to zero the payloads after inspection". A body is a payload in
all but name, so it follows the same order: the warning says what was there,
and `--payload` still takes it out. A test pins both halves.

**The scan finds an email, not a password.** It looks for emails and names,
as it always has. `password=hunter2!!` warns about nothing. The plan's test
line said the scan would warn about the password field, which the scanner
cannot do. The email is what is tested. `--payload` zeroes both.

**`_split_head` is shared** with #184's `_redact_raw`, which split the head
the same way inline, so the two cannot disagree about where a body starts.

**A `raw` with no head separator is zeroed whole**, start line included. It
has no head to keep apart from a body, and nothing of it may survive.

**Anything after a chunked body's trailer section is zeroed.** It belongs to
no message here, and zero is the side to err on.

**Through the CLI**, the issue's login capture comes out with both bodies
zeroed at their lengths, 29 and 20, and the headers redacted by
`--http-headers`. The pin kober asked for is a test, `stream` then
`sanitise --payload` for `raw` and structured sections, length-framed and
chunked, checking that no 8-byte run of any original body survives.

## Changelog

Under `Security`, the one entry of that type in this release: `sanitise
--payload` now zeroes HTTP bodies, which it left as captured since HTTP was
decoded into its own section, and the PII scan reads them. Upgrading is the
advice for anyone who shared a capture sanitised this way.

# Part 7f — #186–#189, what the review of `.dev6` found

kober reviewed `0.17.0.dev6` (`b2541a7`) on the branch. Four issues, all on
this milestone, all reproduced on `v_0.17.0` before planning:

```text
#186  _zero_chunks(b"7\r\nSECRETA\r\n0\r\n")       → ValueError: negative count; sanitise ends the run
      … 0\r\nX-Trail: SECRETB-no-end              → keeps "X-T", zeroes the rest
#187  a chunked body over --mss 200               → every byte after the head zeroed, framing too
#188  bare-LF head, "\r\n\r\n" inside the body   → head runs to the body's CRLF pair; SECRETC kept
      parse_http on the same bytes                → body reported from SECRETD on
#189  7;ext=SECRET1 … 0\r\nX-Checksum: SECRET4…   → extension and trailer value kept
```

**The order** is #186 (a crash first), #188 (a split both parse and
sanitise rely on), #189 (built on the corrected walk), then #187, which is
documentation.

## #186 — a walk that fails zeroes, and the run goes on

**The bug.** When a chunked body's trailer section has no terminating blank
line, `find` returns -1, and `stop` becomes 3, not the "not found" the code
meant. A tail under 3 bytes makes `bytes(len(tail) - stop)` negative and
raises, and `sanitise` ends the whole run with *Error: negative count*. A
longer unterminated trailer keeps its first 3 bytes. kober's corpus hits the
first case, so `sanitise --payload` cannot be run on it at all.

**The fix.**
- An unterminated trailer section is zeroed from where it starts, since
  there is no end to keep it up to.
- **A body that cannot be zeroed as planned is zeroed whole, and the run goes
  on.** `_zero_bodies` is written so that no input raises: the chunk walk's
  every failure is a `None`, and a whole-body zero is the answer to any of
  them. One message's odd bytes never end a sanitise run.

**Tests.** The issue's three tails, each zeroed with no exception. A chunked
body **cut at every offset**, from the head's end to its last byte,
sanitised with `--payload`: none raises, and none keeps a byte of its chunk
data. That is the test kober asked for, and it pins #186 and the rule
behind it.

### What #186 corrected

**A second way to raise "negative count".** `int(…, 16)` reads `-5`, so a
size line of `-5` reached `bytes(size)`. The walk now refuses a negative
size, and `_zeroed` turns any walk failure into a whole-body zero, so no
input to it raises. Bad hex in the section's own `body` or `raw` is zeroed
whole too, rather than raising from `bytes.fromhex`.

**The every-offset test runs the real driver**, `sanitise()` with
`--payload`, on a chunked body cut at each of its offsets. None raises, and
no 4-byte run of either chunk's data is kept in `body` or `raw`. The
trailer in that test is a plain `t`, since redacting trailer values is
#189's.

**Through the CLI**, the issue's crashing capture now writes its output.

## #188 — the head ends at the first separator

**The bug.** `_split_head` and `parse_http` both pick their separator by
whether `\r\n\r\n` occurs *anywhere* in the message. With a bare-LF head
and a CRLF pair inside the body, the head runs into the body. `--payload`
then keeps the body's first line, and `parse_http` misreads the message: the
body line becomes part of the head, and the body starts at the wrong place.
#184's `_redact_raw` splits the same way, and fails closed only because the
stray line has no colon.

**The fix.** One function decides where a head ends: the **earlier** of
`\r\n\r\n` and `\n\n`. `parse_http` uses it, and so does `_split_head`,
so parsing, redaction and zeroing cannot disagree about where a body starts.

**Tests.** The issue's message through `--payload`, `--http-headers` and
`parse_http`: no body byte kept, the header redacted in place, and the body
parsed from its first byte. A CRLF head with `\n\n` in its body the other
way round. Every existing CRLF and bare-LF case unchanged.

### What #188 corrected

**Nothing in the design.** `split_head` is public in `packeteer.parse.http`,
since `parse_http`'s own behaviour depends on it, and `_split_head` in
`app/http.py` is now a call to it. #184's in-place redaction and #185's
zeroing go through `_split_head`, so all three moved together. Every existing
CRLF and bare-LF test passed unchanged, and the new tests cover the issue's
message through `parse_http`, `--payload` and `--http-headers`, and a CRLF
head with an LF pair in its body.

## #189 — `--payload` takes a chunked body's data wherever it is — decided

**The bug.** #185 zeroed chunk data and kept the rest of the framing,
including two places that can carry data. A trailer field is where a
checksum or signature over the body goes, and a digest survives zeroing,
enough to confirm a guessed body. kober's corpus puts `X-Checksum:` in its
trailers, and 6 survive. RFC 7230 §4.1 makes the trailer part of the chunked
body, so `--payload` has as good a claim on it as on the data. A chunk
extension's value can carry data the same way.

**The fix, with `--payload`:**
- **Each trailer field keeps its name, and its value becomes
  `[redacted]`**, as `--http-headers` does for a sensitive header. It is
  plain, it is the word the rest of `sanitise` uses, and it says what
  happened.
- **Each chunk extension keeps its name, and its value becomes `0`s of the
  same length.** That keeps the size line a valid `chunk-ext` token and its
  length as it was.
- **Size lines stay.** They are lengths, and the framing needs them.

**Tests.** The issue's before and after, exactly. An extension with no value,
`;ext`, kept. A quoted extension value zeroed inside its quotes. Several
trailer fields, each redacted. A trailer the walk cannot read, #186's case,
zeroed whole.

### What #189 corrected

**Two shared helpers came out of it.** `_is_field` (a line that reads as one
`name: value`, not folded) and `_redacted` (its value replaced, its spacing
kept) were written inline in #184's `_redact_raw`. Trailer fields need the
same two things, so both now call them.

**A quoted extension value holding a `;` fails closed.** It cannot be split
on `;` with certainty, so every byte of the extensions becomes `0`, keeping
the first `;`. An unclosed quote does the same. Spacing around a value, which
RFC 7230 allows, is kept.

**A trailer that cannot be read line by line is zeroed whole**, its
terminating blank line kept, so a folded value's tail cannot survive.

**A trailer field redacted to `[redacted]` changes the message's length.** A
chunked body declares none, so nothing is made false by it, and
`--http-headers` already changes lengths the same way. Everything else
`--payload` does keeps lengths.

**#185's chunked-framing test pinned the old behaviour** — `;ext=1` and
`X-Trailer: t` kept — and now pins the new. The CLI test that no body byte
survives gained a checksum trailer, and on the old code it fails on it.

## #187 — framing is kept within a segment — decided: documented

**The bug.** `sanitise` works packet by packet. A chunked body that spans
TCP segments cannot be walked from its first segment, so that section is
zeroed whole, framing included, and the continuation segments, which do not
parse as HTTP, are plain payloads, zeroed whole. **Nothing leaks**: the body
is over-zeroed, not under-. But the capture's shape is lost. On kober's
corpus at `--mss 9000`, the sanitised capture decodes 41 of 60 start lines.

**Decided: out of scope.** Keeping framing across segments means putting
each TCP direction back together by sequence number, walking messages there,
and writing the result back into the segments: **TCP reassembly, which is
out of scope for packeteer.** It is the same line drawn in 0.11.0 for
stream-shaped protocols, and #115 records the bugs waiting on the far side of
it. So it is neither built nor filed as later work.

**What changes is what the release says.** #185's changelog entry, the
`--payload` help and the sanitise page promise that a chunked body keeps its
framing. They will say it is kept **for a message within one TCP segment**,
and that a body spanning segments is zeroed whole, framing included, which
loses its shape but keeps nothing of it. #187 is closed at release with a
comment saying so.

**Tests.** The issue's case pinned as the documented behaviour: a chunked body
over `--mss 200`, sanitised, has no byte of its data left anywhere in the
capture.

### What #187 corrected

**What happens was checked before it was written down.** kober's case — two
300-byte chunks and a checksum trailer at `--mss 200`, four server segments —
comes out of `sanitise --payload` with its head kept and nothing of its body:
no data, no size line, no digest. That is what the docs now say.

**The test asserts what is promised, not what is lost.** It checks that no
run of the data and no digest survives, and that the head is kept. It does
not assert that the framing is gone, so it does not stand in the way of a
release that keeps it.

**The wording went into four places**: the `--payload` help, the
`SanitiseOptions.payload` docstring, the sanitise page (which also says that
a message after a spanning one in the same segment loses its shape), and
#185's `Security` entry, still unreleased. #187 is closed at release with a
comment saying that reassembly is out of scope, and why.

## Where this round stands

This is the eighth review, and both issues are faults in code written in
earlier rounds: #190 in #188's `split_head`, half of #191 in #189's trailer
redaction. So were #186, #188 and #189 before them. Each fix to `sanitise`'s
HTTP handling was checked against the cases in its own issue, not against
properties that hold for every capture. This part adds two such properties
as tests, and those, more than the fixes, are what should shorten the next
round.

## #190 — the head ends at the first empty line, however it is spelled

**The bug.** #188 searched for two byte pairs, `\r\n\r\n` and `\n\n`. A last
header line ended by a bare LF, followed by a CRLF blank line, is `\n\r\n`,
which neither pair matches, so the head ran on to the body's own `\n\n`. RFC
7230 §3.5 lets a recipient take a lone LF as a line ending and ignore a CR
before it, which makes `\n\r\n` an empty line like any other. The reverse,
`\r\n\n`, was found at the right place but left a stray `\r` on the head.

**The fix.** `split_head` walks lines. Split on `\n`; a line after the start
line that is empty, or a lone `\r`, ends the head. The head is everything
before that line's preceding line ending, and the separator is that line
ending plus the empty line. One rule covers `\r\n\r\n`, `\n\n`, `\n\r\n` and
`\r\n\n`, and `parse`, `--http-headers` and `--payload` all ask it.

**Tests — a property, not a case.** Every one of the four spellings, crossed
with a body holding a CRLF pair, an LF pair, both, or neither: `split_head`
returns the head without a trailing `\r`, `parse` reads the body from its
first byte, `--payload` keeps no body byte, and `--http-headers` redacts in
place.

### What #190 corrected

**Nothing in the design.** `split_head` walks from the end of the start line,
line by line, and the first line that is empty or a lone CR ends the head.
The head is cut before the previous line's ending, CR included, so no head
ends in a stray CR, and the separator is that ending plus the empty line. The
two byte-pair constants it used are gone. The property test crosses all four
spellings with four kinds of body — plain, a CRLF pair, an LF pair, both —
through `split_head`, `parse`, `--payload` and `--http-headers`: 48 cases,
16 of which fail on the code before it.

## #191 — redaction keeps a value's length — decided

**The bug.** `sanitise` replaces a sensitive value with `[redacted]`, whose
length is rarely the value's. The TCP segment carrying it changes size, but
the sequence numbers of the segments after it are left as captured, so a
reassembler finds bytes missing or overlapping between them. A gap is a
statement that bytes were lost in capture, and kober resynchronises after
one, misreading what follows. Two halves:

- **`--http-headers`, before 0.17.0.** A redacted header changes length,
  with `raw` (#184) or without it, since a canonical message has no `raw`
  and is rebuilt from its fields.
- **`--payload`'s trailer values, #189's.** The same `[redacted]`, chosen in
  #189 because "a chunked body declares no length". The TCP sequence numbers
  were missed. It also contradicts `--payload`'s help, which says lengths
  are kept.

**Decided: redact at the same length.** One function gives the redaction for
a value of a given length: `[redacted]` cut to that length, or padded with
spaces to it. `shop.example.com` (16) becomes `[redacted]      `, a 4-byte
value `[red`. Trailing spaces in a header value are optional whitespace, so a
parser still reads `[redacted]`, and `packeteer parse` reports it so. The
length a redaction reveals is already revealed by `--payload`, which keeps
every length it zeroes. It applies everywhere `[redacted]` is written:

- `_sanitise_http`'s structured headers, a string and every list item;
- `_redacted`, the raw header line (#184) and the trailer field (#189). The
  span replaced is the value after the colon's spacing, up to the line
  ending, trailing whitespace included.

The alternative, renumbering `seq` and `ack` in both directions after each
change of length, would cover more, but it is flow-aware code next to the
reassembly ruled out of scope with #187. It is not taken.

**What still changes length.** A message whose `raw` is dropped and rebuilt
from its fields, because its head cannot be read line by line (#184's
fallback), is grouped and combined as before, and its length can change.
That is the rare, malformed case, and it is documented. **DNS over TCP has
the same fault and is not fixed here**: label redaction and re-compression
both change a message's length, and that wants its own decision. It is
**#192**, filed without a milestone after reproducing it: every one of 6
segments grew from 40 to 47 bytes.

**Tests — the invariant.** For every capture in the real-capture corpus and a
set of generated streams — HTTP with chunked bodies and trailers, given
`raw` messages — sanitised with the defaults, `--http-headers`, `--payload`,
and both: **every TCP segment keeps its payload length**. Plus the issue's
two cases, and a value shorter than `[redacted]`. DNS over TCP is left out of
the generated set until #192, with the reason written beside it.

### What #191 corrected

**One function, two call sites.** `_redaction(length)` in `sanitise.py`
gives `[redacted]` cut or space-padded to a length. `_sanitise_http` asks it
for each structured value and list item, and `_redacted` in `app/http.py`
asks it for a raw header line or a trailer field, measuring the value after
the colon's spacing, trailing whitespace included. A test pins 16, 10, 4 and
0, and that `parse_http` reads a padded value back as `[redacted]`.

**The invariant test is `test_sanitise_lengths.py`.** It builds every TCP
packet of a capture from the parsed spec and from the sanitised one, through
the CLI's own builder, and requires the same length. That runs for all 27
real captures and two generated HTTP captures, under the defaults,
`--http-headers`, `--payload` and both: 116 cases in half a second.

**Its first version missed the half it was written for.** On the code before
the fix, it caught `--http-headers` and not `--payload`. The given response
was sent at `--mss 120`, so its chunked body spanned segments and was zeroed
whole at its length (#187), and its trailer was never reached. And at seed 1,
none of the six generated responses was chunked. Both captures now put
trailers in single segments: the default MSS for the given messages, and
`--chunked-rate 1.0` over 20 requests for the generated ones. On the old code
it now fails `--payload` on both. A property test is only as good as its
inputs reaching the code, and this one was checked against the old code
before it was trusted.

**Ten existing tests pinned `[redacted]` exactly**, in `test_http.py` and
`test_http_raw.py`. Each now expects the redaction at its own value's length,
through small helpers that ask `_redaction`. Two in `test_http.py` had
passed by coincidence, since their values were exactly ten characters long.

**The same fault outside HTTP, found while updating the docs.** A compiled
protocol's generated `sanitise` writes `'[redacted]'` for a `sensitive:`
string whatever its length. For a string sized by a derived length field,
carried over TCP, that is #191 again. For a fixed-size string, `[redacted]`
may not fit its size at all. It is generated code, so it is outside this
fix. It was raised with the user rather than folded in.

| [Q1](#q1) | Given HTTP messages: cycle to `--requests`, or send the list once | **Cycle**, as `protocol_payload_fn` does |
| [Q2](#q2) | Content knobs from a stream config file with `--protocol-messages` | **Refuse them too**, naming the file key |
| [Q3](#q3) | Repeated header names in an HTTP section | **Out of this milestone**; filed as [#172](https://github.com/adamkjonsson/packeteer/issues/172) |

### <a name="q1"></a>Q1 — cycle, or send once

Sending the list once is what a caller replaying a capture probably means;
cycling is what every other `--payload` does. The two differ only when
`--requests` exceeds the list's transactions, and `--requests` has a default
of 10. *Recommendation: cycle*, for one rule across protocols — and a caller
who wants the list once sets `--requests` to its length. If this reads wrong
in kober's review, the alternative is `requests=None` meaning "the list's
length" when `messages` is set.

### <a name="q2"></a>Q2 — config-file knobs

`--config` can set `error_rate` and friends too. A value from a file is
as much the user's as one from a flag. *Recommendation: refuse it the same
way*, naming the file key rather than the flag.

### <a name="q3"></a>Q3 — repeated headers

Needed to send `Transfer-Encoding: gzip` and `Transfer-Encoding: chunked` as
two lines. *Recommendation: not this milestone*: filed as its own issue, since
it changes the `http` section's `headers` shape for every caller.
