## #122 — the bug that arrived with the corpus

Found while collecting captures for #89, and it belongs to that work as much
as to this milestone: **you cannot commit a real corpus until the sanitiser
can actually clean it.**

`sanitise` had no ICMP handling at all. A Neighbour Discovery capture came out
with its Ethernet and IPv6 headers replaced and the same addresses still
inside the payload — the ND target, a link-layer option holding the real MAC,
and the whole packet quoted inside an error.

The link-layer option is what makes it a defect rather than an omission. An
IPv6 link-local address is EUI-64 derived from the MAC, so:

```
1c:0b:8b:3c:e7:a3  → flip the U/L bit, insert ff:fe
                   → fe80::1e0b:8bff:fe3c:e7a3
```

which is exactly the address that had been replaced with `2001:db8::1`. **The
output was a file that looks sanitised, reports success, and can be reversed
by anyone holding it.** A whole-file byte scan of the original "clean" capture
found all eight of its real addresses and MACs still present; after the fix,
none.

### What it settled

**`sanitise` learns structure; the parser does not.** The payload stays opaque
bytes and the round trip is untouched — the same shape `_sanitise_dns` has.

**Replacements go through the same `_Replacer`.** A MAC in a link-layer option
becomes the *same* synthetic MAC as in the Ethernet header, and a quoted
address the same one as in the frame. Substituting something different would
have been almost as misleading as substituting nothing.

**`identifier` and `sequence` were lying.** Those two fields are the halves of
a four-byte field whose meaning depends on the message type; they are named
for what an Echo puts there. For an ICMPv4 Redirect they hold halves of a
gateway *address*, which is how the third leak hid in plain sight — nothing in
the model said an address was there. Fixed by documenting them accurately in
both header classes, both parsers and the packet-spec reference, and adding
`rest_of_header` to read or write all four bytes as one value. The field names
are unchanged, so specs written against an earlier version still build.

**A type it cannot redact warns, sharing `PersonalDataWarning`** with a new
`kind` of `"unredacted"` rather than getting a class of its own. Code that
catches that warning is asking *is this file safe to share*; a separate class
would be silently missed by everyone already asking. Silence is what let the
bug survive.

## #124 and #123 — what collecting captures turned up

Both came out of #89 rather than the umbrella plan, and both were found by
trying to capture traffic rather than by reading code.

**#124 — loopback captures could not be read at all.** `tcpdump -i lo0` on
macOS produces link type 0, which packeteer did not support, so the easiest
traffic there is was unusable. It blocked corpus collection twice in an hour:
an ICMPv4 error needed a cooperating remote host without it, and an IPv6 TCP
session needed a second machine or a tunnel broker, on a laptop with no global
IPv6. With it, both are one command against `::1`.

It was moved ahead of #89 for that reason — a tool for collecting captures is
worth more before the collecting than after.

**#123 — an unsupported link type was silent**, which is how #124 presented:
the frame became an opaque payload, no warning, and the failure surfaced later
as `missing network.src`. Worse, `sanitise` then reported success on a file
where every address was still present.

Fixed three ways, following the precedent already in the codebase
(`UnsupportedIPProtocolWarning`):

- `UnsupportedLinkTypeWarning` at parse time, once per file rather than once
  per packet, since the link type is a property of the capture.
- `sanitise` warns `kind="unredacted"` for any packet that is nothing but an
  opaque payload, because it cannot redact what the parser never saw.
- `build` says the packet was never decoded and why, rather than naming the
  key that is missing as a result.

### What #123 corrected

**#122's warning kind was being relabelled.** `_consolidate_pii_warnings`
rewrote *every* `PersonalDataWarning` with a template that assumed `kind` was
`"email"` or `"name"` — so the `"unredacted"` reports #122 added came out as
*"Possible name found in…"*. A latent bug shipped in #122 and found only
because #123 raised a second warning through the same path. Findings and
reports are now distinguished, and a report keeps the wording whoever raised
it chose while still being consolidated across packets.

**Two existing tests documented the old behaviour**, and both were updated
rather than worked around: one asserted no PII warnings for a spec that is
only a payload, which is now exactly the case that warns; the other asserted
that an unknown link type returns an empty packet, and now asserts it warns
too.

**#125 — `sanitise` kept the client MAC and hostname in DHCP options.** Found
by the check that should have been routine from the start: scanning every
sanitised capture for addresses taken from its own original. `chaddr` was
redacted and option 61 was not, so the real MAC sat two fields from its own
substitution — and the two disagreed, making the capture wrong as well as
leaky. `_DHCP_OPT_HOSTNAME` and `_DHCP_OPT_DOMAIN_NAME` were defined in
`sanitise.py` and never referenced, so the omission was unfinished work rather
than a decision.

That is four of these in one cycle, after #113's ignored spec keys, #122's
unredacted ICMP payloads and #123's silent link type. **packeteer's default
failure mode has been silence**, and every one was found by checking output
rather than by reading code. The corpus work in #89 is what makes that check
automatic.

## The constraint that shapes this milestone

**v0.11.0 shipped a compiler whose output is a second-class citizen.** A
compiled protocol parses, builds and serialises exactly like a built-in, and
then falls short in three specific places:

- `packeteer sanitise` **does not redact it**, and says nothing;
- the `packeteer` command line cannot load it at all;
- `packeteer stream` cannot generate traffic with it.

The first is a defect rather than a gap. For everything else in packeteer an
unregistered protocol means a feature you do not get; there it means data you
meant to remove is still there, reported as success. That is why #117 is
first and why its open question is worth settling before it starts.

**And packeteer now has two protocol mechanisms permanently.** DNS, DHCP and
HTTP are not expressible in the spec subset — DNS needs compression pointers,
HTTP needs delimiter framing — so the built-ins stay hand-written. Two
mechanisms with no shared test is how they drift, which is #120.

# Part 1 — finishing the compiler's citizenship

## #117 — sanitisation from the spec

`sensitive: true` has been in the grammar since #105 and is printed by
`packeteer protocol show`, but nothing reads it: a compiled protocol registers
with `sanitise=None`, so #101's loop skips it.

`codegen` emits a redaction function from the annotated fields and puts it on
the `AppProtocol`. It follows a field into nested units and repeated ones, and
the existing UTF-8 PII scanner (`_scan_utf8_payload`) runs over generated
`string` fields, where a name or an email is far likelier to be than in an
opaque payload.

<a id="q4"></a>
### Q4 — what happens to fields nobody annotated

The one open question on this milestone, carried from
[the umbrella plan](user-defined-protocols.md#q4).

| Answer | Consequence |
|---|---|
| Redact nothing unannotated | Silent, and the failure mode is a leak |
| Redact everything not marked safe | Safe, and makes `sanitise` useless on the protocol you added in order to *see* it |
| **Redact what is annotated, warn when a spec annotates nothing** | *Recommended* |

The warning goes through the existing `PersonalDataWarning` machinery, once
per spec rather than per packet.

This is consistent with what #102 settled for hand-written protocols — an
`AppProtocol` with no `sanitise` callable passes through untouched, documented
as a deliberate choice by whoever registered it. The difference is that a
*compiled* protocol always has a sanitiser, so "nobody wrote one" is not the
failure mode available to it; "nobody marked anything" is, and that is what
the warning is for.

**Silence is the one outcome that must not be available.**

## #118 — loading a protocol from the command line

Three mechanisms: a repeatable global `--protocol ./sensor.py`, a
`"protocols": […]` key in the packet spec so a spec is self-describing, and
`PACKETEER_PROTOCOLS` for a shell that always wants the same ones. Paths in a
spec resolve relative to the spec file.

### The rule that matters

All three import Python from a path, in a tool people point at captures they
did not produce. That is no worse than `import` — the user names the file —
but one rule follows and it is not negotiable:

> **A path must never be taken from a capture's contents.** The packet-spec key
> is a path the *user* wrote in a spec they are editing. It must not become a
> path packeteer discovers while parsing someone else's traffic.

The docs must also say plainly that a protocol module is code and is trusted
as code — #103 already says this for hand-written protocols, and #121 carries
it to the CLI pages.

## #119 — driving a stream with a compiled protocol

`--payload <registered name>`, with `http` and `vpn` still working. The
generator side is nearly free, since `TCPSession.send()` already takes bytes.

What it actually needs is a way to say **what messages to send**, which is
`--protocol-messages sensor.json` — a file of packet-spec sections, sent in
order. **This stays out of the spec grammar.** A spec describes a protocol;
which messages to send is a property of the traffic you want, and putting it
in the grammar would make every spec carry test data.

Worth remembering #83: `--payload http` silently ignored TCP anomaly options
because the impairment passes identify packets by their labels. Whatever
labels the new path emits have to be the ones those passes expect, or
impairments will be dropped the same way.

## #120 — one contract, both mechanisms

A harness that takes any registered protocol and asserts the contract, run
over the built-ins and the example specs alike. The properties are listed on
the issue; the one that matters most is the last —

> `PacketBuilder.app` → `parse_packet` → packet spec → `build` is
> byte-identical

— which is currently asserted for compiled protocols and for the built-ins
separately, in different files, with different fixtures. That is exactly the
shape of a guarantee that quietly stops holding on one side.

## #121 — the guides

#103 and #113 documented both routes, but the pages a reader arrives at first
still describe the world as it was before v0.10.0: `docs/guide/parsing.md`
names only `.dns`, `.dhcp` and `.http`, and `generating.md` only the three
builder methods.

The thing to state once and prominently: **packeteer has two protocol
mechanisms and will keep both.** A reader who finds only one will assume the
other is legacy.

# Part 2 — two older issues this milestone answers

## #89 — a tracked capture corpus

`testcases/` holds thirteen captures and **none of them are in the
repository**; `.gitignore` excludes `*.pcap` and `*.pcapng`. The sweeps added
with #86 and #87 therefore skip on a clean checkout, which keeps CI honest and
means the assertion runs nowhere automatic.

**Every capture CI can see is one packeteer generated itself**, and the issue
records what that costs: across the eleven synthetic captures, 0 of 1,314 TCP
packets carry any TCP option, while the one real capture has options on all
13. #87 existed because of that, and was found by hand.

### Why it belongs in this milestone rather than another

Two things this cycle argued for it, neither of them in the original issue.

The v0.11.0 release ran `2606 passed, **2 skipped**` on a clean clone, and
those two skips are exactly this corpus — so the whole spec compiler shipped
without CI ever running a real capture through the round trip.

And the CI failure at the end of v0.11.0 was the same class of problem: a test
that read files from outside the checkout, which passed locally and nowhere
else. An untracked corpus is that, standing, by design.

### What #89 turned up

Assembling it found two more defects, both by the same check — scanning each
sanitised capture for addresses taken from its own original:

- **#125**, the DHCP client MAC and hostname, fixed.
- **#126**, a truncated capture that does not round-trip. `parse` → `build`
  loses the IP header's declared length, the record's `orig_len` and the
  file's `snaplen`, so a snaplen capture comes out *complete* — smaller,
  internally consistent packets that never existed on any wire.

**#126 blocks a corpus member.** The snaplen capture was collected and could
not be committed: sanitising it destroys the property it was collected for.
So #92's and #94's paths still have no real-traffic coverage, which is
recorded in the manifest's known gaps rather than left to be rediscovered.

### The option to take

The issue lists three; **option 1 — commit a small corpus** — is the only one
that closes the gap, and it says so. The others are worth naming as rejected
rather than forgotten: a generated fixture can only contain shapes someone
thought to write, which is the property that let #87 hide; and a local
pre-release check is what happens if nobody does anything.

**`http_example.pcapng` is real traffic and goes through `packeteer sanitise`
first.** Its MAC and IP addresses want a look before they land in a public
repository. That packeteer sanitises its own corpus with its own command is a
pleasing check on the command.

Worth doing what #68, #86 and #87 all did: confirm each sweep **fails without
the fix it guards**. Done, and it does: with #86's `pad: false` removed from
`_apply_ethernet`, the round-trip sweep fails on `arp.pcapng` packet 1
immediately. A sweep nobody has seen fail is a sweep nobody knows works.

### The shape it took

`testcases/real/`, eight captures, 92 KB in total, each named individually in
`.gitignore` — so adding one is an act rather than an accident, and an
unsanitised file cannot be committed by being dropped in the directory. The
synthetic captures stay untracked, which means **everything committed is real
traffic** and the distinction needs no other marker.

`MANIFEST.md` says what each capture is *for*, and a test fails if a capture
is not named in it — a capture nothing asserts anything about is a file, not a
test. Another test asserts the reasons they were collected still hold: that
`tcp_v4.pcapng` really does carry two different option layouts, that
`dns.pcapng` really does use compression pointers, that the loopback capture
really is `DLT_NULL` with offloaded checksums. Without those, the corpus
quietly becomes decoration.

## #84 — the chunked body, and why the answer is now clear

`parse_http` trims to `Content-Length` and has no branch for
`Transfer-Encoding`, so a chunked message's `body` carries its chunk sizes and
terminator rather than the payload a recipient would reconstruct.

The issue lists three options and leaves the decision open, ending:

> Worth revisiting if kober or another consumer wants packeteer to hand back
> reconstructed payloads rather than decode the framing itself — which, for a
> project whose entire purpose is decoding HTTP framing, it may well not.

**v0.11.0 answered that.** Stream-shaped protocols were put out of packeteer's
scope and into kober's, on the ground that reassembly cannot serve byte-exact
reconstruction. De-chunking is the same argument in miniature: chunk
boundaries are a **sender's choice**, not a property of the payload, so a
de-chunked body cannot be re-chunked to reproduce the capture. A 70-byte body
split `1c/c/18/4` and the same body split `40/6` are different bytes on the
wire and identical afterwards.

**Recommendation: option 1 — leave the behaviour, document it.** `body` is the
encoded body, chunked framing is not decoded, and the consumer who wants the
payload is the one that decodes framing for a living.

That makes #84 a documentation issue: the `parse_http` docstring, the `http`
section of `docs/packet-spec/format.md`, and a sentence in
`docs/guide/parsing.md`. It should say *why*, not just *what*, so the question
is answered rather than rediscovered a third time.

If that recommendation is rejected, option 2 (a separate `decoded_body`) is
the honest shape, because it is the only one where both values exist at once.
Option 3 — an opt-in `dechunk=True` — should not be taken: a caller who passes
it can no longer round-trip what they parsed, which is a foot-gun rather than
a feature.

## Order of work

0. **#122** — done. It had to come first in practice: a real corpus cannot be
   committed until `sanitise` can clean it.
1. **#89** — the corpus. First of the rest, and deliberately: it is cheap, and it makes CI
   meaningful for everything after it. Shipping the rest of this milestone
   against synthetic captures only would repeat v0.11.0's blind spot.
2. **#117** — sanitisation. The defect, and the one with an open question.
3. **#118** — CLI loading.
4. **#119** — `stream --payload`.
5. **#120** — the conformance suite. Needs #117, or two of its properties
   cannot be asserted uniformly.
6. **#84** — the chunked-body decision, written down.
7. **#121** — the guides, last, describing the finished shape.

#89 and #84 are independent of the rest and of each other.

## Cross-cutting

- **Version.** `pyproject.toml` goes to `0.12.0.dev0` at the start.

- **Semver.** All additions, no removals. `--payload` accepting more names is
  not breaking. No `Breaking:` markers expected.

- **The umbrella plan finishes here.** Once #117–#121 land,
  [plans/user-defined-protocols.md](user-defined-protocols.md) is delivered in
  full, and the standing cost it names — two app-layer mechanisms, kept
  indefinitely — becomes a permanent property of the project rather than a
  transitional one. #120 is what makes that sustainable.

- **kober.** #84's answer leans on the split v0.11.0 settled, so it is worth
  telling them: packeteer will not de-chunk, on the same ground it will not
  reassemble.

- **Release.** All issues close at release with the milestone, not at merge.
