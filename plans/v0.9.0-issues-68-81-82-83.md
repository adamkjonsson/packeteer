Seven issues on the v0.9.0 milestone. Three of them (#81, #82, #83) come from
[zipline-kober](https://github.com/adamkjonsson/zipline-kober), which is using
`packeteer stream --payload http` as an adversarial input source for an HTTP
decoder, and they form a chain. #68 was thought to be the last known gap in the
`parse` → edit → `build` round trip, deferred out of v0.8.0; measuring it
turned up #86, and the sweep #86 made possible turned up #87 — each fix
uncovering the next, because until the one before it landed the gap it left
hid everything behind it. #85 was filed during #83. All three were added to
the milestone after the first issues landed.

| Issue | Summary |
|-------|---------|

## The constraint that shapes this milestone

**0.8.0 has shipped.** This is the opposite of the situation that made the
v0.8.0 milestone cheap. `encode_http_message`, `HTTPRestConfig`,
`generate_http_stream` and `generate_tcp_stream`'s seeded output are all
released public API, so every change here is a compatibility question rather
than a free edit.

Three consequences run through everything below:

- Changed behaviour needs a `Changed` entry, and anything a caller could have
  depended on needs a leading **`Breaking:`** with the migration.
- `pyproject.toml` is at a bare `0.8.0`. **First commit of the cycle bumps it
  to `0.9.0.dev0`**, per CLAUDE.md — nothing else can land honestly until it
  does.
- Under 0.x a breaking change may ride a minor bump, so none of this needs
  deferring to 1.0 — it needs *calling out*.

Suggested order: **#81 → #82 → #83**, with **#68** independent and runnable in
parallel or last. #81 before #82 is a hard dependency the issue itself flags.
#82 before #83 is a judgement call and the reasoning is worth keeping: impaired
*chunked* traffic is the case that actually exercises the reporter's decoder,
and the framing should be correct before segments start disappearing out of the
middle of it.

**#85 must come after #83** and did: it changes how loss is applied, and #83
had to establish the shared impairment module first. Between #68 and #85 the
order is free. #68 first is the marginally better bet — it is fully specified
with nothing left to decide, while #85 still has an open question, and that
question can be settled while #68 is in flight.

**#86 after #68**, which it was found by, and which shares its shape. Of the
two remaining, #86 first: it is small, fully specified, and finishes the round
trip, so it can land while #85's open question is still being settled.

**#87 after #86**, which found it. Of the two now left, **#87 first**: it is
the smallest of the three round-trip fixes, is fully specified, and completes
a set — leaving #85, the only one with a question still open, for last.

## #81 — `Content-Length` beside `Transfer-Encoding`

**Done, `1660372`.** Landed as planned; the encoder now skips the automatic
header when the message frames itself, and matches header names
case-insensitively.

Smallest, no design fork, and it blocks #82.

### Verified

Both halves reproduce on 0.8.0, including a second bug the issue only
hypothesises about:

```python
HTTPResponse(headers={"Transfer-Encoding": "chunked"}, body=b"4\r\nabcd\r\n0\r\n\r\n")
# b'HTTP/1.1 200 OK\r\nTransfer-Encoding: chunked\r\nContent-Length: 14\r\n\r\n...'

HTTPResponse(headers={"content-length": "5"}, body=b"hello")
# b'HTTP/1.1 200 OK\r\ncontent-length: 5\r\nContent-Length: 5\r\n\r\nhello'
```

The first is the RFC 7230 §3.3.3 smuggling construction, with a length that
counts the chunk framing rather than the payload. The second is a **duplicate
`Content-Length`** — a caller who wrote the header in lower case gets it twice.
That one is a plain bug, and it is fixed by the same case-insensitive lookup.

### Implementation

`src/packeteer/generate/http.py`, in `_build_http_message` (line 127):

```python
present = {k.lower() for k in headers}
if msg.body and "content-length" not in present and "transfer-encoding" not in present:
    headers["Content-Length"] = str(len(msg.body))
```

Docstring ripple only, but in four places: the module docstring, both
dataclass `headers:` attribute descriptions, and `encode_http_message`. All
four currently promise the header unconditionally; they need the "unless the
message frames itself" clause.

Explicitly **not** doing: chunking the body inside the encoder. The issue is
right that encoding a body and framing it are different jobs.

### Tests

`src/tests/test_http.py`. Chunked message gets no `Content-Length`; lower-case
`content-length` is respected rather than duplicated; mixed case
(`Content-length`) likewise; the ordinary counted-body case is unchanged; empty
body still gets no header.

### Undecided

1. **Is the case-insensitive fix in scope here, or its own issue?** The issue
   suggests "a separate look" since it affects the existing check too.
   *Recommendation: same change.* It is two lines, it is a real duplicate-header
   bug, and splitting it means writing the same test file twice.

   **Decided (Adam, 2026-08-27): same change.** Shipped in `1660372`. Matching
   is case-insensitive; the caller's own spelling is preserved on the wire,
   which is pinned by a test — normalising it would have been a second silent
   behaviour change nobody asked for.

### Changelog

`Fixed`. Not `Breaking:` — the old output was malformed, and no caller can have
been relying on a `Content-Length` that contradicted its own `Transfer-Encoding`.

## #82 — Chunked responses from `--payload http`

**Done, `85d3e61`.** Landed with one deviation from the plan, recorded under
*What the defaults turned out to be* below.

### Verified

```console
$ packeteer stream --payload http --sessions 6 --requests 40 --seed 1 --pcap http.pcap
Wrote 1002 packet(s) to http.pcap (link type: 1, 6 sessions)
chunked: 0   content-length: 263
```

`Transfer-Encoding` appears nowhere in `src/packeteer/generate/`.

### The cost the issue does not see: there is no CLI path at all

`_generate_http_payload_stream` constructs **`HTTPRestConfig()` with no
arguments** (`src/packeteer/__main__.py:1718`). Not one HTTP content knob is
reachable from the CLI — `error_rate` included. So `--chunked-rate` is the
first of its kind and pays the whole plumbing cost:

- `argparse` flag in the `stream` parser
- an entry in `_STREAM_CONFIG_KEYS` (`__main__.py:1344` region)
- an entry in `src/packeteer/generate/stream.ini.template`, which
  `--write-config` emits and which #78 has just finished de-staling
- `docs/cli/stream.md`
- actually threading the values into the `HTTPRestConfig(...)` call

CLAUDE.md requires everything in the CLI to be reachable from the API; this is
the inverse gap, and it is the same fix.

### Implementation

`src/packeteer/generate/payloads/http.py`:

```python
@dataclass
class HTTPRestConfig:
    ...
    chunked_rate: float = 0.0                  # P(a bodied response is chunked)
    chunk_size: tuple[int, int] = (16, 512)     # bytes per chunk, before the last
    trailer_rate: float = 0.0                   # P(a chunked body carries trailers)
```

A `_chunk_body(body, rng, chunk_size, trailers)` helper walks the body into
size-line + CRLF segments, terminates with `0\r\n\r\n`, and optionally inserts
a trailer section before the final CRLF. Applied in
`generate_http_conversation` where the response is built, setting
`Transfer-Encoding: chunked` and leaving `Content-Length` off — which only
works once #81 has landed.

Two details from the issue that are worth honouring literally, because they are
what makes the output useful:

- **More than one chunk per body.** A single-chunk body does not distinguish a
  decoder that walks the size lines from one that reads to the end. The default
  `chunk_size` must be small enough relative to `_random_json` bodies that
  multiple chunks are the normal case — check this, since the generated JSON is
  ~80 bytes and a `(16, 512)` range would frequently produce one chunk. The
  range likely wants to be smaller, or the bodies larger.
- **Chunked only on HTTP/1.1.** The generator always emits `1.1` today, so this
  is a guard rather than a branch, but it should be explicit.

### What the defaults turned out to be

The bodies measured 63–70 bytes, not ~80, which settles the question above:
`chunk_size` shipped as **`(8, 32)`**, not the issue's `(16, 512)`, which would
have produced a single chunk for nearly every body and defeated the issue's own
first priority. The defaults give 3–8 chunks per body.

One hazard found while implementing: a `chunk_size` minimum below 1 emits a
zero-size chunk, which *is* the terminator — the body would end early and
silently. `generate_http_stream` now rejects the range.

The seeded-output promise held, but only after a fix: the response header set
must be built **before** the body, matching the keyword-argument evaluation
order of the expression it replaced. Digests taken before the change caught
this; all three seeds now reproduce byte-for-byte, and a test pins the guard by
generating with `trailer_rate=1.0` and `chunked_rate=0.0`.

### Interaction with the parser — worth stating

`parse_http` trims the body by `Content-Length` and **does not de-chunk**
(`src/packeteer/parse/http.py:63`). A chunked body therefore passes through as
opaque bytes: the byte-exact round trip still holds, but a `to_config` `http`
section for a chunked response will carry the chunk framing inside `body`.

### Tests

`src/tests/test_payload_http.py`. `chunked_rate=1.0` produces
`Transfer-Encoding` on every bodied response and `Content-Length` on none;
`chunked_rate=0.0` is byte-identical to today's output for a given seed;
multi-chunk bodies; terminator present; trailers when enabled; the reassembled
TCP payload de-chunks back to the original JSON; and the CLI flag reaching the
config.

### Undecided

2. **Expose `--error-rate` in the same change?** *Recommendation: yes.*
   Shipping a config class that is half-reachable from the CLI is the state
   this issue is complaining about, one knob later.

   **Decided (Adam, 2026-08-27): yes.** All five HTTP knobs are now CLI flags
   and `[stream]` keys.
3. **Should `parse_http` learn to de-chunk?** *Recommendation: no, and file it
   separately if zipline-kober wants it.* De-chunking makes `body` no longer
   the bytes on the wire, which is a round-trip question, not a generator one.

   **Decided (Adam, 2026-08-27): out of scope, filed as
   [#84](https://github.com/adamkjonsson/packeteer/issues/84)** (unmilestoned).
   The issue records why the current behaviour is what makes the byte-exact
   round trip work: chunk boundaries are a sender's choice, so a de-chunked
   body cannot be re-chunked back to the captured bytes.
4. **Trailers in or out?** The issue lists them as second priority. They are
   ~5 lines given the chunker exists. *Recommendation: in, defaulting to 0.0.*

   **Decided (Adam, 2026-08-27): in.** `trailer_rate`, announced with a
   `Trailer` header naming the fields, per RFC 7230 4.4.

### Changelog

`Added`, naming both the config fields and the CLI flags.

## #83 — Impairments on the payload paths

The large one, and the one that decides whether the milestone fits.

**Done, `4ce7752`.** Landed with the full impairment set, `--mss`, and the VPN
subset.  One thing could not be preserved — see *The byte-identity result*
below.

**Scope grew on 2026-08-27:** `--mss` is now part of this issue
([comment](https://github.com/adamkjonsson/packeteer/issues/83#issuecomment-5443992815)).
See *Segment size* below — without it the impairments cannot produce their most
interesting output on the HTTP path, so it is a prerequisite rather than an
extra.

### Verified

```console
$ packeteer stream --payload http --sessions 1 --requests 4 --packet-loss 0.5 --pcap loss.pcap
Warning: TCP anomaly options (...) are not applied with --payload http; ignoring them.
Wrote 23 packet(s) to loss.pcap (link type: 1)
```

### Better news than the issue assumes

Retransmission, payload corruption, server RST and stray injection are
**already post-passes over a finished packet list**
(`src/packeteer/generate/tcp_stream.py:637-745`). Only packet loss is inline in
`emit` — and it drops *after* the sequence number has advanced, so converting
it to a post-pass is semantically identical. The issue's option 2 (apply
impairments as a pass over the assembled stream) is therefore within reach, and
option 1 (thread parameters into `generate_http_stream`) would be the worse
trade: it would put a second copy of the impairment logic on a second path.

### The real cost: the passes identify packets by parsing labels

Every pass keys off label text — `"DATA[3]"`, `"ACK[3]"`, `"FIN-ACK"`, `"ACK"`.
The payload path labels segments from `AppMessage`, and the two label
vocabularies collide in a way that is actively dangerous:

| | generic path | `--payload http` path |
|---|---|---|
| data segment | `DATA[0]`, `DATA[1]` | `GET /api/v1/sessions`, `200 OK` |
| `ACK[i]` means | server's ack of `DATA[i]` | *i*-th ack overall, **either direction** |
| data direction | client → server only | both |

So `ACK[i]` exists on both paths with **different meanings**. The corruption
pass looks up `f"ACK[{i}]"` by data index to shift its timestamp; run
unchanged against an HTTP stream it would silently shift the wrong packet.

**Every predicate must become structural** — `payload_len > 0`, `flags`,
`direction` — rather than label-derived. That is the bulk of the work, and it
is an improvement worth having regardless.

Two more consequences of bidirectionality:

- **Server RST** currently splits on client-sent data. On HTTP the interesting
  case is an RST mid-*response*, which is a different choice, not a port.
- **Stray packets** draw their payload size from `min_payload`/`max_payload`,
  which the HTTP path has no equivalent of. Needs a default or a new knob.

### Segment size — `--mss`, added to this issue

`generate_http_stream` takes an `mss` parameter (default 1460) and passes it to
`render_tcp_session`, but `_generate_http_payload_stream` never passes it, so
it is unreachable from the CLI and from a config file, and it is not in
`_STREAM_PARAMS`. Found while implementing #82.

This is not a separate nicety. The generated JSON bodies are 63–70 bytes, so a
whole HTTP message fits in one segment, and two things follow that blunt
exactly what this issue is for:

- **A chunk boundary never crosses a segment boundary.** Since #82 a response
  splits into 3–8 chunks, but they arrive in one segment, so a decoder never
  holds a partial size line across a read — the case a streaming decoder is
  most likely to get wrong.
- **Losing a segment loses a whole message.** With one segment per message,
  `--packet-loss` removes an entire request or response rather than punching a
  gap into the middle of one. The issue asks for "a real gap in the middle of a
  message a decoder is already part-way through"; at the default MSS that gap
  is unreachable at any loss rate.

Shape: `--mss BYTES`, an `mss` key in `_STREAM_PARAMS`, the INI template, and
`docs/cli/stream.md`. HTTP-only in practice — `--payload vpn` is UDP and has no
segmentation, and the generic `generate_tcp_stream` path sizes segments from
`--min-payload` / `--max-payload` — so the help text should say so, the way the
other `--payload`-specific flags do. Worth checking how a small MSS interacts
with the `--mtu` fragmentation pass, since both split packets at different
stages.

Do this **first** within the issue: it is small, independent of the extraction,
and it is what makes the impairment tests worth writing.

### `--payload vpn` cannot be fixed the way the issue suggests

`generate_vpn_stream` renders over `render_udp_session`
(`src/packeteer/generate/payloads/vpn.py:347`). It is UDP. Loss and payload
corruption port over; retransmission, server RST and TCP hijacking are TCP
concepts with no UDP meaning. VPN gets **a subset and a narrowed warning**, not
the same fix — the issue's "would fix `--payload vpn` in the same change" is
not available.

### Implementation

0. Expose `--mss` (above), so the impairments have multi-segment messages to
   damage.
1. Extract the four post-passes plus loss into `generate/impairments.py`,
   operating on a list of stream packets plus the endpoint context they need
   (IPs, ports, MACs, `include_ethernet`, `ip_ttl`, `encap`, `window`).
2. Replace label parsing with structural predicates; keep labels as output
   only (`RETRANS[...]`, `CORRUPT[...]`, `STRAY[...]` stay, since tests and
   users read them).
3. `generate_tcp_stream` calls the shared module instead of its inline copies.
4. Payload generators accept an impairment config and apply it **per flow**,
   before `merge_streams` — a `CombinedStream` is many connections interleaved
   and impairments must not reach across them.
5. `__main__.py` drops the warning for the flags that now work, and narrows it
   for the VPN/UDP subset.

### The byte-identity result

Digests of 112 seed and option combinations were taken before any change.
**108 reproduce exactly.** The four that do not are the two configurations
combining `--server-rst` with `--packet-loss`.

That combination was a bug, not a design choice worth preserving. The RST pass
kept an acknowledgement by comparing the segment number in its label
(`ACK[8]` → 8, an absolute index) against `k`, a *position* in the list of
segments that survived loss. The two agree only when nothing was dropped. With
loss the pass discarded acknowledgements for segments delivered before the
reset and kept some sent after it, and an ACK whose own segment was lost fell
through to be read as part of the teardown.

Reproducing it exactly would have required carrying the generator's own
segment numbering into the impairment module — the one dependency the whole
extraction exists to remove, since that numbering is what the two emit paths
disagree about. The cut is now by time, which needs no numbering.

Two things found on the way that the plan had not anticipated:

- **`ACK[i]` means different things on the two paths** — the ack of `DATA[i]`
  on the low-level path, an *i*-th-overall counter in either direction on the
  HTTP path. The corruption pass looks up `ACK[i]` by data index to shift its
  timestamp; run unchanged against an HTTP stream it would have silently
  shifted the wrong packet.
- **Adjacency is not a safe way to pair a segment with its ACK.** Both paths
  emit a segment and then its ack, so it looks safe — until loss removes one
  of them and the survivor sits beside an unrelated packet. Pairing is by
  sequence number instead.

### The reproducibility break

Reordering RNG draws changes seeded output. `generate_tcp_stream` documents
that "the same seed reproduces the whole capture", so existing seeds will
produce different captures after this. Unavoidable if the passes are shared,
and it needs a `Changed` entry saying so plainly. The `testcases/*.pcap`
fixtures (`packet_loss.pcap`, `retransmission.pcap`, `payload_corruption.pcap`,
`stray_1.pcap`, `sudden_termination_*.pcap`) should be checked for tests that
pin exact bytes.

### The trim, if the milestone runs long

**Loss + retransmission + corruption** via the extracted post-pass covers the
reporter's actual need — a gap in the middle of a message a decoder is part-way
through. **RST + strays deferred** to a follow-up issue. That is roughly a day
instead of two to three, and it is a clean split because those two are exactly
the passes with the bidirectionality questions.

### Tests

Existing `generate_tcp_stream` impairment tests must keep passing (adjusting
only for seeded-output changes); the same impairments applied to an HTTP stream
drop/duplicate/corrupt the expected proportion; per-flow isolation with
`--sessions > 1`; impairments plus `chunked_rate` together; the VPN subset; and
the warning appearing only for flags that genuinely do not apply.

The case worth writing carefully, and the reason `--mss` is in scope: a small
MSS plus `--packet-loss` leaves a message **partially** delivered — a gap in
the middle of a body a decoder is already part-way through — rather than
removing it whole.

### Undecided

5. **Warning or error for an ignored option?** The issue asks for a decision
   either way. *Recommendation: add `--strict`, keep warning as default.* The
   failure mode being reported — a test suite that believes it is exercising
   packet loss and is not — is exactly the kind an exit code catches and a
   stderr line does not.

   **Decided (Adam, 2026-08-27): warning only, no `--strict`.** The warning is
   now narrow enough to be actionable — it fires only for the three options
   that genuinely cannot apply to UDP, and names them.
6. **Is the seeded-output change acceptable in 0.9.0?** *Recommendation: yes,
   under `Changed` with `Breaking:`.* Pre-1.0 policy allows it, and the
   alternative is preserving RNG call order across a refactor, which would
   constrain the design for the sake of captures nobody has archived.

   **Decided (Adam, 2026-08-27): preserve exact draw order.** Achieved for 108
   of 112 combinations; the exception is `--server-rst` with `--packet-loss`,
   documented above and under `Fixed` in the changelog rather than as a
   `Breaking:` change, since the old behaviour was incorrect.
7. **Full set or the loss/retrans/corruption subset?** Depends on how #81/#82
   land. Decide at the point #82 merges, not now.

   **Decided (Adam, 2026-08-27): all five.** The bidirectionality questions
   resolved more cleanly than feared: a RST is still sent by the server, and
   the split point is a data segment in either direction.
8. **What should `--payload vpn` get?** Raised once the UDP finding landed.

   **Decided (Adam, 2026-08-27): loss and corruption, with a narrowed
   warning.** Stray payload sizes come from the existing
   `--min-payload`/`--max-payload`, so no new knob was needed.

## #68 — Fragment transport length and checksum

**Done, `df317ff`.** Landed as planned, including the "only when it differs"
filter that was the one real design question. See *What the filter caught*
below.

Independent of the HTTP chain; runnable in parallel.

### Verified

Reproduces exactly, and the issue's numbers are right to the byte. A 1032-byte
UDP datagram fragmented at MTU 576, round-tripped through `packeteer parse` →
`packeteer build`:

```
frag 0: identical=False  len=586/586   differing bytes: [38, 39, 40, 41]
  original UDP len,cksum: (1032, 2577)
  rebuilt  UDP len,cksum: (552, 15102)
frag 1: identical=True   len=514/514
```

Offsets 38–41 are precisely the UDP length and checksum fields. Everything else
round-trips, and later fragments are byte-identical — the damage is exactly the
four bytes the issue names.

The spec for fragment 0 confirms the cause; the `transport` section has nowhere
to put either value:

```json
"transport": {"src_port": 12345, "dst_port": 9999}
"network":   {"src": "10.0.0.1", "dst": "10.0.0.2", "protocol": "udp",
              "ttl": 64, "identification": 15597, "flags": 1}
```

### Implementation — option 1, record the captured values

The issue's option 1 over option 2, for the reason it gives: a spec addition
rather than a special case, backwards compatible since both keys are optional,
and useful beyond fragmentation — it becomes the only way a spec can express a
deliberately wrong checksum, which today only the byte-level fuzzer can do.

The parse side is nearly free. Both parsers already unpack the fields and
throw them away:

- `src/packeteer/parse/udp.py:32` — `src_port, dst_port, length, _ = unpack(...)`
- `src/packeteer/parse/tcp.py:122` — `window, _, urgent_ptr = unpack(...)`

Replacing the `_` and carrying the values is the whole capture step. Then:

- `UDPHeader` (`generate/udp.py:31`) gains `length: int | None = None` and
  `checksum: int | None = None`; `TCPHeader` (`generate/tcp.py:117`) gains
  `checksum: int | None = None` (no length field of its own — for TCP only the
  pseudo-header length used for the checksum is wrong).
- `_build_udp_header` / `_build_tcp_header` use the override when present and
  derive as now when absent.
- `PacketBuilder.udp()` / `.tcp()` gain the keyword arguments
  (`builder.py:1209`, `:1231`).
- `_dispatch_transport` (`__main__.py:470`) reads the new spec keys.
- `_apply_transport` (`parse/to_config.py:345`) emits them.

Blast radius is small: parse and generate share the header dataclasses, and
only five sites construct them.

### The one real design question

`_apply_transport` must emit `length`/`checksum` **only when the captured value
differs from the derived one**. Emitting them unconditionally would add two
keys to every packet in every spec — noise in the common case, and louder
round-trip diffs forever. That means computing the expected value at
serialisation time and comparing, which is the part of this issue that is
actually work rather than plumbing.

### What the filter caught

The "emit only when it differs" rule is tight, and the corpus says so. The keys
appear on:

| capture | packets carrying them | what they are |
|---|---|---|
| `fragmentation.pcap` | 59 of 287 | the first fragments — the same 59 datagrams #72 counted as reassembled |
| `payload_corruption.pcap` | 11 of 218 | packets whose checksum was wrong on the wire |
| the other eleven captures | 0 | — |

Byte-exact round trips improved exactly there and nowhere else:
`fragmentation.pcap` 115 → **174** of 287, `payload_corruption.pcap` 100 →
**111** of 218, with `udp`, `no_errors`, `delay` and `sctp` unchanged.

The comparison lives in `parse/core.py`, not in `to_config`: `update_config` is
handed a bare header, while the parse walk is the one point holding the IP
header, the transport header and the payload at once.

**A separate round-trip gap, found while measuring this and not part of #68:**
`no_errors.pcap` rebuilds 100 of 207 packets byte-for-byte both before and
after. The difference is Ethernet padding — the builder pads a frame to the
60-byte minimum and those captures hold unpadded 54-byte frames. Every byte
before the padding matches. Filed as

### Tests

## #85 — Packet loss leaves acknowledgements behind

**Done: `f18f0e6`** (the correction) **and `e359992`** (the recovery knob).
One thing had to be added that the plan did not foresee — see *The SYN
exemption* below.

Filed during #83 and added to the milestone afterwards. It predates that work
— it reproduces on 0.8.0 and every earlier version with `--packet-loss` — but
#83 made it reach two more paths, which is why it surfaced now.

### The semantics, settled

**Decided (Adam, 2026-08-27): a lost packet is lost on the wire.** Neither the
capture point nor the receiver sees it. A receiver therefore cannot acknowledge
it, and cannot acknowledge anything after it either, because TCP
acknowledgements are cumulative.

That reading is what makes the current model wrong rather than merely loose.
The alternative reading — loss at the capture point, a tap missing frames —
would have made the existing output defensible, so this was worth settling
before any code moved.

### Verified

Eight 100-byte segments at `--packet-loss 0.25`, seed 3:

```
label      dir           seq          ack  len
SYN        c2s    2337446730            0    0
ACK[0]     s2c    2593816830   2337446831    0     <- acks DATA[0], which is not here
ACK[1]     s2c    2593816830   2337446931    0     <- acks DATA[1], which is not here
DATA[2]    c2s    2337446931   2593816830  100
DATA[3]    c2s    2337447031   2593816830  100
ACK[3]     s2c    2593816830   2337447131    0
...
ACK[7]     s2c    2593816830   2337447531    0     <- acks DATA[7], which is not here
```

Reproduces on the payload paths too, via `apply_packet_loss`.

### Three consequences, in increasing order of how wrong they are

1. **An ACK for a segment that is not in the capture.** The visible symptom.
2. **Every later acknowledgement is overstated.** The bigger one, and not
   fixed by dropping the first ACK. With `DATA[0]` and `DATA[1]` gone,
   `ACK[3]` still claims every byte through segment 3. A real receiver stops
   advancing at the gap and repeats its last in-order ack — a run of
   **duplicate ACKs**, which is the signal fast retransmit is built on and what
   an analyser looks for around a loss event.
3. **A lost control packet produces an impossible conversation** — a capture
   whose SYN is missing but whose exchange proceeds, or where the client sends
   data after a lost SYN-ACK on a connection that was never established.

### The structural consequence #83 leaves behind

Loss is applied in two different places, and this issue invalidates one of
them:

- `emit()` in `tcp_stream.py:484` decides per packet, at emission time.
- `apply_packet_loss` in `impairments.py:224` filters the finished list, which
  is how the payload paths get loss.

That second form rests on an equivalence written into its own docstring:
dropping a packet afterwards leaves the same hole in the timeline as never
emitting it, because timestamps come from emission position. **That
equivalence stops holding here.** Suppressing the acknowledgement of a lost
segment needs the decision made where the ACK is about to be emitted, so
`TCPSession` has to learn about loss and `apply_packet_loss` loses its reason
to exist. Its docstring claims the equivalence in as many words and must not
be left saying so.

### Implementation

Staged, because the last step is a design question rather than a correction:

1. **Suppress the acknowledgement of a lost segment.** Move the drop decision
   into the data-transfer loop on both paths — `generate_tcp_stream`'s loop and
   `TCPSession.build` — and retire `apply_packet_loss`.
2. **Clamp later acknowledgements to the last in-order byte**, so the segments
   after a gap are answered with duplicate ACKs until it is filled. This is
   what makes generated loss look like loss to anything that reads a capture.
3. **Decide whether a lost segment is retransmitted** — see the open question
   below.

### Interaction with what #83 just landed

- `_ack_positions` pairs by sequence number, so a run of duplicate ACKs gives
  several bare ACKs with the same `ack` value. It takes the first via
  `setdefault`, which is the right one, but worth a test rather than an
  assumption.
- The RST pass cuts acknowledgements **by time**, not by sequence number, so
  duplicate ACKs do not disturb it.
- Corruption and stray injection do not read acknowledgements at all.
- `apply_datagram_impairments` is unaffected: UDP has no acknowledgements.

### Tests

A lost segment leaves no ACK behind; acknowledgements after a gap repeat the
last in-order value rather than advancing; the count of duplicate ACKs matches
the number of segments delivered after the gap; loss on the payload path
behaves the same way at a small `--mss`; and the property that should hold over
any generated capture — **no acknowledgement names a byte the capture never
carried.** That last one is worth writing as a sweep over several seeds and
rates, since it is the whole issue stated as an invariant.

### The SYN exemption, which the plan did not foresee

Implementing steps (1) and (2) made consequence (3) *worse* rather than
better. With the acknowledgement rule corrected, a dropped SYN-ACK leaves the
client never learning the server's initial sequence number, so every later
segment came out carrying `ack=0` — visibly malformed, where before it had
merely been implausible.

**The SYNs are now exempt from loss.** It is the narrowest fix: everything
after the handshake, teardown included, can still be lost, and a lost FIN or
final ACK produces a perfectly plausible capture. Modelling the real outcome —
a connection that never establishes — needs setup retransmission the generator
does not have.

At 100 % loss the output is now `["SYN", "SYN-ACK"]` rather than nothing, and
the test that encoded the old expectation was updated to say why.

### The result

The blast radius came out exactly where intended. Against digests of 112 seed
and option combinations, **the 32 involving `--packet-loss` moved and the
other 80 did not**, and both payload paths are byte-identical when no
impairment is configured.

`apply_packet_loss` is gone, as the plan predicted. Its docstring claimed
dropping a packet afterwards was equivalent to never emitting it — true of
timestamps, false once a loss has to suppress a dependent acknowledgement.
What survives is private and documented as correct for connectionless flows
only.

### Undecided

9. **Is a lost segment retransmitted?** Real TCP recovers, so a connection that
   loses a segment and never resends it stalls. The current model has no
   recovery at all, so a lossy stream simply carries a permanent hole.

   *Recommendation: make it a knob, defaulting to no recovery.* Both are worth
   generating — a decoder should survive either — and the no-recovery case is
   the harsher input, which is what this generator is for. It must **not** be
   folded into `retransmission_probability`, which today means a *spurious*
   retransmission of a segment that did arrive; that is a different event and
   overloading it would make both unreadable.

   Step (3) also raises what the teardown should look like when the byte range
   was never completed, since a graceful four-way close is not what a real
   connection would do after an unrecovered loss.

   **Decided (Adam, 2026-08-28): a knob, defaulting to no recovery.** Shipped
   as `--retransmit-lost` / `ImpairmentConfig.retransmit_lost`, kept separate
   from `retransmission_probability` for the reason above.

   The part worth recording is what makes it look like recovery rather than a
   replayed packet: the acknowledgement following the retransmission covers
   everything contiguous the receiver holds by then, so a receiver that had
   been repeating its last in-order value **jumps forward in one step** over
   every segment it had been holding behind the gap. That needs the delivered
   byte ranges rather than a running counter.

   The teardown question is left as it was: a graceful close still follows an
   unrecovered loss. Worth its own issue if it matters to a consumer.

### Changelog

`Fixed`. Steps (1) and (2) change what `--packet-loss` produces for every seed,
so they should land in one change rather than two — the output should move
once — and the entry must say so plainly.

Worth noting in the same entry that #83's byte-identity work is not undone by
this: that was about not moving output gratuitously during a refactor, and this
moves it deliberately, to correct it.

## #86 — Short Ethernet frames get padded on rebuild

**Done, `b670062`.** Landed as planned, and the corpus assertion it was for now
passes — see *The result* below.

Found while measuring #68, and independent of it: the numbers are identical
before and after that change.

### Verified

`build` pads to the 60-byte Ethernet minimum; `parse` records nothing about
whether the frame it read was padded. A captured 54-byte frame therefore
rebuilds as 60 bytes, with every original byte correct and six zeros appended.

**Padding is now the entire remaining round-trip gap.** In every capture in
the corpus, three counts come out equal — frames under 60 bytes, packets that
differ, and packets that differ *only* by padding:

| capture | packets | < 60 bytes | differ | differ only by padding |
|---|---|---|---|---|
| `no_errors.pcap` | 207 | 107 | 107 | **107** |
| `delay.pcap` | 207 | 107 | 107 | **107** |
| `retransmission.pcap` | 219 | 107 | 107 | **107** |
| `packet_loss.pcap` | 193 | 99 | 99 | **99** |
| `stray_1.pcap` | 208 | 107 | 107 | **107** |
| `sudden_termination_1.pcap` | 53 | 28 | 28 | **28** |
| `fragmentation.pcap` | 287 | 113 | 113 | **113** |
| `sctp.pcap` | 207 | 4 | 4 | **4** |
| `udp.pcap` | 100 | 0 | 0 | 0 |

Nothing else differs anywhere. Fixing this makes `parse` → `build` byte-exact
over the whole corpus: `fragmentation.pcap` 174/287 → **287/287**,
`no_errors.pcap` 100/207 → **207/207**.

That makes #86 worth more than its size suggests. It is the difference between
"the round trip is exact except for a long tail" and "the round trip is exact",
and the corpus becomes a regression test that can assert the latter.

### Why it survived this long

Short frames are the ordinary TCP control packets — SYN, bare ACK, FIN — so
this is not an exotic case. It went unnoticed because it depends on where the
capture was taken: padding is added by the NIC, so a capture taken above the
driver never sees it, while a frame that *was* padded on the wire arrives at
60 bytes and rebuilds at 60 bytes, correctly.

### Implementation — smaller than it looks

The build side is already complete: `EthernetHeader.pad`,
`PacketBuilder.ethernet(pad=…)`, and the spec key `ethernet.pad`, read at
`__main__.py:881`. **Only the parse side is missing.** `_apply_ethernet` in
`parse/to_config.py` writes `src_mac`, `dst_mac`, `enabled` and VLAN tags, and
never writes `pad`, so `build` falls back to its `True` default.

Follow the shape #68 settled on — record the anomaly, stay silent otherwise:

- The Ethernet parser sets `pad=False` when the frame is under 60 bytes.
- `_apply_ethernet` emits `"pad": false` only when it is `False`, so ordinary
  specs gain no key.
- Nothing on the build side changes.

### The one thing to get right

Where the length test lives. The Ethernet parser sees the whole frame and can
measure directly, but a tunnelled inner frame is parsed by a recursive
`parse_packet` call, where "the frame" is the inner one rather than the
captured one. An inner frame under 60 bytes is normal and must **not** be
marked unpadded on that basis — the padding rule applies to what was on the
wire, which is the outer frame. Worth a test at two tunnel depths.

### The result

Every one of the eleven shipped `*.pcap` captures now rebuilds byte-for-byte —
2 271 packets, no exceptions — and `test_frame_padding.py` asserts it as a
subtest per capture.

The trap was where the plan said it would be, and `_shift_offsets` turned out
to be the right home for the correction: it is already the one place that knows
a frame was nested, and all seven recursive `parse_packet` call sites go
through it, which was worth checking rather than assuming.

**A third round-trip gap, found by the same sweep and not part of #86.** The
two `*.pcapng` captures still do not round-trip, and `http_example.pcapng`
fails on all 13 packets even with `--no-decode-app`. Every one differs *only*
inside the TCP options field:

```
captured options: 0101080a21c6e61e65f1e0d5    NOP, NOP, Timestamps
rebuilt  options: 080a21c6e61e65f1e0d50101    Timestamps, then NOP NOP
```

`_build_options` pads to the 4-byte boundary by appending NOPs, while senders
put them first so the option itself aligns. Semantically identical, byte
different — and since timestamps are near-universal in modern TCP, this affects
most real captures. Filed as
[#87](https://github.com/adamkjonsson/packeteer/issues/87) and added to this
milestone; it is the last known gap.

### Tests

A short frame round-trips at its captured length; a genuinely padded 60-byte
frame still round-trips (the case that works today and must keep working);
`pad` is absent from an ordinary spec; tunnelled inner frames are not marked;
and the corpus assertion this issue makes possible — **every packet in every
`testcases/` capture rebuilds byte-for-byte**, which is worth writing as a
sweep now that it can pass.

### Changelog

`Fixed`. Worth stating the corpus result, since it is the first point at which
the round trip is exact rather than nearly exact.

## #87 — TCP options rebuilt with the padding in the wrong place

**Done, `0974e84`.** Landed as planned. **Every shipped capture now rebuilds
byte-for-byte** — see *The result* below.

Found by the corpus sweep #86 added. It is the **last known gap** in the round
trip.

### Verified

Options are re-encoded in a canonical order with NOP padding appended; senders
put the NOPs first so the option itself lands aligned:

```
captured: 0101080a21c6e61e65f1e0d5     NOP, NOP, Timestamps
rebuilt : 080a21c6e61e65f1e0d50101     Timestamps, then NOP, NOP
```

Same length, same option, same values, different bytes. The rebuilt region
parses back to an identical `TCPOptions`, so nothing downstream of a parse
notices — only the wire bytes differ.

**It hits real captures and no synthetic ones**, which is why it hid until the
sweep existed:

| capture | TCP packets | with options | options byte-exact |
|---|---|---|---|
| `http_example.pcapng` (real) | 13 | **13** | **0** |
| every shipped `*.pcap` (generated) | 1 314 | **0** | — |

All twelve distinct option layouts in that capture are the same shape:
`NOP, NOP, Timestamps` becoming `Timestamps, NOP, NOP`. Timestamps are
near-universal on modern TCP, so in practice this affects most real captures on
most of their packets.

### It is a documented decision, not an oversight

`_build_options` says so in as many words: the order "is canonical rather than
a replay of whatever a capture contained, so a parse → build round trip
preserves every option's presence and value but not necessarily its original
byte layout". `_parse_options` likewise skips NOP and EOL as "structural
padding … not modelled".

So this is a request to revisit a deliberate choice, now that it is the one
thing between the project and an exact round trip. Worth keeping in mind when
writing the changelog entry: the old behaviour was chosen, not missed.

### Why no canonical order can fix it

Senders disagree. Linux emits `MSS, SACK-perm, TS, NOP, WS` on a SYN; macOS
emits `MSS, NOP, WS, NOP, NOP, TS, SACK-perm, EOL`. Matching one breaks the
other, so reproducing the captured bytes is the only approach that works in
general — which is the same conclusion #68 reached about transport lengths.

### Implementation — the cheapest of the three

Same shape as #68 and #86, and unusually contained: everything needed sits
inside one function. `_parse_options` is handed the raw option region and
produces the `TCPOptions` it decoded, so it can re-encode and compare on the
spot.

- `TCPOptions` gains `raw: bytes | None = None`.
- `_parse_options` sets `opts.raw = data` when `_build_options(opts) != data`.
- `_build_options` returns `opts.raw` verbatim when set.
- `to_config` emits `transport.options.raw` as hex when present;
  `_parse_tcp_options` reads it back.

No `parse/core.py` involvement, unlike #68 — the comparison needs only the
option region, which `_parse_options` already holds.

### The footgun to document

With `raw` set, editing `mss` or `timestamps` on the same `TCPOptions` has no
effect, because `raw` wins. The docstring must say to clear `raw` when editing
fields. Detecting a changed field automatically is more trouble than it is
worth and would make the precedence rule harder to explain, not easier.

### The result

| capture | packets | round-trips |
|---|---|---|
| all eleven `*.pcap` | 2 271 | **all** |
| `http_example.pcapng` | 13 | **all** — was 0 |
| `dns_example.pcapng` | 8 | **all**, with `decode_app=False` |

The one remaining exception is `dns_example.pcapng` parsed with app decoding
on: re-encoding a decoded DNS message normalises it. That is the documented
`--no-decode-app` caveat and has nothing to do with option layout, so the
corpus test parses with `decode_app=False`.

The key stays quiet where it is not wanted. It appears on 13 packets across the
whole corpus — all of `http_example.pcapng`, the one real capture — and on none
of the 1 314 TCP packets in the generated captures, which carry no options at
all. That last fact is what became #88.

The estimate held: this was the cheapest of the three round-trip fixes, and
needed no `parse/core.py` involvement.

### Tests

A capture whose options carry leading NOPs round-trips byte-for-byte; an
option set the canonical encoder *does* reproduce leaves `raw` unset, so
ordinary specs gain no key; `raw` survives to the spec and back as hex; editing
a field with `raw` set behaves as documented; and the corpus sweep from #86
extends to the `*.pcapng` captures — at which point **every shipped capture
round-trips**, which is the assertion worth having.

`dns_example.pcapng` will still need `--no-decode-app` to be exact, since
re-encoding a decoded DNS message normalises it. That is the documented
`--no-decode-app` caveat and a separate matter from this issue.

### Related, and deliberately out of scope

Generated traffic will still emit `Timestamps, NOP, NOP`, since `packeteer
stream` has no captured bytes to replay. A synthetic capture whose option
layout no real stack produces is distinguishable from real traffic by exactly
the tools packeteer exists to feed — a realism question for the generator, not
a round-trip question.

Filed as [#88](https://github.com/adamkjonsson/packeteer/issues/88),
**unmilestoned pending a decision**. Investigating it found the problem is
wider than the padding: a generated SYN carries **no TCP options at all**, the
payload paths cannot carry any (`TCPSession` passes `None` unconditionally and
has no parameter for them), and `packeteer stream` has no CLI or config surface
for them either — so `--mss 128` segments at 128 bytes while advertising no MSS
option, leaving the capture unable to say what MSS was in force.
